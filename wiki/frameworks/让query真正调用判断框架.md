# 让 query 真正调用判断框架

## 问题是什么

当前仓库已经积累出几类很有价值的中间层：

- `wiki/topics/` 里的世界知识与概念框架
- `wiki/frameworks/` 里的高复用判断入口
- `wiki/topics/` 里的具体应用分析

但如果 query 只是“找几页相关内容然后总结一下”，它其实仍然更像一个增强检索器，而不是一个真正站在判断框架上工作的系统。

结果就是：

- 能答，但不够深
- 会引用页面，但不一定真正调用其中的 framing
- 能复述结论，但不一定能把多个框架压成更高层判断
- 容易得到“正确但平”的回答

这个问题本质上不是资料不够，而是 **query 的默认工作面还不对**。

## 本库已有材料其实已经给出答案方向

### 1. 默认工作面比信息存储更关键

[信息复利系统设计](../topics/context-memory-knowledge-system/information-compounding-systems-design.md) 已经给出最关键的一句：

> 真正重要的，不是系统有没有保存足够多的信息，而是未来的高价值工作，到底默认站在哪一层上发生。

如果 query 发生时，agent 仍然主要站在“零散相关页 + 临场拼接”的层上，那说明这些框架虽然存在，但还没有成为默认工作面。

### 2. 这个仓库本来就不是单纯 QA 系统

[知识库运行模型](../topics/context-memory-knowledge-system/knowledge-base-operating-model.md) 和 [本地知识库模式](../topics/context-memory-knowledge-system/local-knowledge-base-patterns.md) 都明确了：

- `knowledge` 负责世界知识
- `frameworks` 负责高复用、低噪音的判断框架与 query 入口
- `bridges` 负责把这些层重新组合成具体建议

也就是说，真正高价值的 query，不应该直接停留在知识摘要层，也不应该默认继续往 bridge 堆页，而应先经过 framework 这一层再决定是否需要具体应用分析。

### 3. 高价值 query 应该产出新的工作面，而不是只消耗旧页面

[课题组公共研究知识库的产品化与评测策略](../topics/research-knowledge-governance/lab-research-knowledge-base-product-strategy.md) 里已经把这点说得很清楚：

- 系统的价值不只是回答问题
- 更重要的是把高价值判断持续沉淀回公共工作面

如果 query 每次只是消费已有页面，而不把新的高质量综合写回 `frameworks/` 或在必要时写回 `bridges/`，那么框架永远只是“库存”，不会变成越来越强的判断层。

### 4. 这个仓库天然在反对“共识化平回答”

[AI 知识系统的产品定义信念](../topics/context-memory-knowledge-system/ai-knowledge-systems-product-definition-beliefs.md) 和 [课题组公共研究知识库的产品化与评测策略](../topics/research-knowledge-governance/lab-research-knowledge-base-product-strategy.md) 都指向同一个风险：

- 如果系统只是从已有材料里找最大公约数
- 它会越来越擅长总结共识
- 但越来越难产生有区分度的判断

所以你现在感受到的“不够深”，很多时候不是 query 失败，而是 query 仍停留在“找共识、做摘要”的工作模式里。

## 为什么这个问题在仓库层尤其重要

这个问题重要，不是因为 query 需要读更多页，而是因为仓库已经开始具备框架层，却还可能在执行时滑回普通摘要模式。

一旦发生这种滑回，系统就会出现三个问题：

1. 已有框架没有真正变成默认工作面
2. 高价值 query 不能稳定产出新的框架入口
3. 回答会越来越像共识化整理，而不是有区分度的判断

所以这里真正要优化的，不是检索覆盖率，而是让 query 更稳定地先站在 `frameworks/` 上，再去调用 `knowledge/` 与 `bridges/`。

## 我会怎么优化

我会把优化拆成三层：query 规则、仓库结构、评测方式。

---

## 一、先改 query 规则：从“找相关页”改成“激活框架”

### 1. 给 query 增加一个显式的“框架激活”步骤

在正式回答前，不要直接开始总结，而是先强制完成四件事：

1. 这是什么类型的问题：事实、建议、评估、设计、比较、决策
2. 这次最该调用的 **上位框架** 是什么
3. 这次最该调用的 **领域页** 是什么
4. 这次最该调用的 **具体 bridge 或案例页** 是什么

例如一个产品定义问题，query 不该只读主题页，而应先明确：

- 上位框架：`默认工作面` / `信息复利`
- 领域页：某个具体产品或架构页
- 具体应用页：某个产品定义或方案分析页

这样回答才会自然更像“判断”，而不是“摘要”。

### 2. 把输出结构改成固定三层

对 advisory query，默认强制输出三层：

1. **材料层**：现有页面已经说明了什么
2. **框架层**：这次回答到底站在哪个判断框架上
3. **结论层**：结合材料与框架后，最合理的建议是什么

这个结构其实已经写在 `schemas/query.md` 里，但执行上可以更硬一点。否则 agent 很容易直接滑回普通总结模式。

### 3. 回答前先要求 agent 说出“本次最关键的张力”

深度回答和普通回答最大的差别，常常不是信息更多，而是它能指出核心张力。

比如：

- 复利 vs 即时可用
- 共识提炼 vs 反共识判断
- 通用性 vs 默认工作面质量
- 更多材料 vs 更高密度中间层

如果 query 前没有这一步，回答往往会变成把几页内容拼平。

### 4. 少做“面面俱到”，多做“主判断 + 边界”

深度回答通常不是把所有点都说一遍，而是：

- 先给一个主判断
- 再给这个判断的适用边界和反例

这点也很适合写进 query 规则。否则 agent 为了显得全面，很容易稀释锋利度。

---

## 二、再改仓库结构：不要让 query 每次都从零拼框架

### 1. 增加“框架入口页”，而不是只靠分散主题页

现在很多判断框架散在不同页面里。人读起来没问题，但 query 时 agent 仍然要临场判断哪些框架应一起调用。

更稳的做法，是增加几类高密度入口页，例如：

- `产品判断框架入口`
- `研究判断框架入口`
- `职业判断框架入口`
- `AI 系统设计框架入口`

这些页不需要很长，重点是回答：

- 常用上位框架有哪些
- 它们各自适用于什么问题
- 哪些知识页和 bridge 页常常应该一起读

这相当于给 query 一个更好的“framework router”。

### 2. 对高频问题，优先写 framework 页，必要时再写 bridge 页

不要期待 query 每次临场把 `knowledge + bridges` 拼得很好。更好的方式是：

- 一旦某类问题重复出现
- 先判断它更像高复用入口，还是具体应用分析
- 高复用入口写进 `frameworks/`
- 具体结论再写成 bridge

例如：

- 如何做产品边界取舍
- 如何判断一个知识系统的默认工作面
- 如何区分知识编译问题和判断蒸馏问题

这样下次 query 时，agent 先站在 `frameworks/` 上，再决定要不要继续调用具体 bridge，而不是重新站在原始分散页上。

### 3. 把“反共识判断”单独沉淀出来

如果一个系统只把框架沉淀成共识版总结，query 自然很难变深。

所以可以逐渐增加一类页面，专门记录：

- 常见误判
- 反例
- 不值得做的方向
- 某类框架最容易被误用的方式

这类页面会显著提高 query 的区分度。

---

## 三、最后改评测：不要只看答得对不对，要看有没有真正调用框架

如果想知道优化是否有效，我会用下面几条标准看 query：

### 1. 有没有明确站在某个上位框架上回答

不是只提到框架名，而是回答结构真的被那个框架组织起来。

### 2. 有没有把 `knowledge`、`frameworks` 和 `bridges` 分层调用再重组

如果几层混成一团，说明系统还在普通总结模式。

### 3. 有没有指出核心张力，而不只是列观点

深度感往往来自张力显化。

### 4. 有没有给出真正的下一步动作

不是停留在理解层，而是把判断推进到“所以接下来该怎么做”。

### 5. 有没有把高价值回答写回仓库

如果一次好回答没有形成新的 bridge 或更新某个入口页，那下次大概率还要重新来一遍。

## 一个最小可行的改法

如果不想一下子改很多，我建议先做最小闭环：

### 第一步：只改 query prompt / schema

给 advisory query 增加三个硬要求：

1. 回答前先列出本次调用的 1 个上位框架、2 到 4 个核心页面
2. 回答必须按“材料层 / 框架层 / 结论层”组织
3. 回答末尾必须给出“如果这类问题会重复出现，应该回写成什么页面”

### 第二步：补 2 到 3 个高频框架入口页

优先补你最常问的那一类，而不是做大全。

### 第三步：把最好的几次 query 手工回写成 framework 或 bridge

这样可以测试：

- 回写后，下次回答是否明显更快更深
- 哪些问题值得提前编译成 framework，哪些问题适合保留为具体 bridge

## 一句话结论

你现在遇到的问题，不是 wiki 里没有框架，而是这些框架还没有成为 query 的默认工作面。

所以优化重点不该是“再读更多页”，而是：

> 让 query 从“相关内容检索器”升级成“框架激活器”，并把高质量回答优先写回成新的 framework 工作面，只有在需要具体分析时才进入 bridge。

这样，深度就不再主要依赖当次模型状态，而会越来越依赖仓库本身已经积累起来的判断层。
