# 产品定义判断框架

这页服务于新产品定义、未来场景拆解、MVP 形态判断、记忆系统与 agent 产品定位这类问题。

它不回答“功能怎么做”，而是先回答“到底在定义什么产品”。

## 先看什么

遇到产品定义问题时，优先先问六件事：

1. 真正值得优化的高价值问题是什么
2. 用户是谁，关键场景是什么，代价最大的摩擦在哪里
3. 这到底是搜索工具、研究助手、行为教练，还是别的产品
4. 什么是最小但仍然像 magic 的 MVP
5. 成功怎么定义，也就是什么算完成、什么算有效
6. 第一性决策到底是用途、边界和上下文，还是只是技术栈选择

## 核心判断

### 1. 最重要的架构决策，往往发生在写第一行代码之前

很多看似技术问题，真正的分水岭其实是产品定义问题。核心问题一变，目标、交互、输出格式和技术架构都会一起变。

主要依据：
- [AI Architect Lens](../knowledge/ai-architect-lens.md)

### 2. builder 先看功能，architect 先看高价值问题

同一组能力可以被包装成完全不同的产品。差别不在“能不能做”，而在“到底在解决哪个更值钱的问题”。

所以产品定义的第一步，不该是列 feature，而该是先找：

- 真正的痛点
- 痛点为什么重要
- 这个问题被解决后，用户世界里什么会明显变好

主要依据：
- [AI Architect Lens](../knowledge/ai-architect-lens.md)

### 3. 先写 `Product Definition Brief`，再进入实现

在这类问题里，第一阶段产物不该是 prompt、页面或代码，而该是一份足够清楚的 brief，至少回答：

- 核心问题是什么
- 用户是谁，关键场景是什么
- MVP 的最小形状是什么
- 成功标准和 acceptance criteria 是什么

没有这一层，后面的实现很容易只是更快地做错东西。

主要依据：
- [AI Architect Lens](../knowledge/ai-architect-lens.md)

### 4. 同一能力，不同目标，会导向不同产品

例如同样是实时辅助系统，它可以是：

- 信息外包系统
- 行为表现教练

同样是记忆系统，它可以是：

- 快速事实检索工具
- 研究助手
- 长期模式发现系统

一旦目标不同，所需数据、反馈闭环、评测方式和架构重点都会不同。

主要依据：
- [AI Architect Lens](../knowledge/ai-architect-lens.md)
- [AI Architect 的 Context Intelligence 镜头](../knowledge/ai-architect-context-intelligence.md)

### 5. MVP 的标准不是越糙越快，而是最小且足够可被判断

一个有效 MVP 不只是能运行，还要足够像一个值得被评估的产品。否则测试到的可能只是粗糙感，而不是假设本身。

“最小”不等于“半成品”。更准确的说法是：最小但仍然能让用户产生真实反应。

主要依据：
- [AI Architect Lens](../knowledge/ai-architect-lens.md)
- [Pre-PMF 验证手册](../knowledge/pre-pmf-validation-playbook.md)

### 6. 对 AI 记忆系统，第一性决策是用途与边界，不是向量库

高价值记忆系统首先在做个人上下文移植，而不是单纯教模型更多公共知识。

因此更先该问的是：

- 它服务事实检索，还是深层模式发现
- 它更像搜索框，还是研究助手
- 它应该知道什么，不该知道什么
- 访问边界和信任边界怎么划

这些问题比“先选哪种 RAG 技术”更接近决定性选择。

主要依据：
- [AI Architect 的 Context Intelligence 镜头](../knowledge/ai-architect-context-intelligence.md)
- [AI 知识系统的产品定义信念](../knowledge/ai-knowledge-systems-product-definition-beliefs.md)

## 常见张力

- 可能性能做 vs 值不值得做
- feature 列表 vs 高价值问题
- MVP 速度 vs 测试可信度
- 通用能力 vs 明确产品主语
- 全量上下文接入 vs 信任边界
- 技术栈选择 vs 产品定义选择
