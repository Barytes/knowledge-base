# 知识系统判断框架

这页服务于知识系统、query、memory system、仓库分层这类问题。

它不是完整分析，而是一张高频判断表。

## 先看什么

遇到知识系统问题时，优先先问四件事：

1. 未来高价值工作默认站在哪一层上发生
2. 这里面对的是知识编译问题，还是判断蒸馏问题
3. 现在缺的是材料存储，还是可调用的工作面
4. 这次产物更像框架入口，还是具体应用分析

## 核心判断

### 1. 默认工作面比信息存储更关键

真正重要的不是存了多少信息，而是未来任务是不是先站在一个已经提炼过的中间层上工作。

如果每次 query 仍然主要回到 raw 或分散页面重新拼装，系统就还没有形成复利。

主要依据：
- [信息复利系统设计](../topics/context-memory-knowledge-system/information-compounding-systems-design.md)

### 2. 先区分知识编译与判断蒸馏

- `llm-wiki` 类问题更像把高信号外部材料编译成可维护 wiki
- `context-infrastructure` 类问题更像从高噪音个人痕迹里提炼稳定判断

这两类问题都在做“压缩”，但数据分布、失败模式和最佳层次不同。

主要依据：
- [AI 知识系统的产品定义信念](../topics/context-memory-knowledge-system/ai-knowledge-systems-product-definition-beliefs.md)
- [本地知识库模式](../topics/context-memory-knowledge-system/local-knowledge-base-patterns.md)

### 3. wiki 本身可以是压缩层，不必急着再造更多层

很多时候真正该做的，不是继续发明新的中间表示，而是让 `wiki` 本身承担压缩、关联、回查和写回功能。

高价值信号常常会以“高复用 wiki 节点”的形式涌现出来，而不是必须先验定义成新的类型。

主要依据：
- [什么是公共知识库应该共享的公共知识](../topics/research-knowledge-governance/什么是公共知识库应该共享的公共知识.md)

### 4. `frameworks/` 和 `bridges/` 的职责必须分开

- `frameworks/` 放高复用、低噪音的入口页与判断框架
- `bridges/` 放具体情境下的分析、memo 和应用结论

如果什么 durable query 都进 `bridges/`，它会越来越大，也越来越像噪音池。

主要依据：
- [知识库运行模型](../topics/context-memory-knowledge-system/knowledge-base-operating-model.md)
- [让 query 真正调用判断框架](让query真正调用判断框架.md)

### 5. 优先追踪人的复用，而不是只看 agent 能不能检索到

一个知识页真正值不值得保留，更强的信号常常不是“能搜到”，而是：

- 人会不会回到这页
- 会不会基于这页继续提问、编辑、引用和分享
- 会不会把它带回后续工作流

主要依据：
- [什么是公共知识库应该共享的公共知识](../topics/research-knowledge-governance/什么是公共知识库应该共享的公共知识.md)

## 常见张力

- raw/wiki vs 蒸馏信号
- 可回查性 vs 默认工作面锋利度
- 高复用入口 vs 具体应用 memo
- 共识编译 vs 反共识判断
