# 框架路由入口

这页是 `frameworks/` 的默认入口。

对设计、评估、比较、决策类 query，优先先读这页，再决定进入哪个框架页，而不是直接去 `knowledge/` 或 `bridges/` 撒网。

`frameworks/` 应专注沉淀从 `knowledge/` 与 `bridges/` 中抽出来的高复用判断，不混入个人判断层内容。

## 使用原则

先判断问题类型，再选一个主框架。默认只选一个主框架起步；只有在张力明显跨域时，再补第二个框架。

推荐顺序：

1. 读这页
2. 进入一个最相关的 framework 页
3. 再按该页指向去读 `knowledge/`、`bridges/`
4. 只有当问题需要具体 memo 或应用判断时，才落到 `bridges/`

## 路由表

### 1. 知识系统 / query / memory system

适用问题：
- 这个知识库该怎么分层
- query 为什么不够深
- 什么该写进 `frameworks/`，什么该写进 `bridges/`
- `llm-wiki`、`context-infrastructure`、raw/wiki 之间怎么理解

先读：
- [知识系统判断框架](知识系统判断框架.md)
- [让 query 真正调用判断框架](让query真正调用判断框架.md)

### 2. 研究知识库 / 公共知识 / 方向筛选

适用问题：
- 研究知识库该先优化什么
- 怎样支持 gap、tension、反共识判断
- 为什么不能只做 QA
- 什么才算公共层应该共享的知识

先读：
- [研究判断框架](研究判断框架.md)

### 3. AI 产品 / agent / runtime / workflow

适用问题：
- 一个东西到底算不算 AI 产品
- 该做 RAG、workflow 还是 agent
- 复杂度到底卡在模型、runtime 还是契约
- 什么任务该交给 AI，什么判断不该外包
- harness 该做厚还是做薄
- subagent、compaction、skills、tooling 到底在补偿什么

先读：
- [AI 系统产品判断框架](AI系统产品判断框架.md)
- [Harness 架构判断框架](Harness架构判断框架.md)

### 4. 产品定义 / MVP / Pre-PMF / go-to-market

适用问题：
- 一个想法到底在定义什么产品
- 应该先做什么 MVP，什么才算足够可测试
- 这轮到底在验证哪条路径
- 反馈很多，但哪些算强信号
- 为什么不能只发布一次就下市场结论

先读：
- [产品定义判断框架](产品定义判断框架.md)
- [产品验证判断框架](产品验证判断框架.md)

### 5. 职业路径 / 求职 / market fit

适用问题：
- AI 时代职业路径怎么选
- 求职为什么海投失效
- 应该积累工资资格还是资产与选择权
- 如何把自己组织成市场能识别的产品
- 简历、面试、reference 与 reputation 该怎么一起看

先读：
- [职业判断框架](职业判断框架.md)
- [职业信号与叙事框架](职业信号与叙事框架.md)

### 6. 方向判断 / 执行卡点 / 学习与做事方法

适用问题：
- 现在该继续想还是先做
- 这是方向问题还是执行问题
- 为什么很多建议看起来彼此矛盾
- 该先搭框架还是先练手

先读：
- [方向与执行判断框架](方向与执行判断框架.md)

### 7. AI 产业 / 投资 / 创业位置

适用问题：
- AI 产业该怎么看层次与控制点
- 这条 AI 信号到底是事件、结构还是解释层变化
- 哪些环节在拿真钱，哪些环节主要靠资本预期
- 为什么 `Harness` 更像创业带，而不是再包一层通用软件
- 一个方向是在哑铃结构两端，还是卡在最危险的中间层

先读：
- [AI 产业与投资判断框架](AI产业与投资判断框架.md)

## 写回规则

- 如果结果主要回答“以后这类问题该先站在哪个框架上看”，更新 `frameworks/`
- 如果结果主要回答“在这次具体情境下该怎么做”，写进 `bridges/`
- 如果结果只是一次性答复，不写回
