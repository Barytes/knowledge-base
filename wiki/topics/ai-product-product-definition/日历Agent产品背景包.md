# 日历 + Agent 产品背景包

> 用途：为新项目中的 Codex 提供完整产品背景。本文保留想法的演进、核心信念、当前产品假设、PRD、关键体验、边界、验证方式和未决问题。不要把其中仍待验证的假设误写成已经确认的用户需求。

## 一、最初的产品直觉

最初的想法是做一个后台守护 Agent，实时感知用户日常工作流，并自动把可以自动化的部分搭建成 Agent。

这个表述容易被理解成更自动化的 workflow mining 或 Agent Builder：系统观察用户行为、发现重复流程、生成自动化候选，再让用户确认、部署和维护。

这不是用户真正想做的产品。

真正的愿景是：

> 给人一个自然完成工作的环境，把 Agent、workflow、工具调用和 context routing 隐藏在最后。用户只推进自己的工作，不需要学习、选择、调用或管理 Agent。

目标体验由三个词组成：

- `frictionless interaction`：用户不需要把工作意图重新翻译成 prompt、workflow 或 Agent 配置。
- `contextual intelligence`：系统持续理解当前事项、项目历史、相关人员、既有材料和最近变化，用户不必反复补充背景。
- `proactive intelligence`：系统在被明确调用前开始准备，并在合适时机把有用成果带回当前工作，而不是用更多通知打扰用户。

Agent 的隐藏指操作上隐藏，不是机制上不可检查。用户默认不管理 Agent，但在风险、异常、权限和重要判断处仍然能够查看依据、纠正理解和接管。

## 二、必须避免的错误理解

### 1. 不是自动替用户搭建 Agent 的 Agent Builder

如果用户仍要审核候选流程、决定是否自动化、配置权限、理解 Agent 状态和维护运行结果，那么 AI 元工作仍然存在，只是从亲手搭建变成审核系统搭建。

产品主语必须是人的工作、项目和成果，不是 Agent 或自动化。

### 2. 不是 Codex、Power Automate 或聊天助手的轻量包装

这些工具主要回答“怎样把一项工作交给 AI”。当前想法要回答的是“怎样让人的正常工作天然处于一个会理解、会预判、会执行的环境中”。

用户不应该先意识到需要 AI，再打开 AI 产品、选择 Agent、描述任务和等待结果。

### 3. 不是会议纪要产品

会议曾被用来说明这个范式：谈到事实问题时，系统自动查询；谈到具体想法时，系统生成 Demo。但会议只是工作事项的进行阶段，不是产品完整边界。

会议前的准备、会议中的实时辅助和会议后的继续推进，应属于同一项工作。

### 4. 不是抽象的“项目现场”

“项目现场”仍然过于抽象。Codex、Notion、Slack 等产品都可以声称自己是项目现场。产品必须回答：用户什么时候打开它、做什么自然动作、系统自动发生什么、眼前出现什么结果。

### 5. 不是浏览器产品

浏览器覆盖很多网页工具，但软件运行在浏览器中不等于工作本体发生在浏览行为中。表格建模、文档协作、客户管理和代码审查即使出现在网页里，也仍然属于各自专业工作。

浏览器可以成为承载方式，但不应成为产品定义。

### 6. 不是替代全部工作软件的大而全套件

知识工作分散在日历、文档、表格、邮箱、通讯、会议、IDE、设计工具和业务系统中。重新制作所有专业工具会稀释真正独特的产品命题。

产品要替代的不是这些软件，而是人长期承担的胶水劳动：恢复上下文、搬运信息、重新解释意图、在工具间推动下一步，并在 deadline 临近时从零开始。

## 三、知识工作的基本结构

不同职业使用的软件不同，但多数知识工作会经历类似循环：

```text
接收变化
→ 理解情况
→ 形成判断
→ 创造成果
→ 与他人对齐
→ 做出决定
→ 推动执行
→ 跟进结果
```

管理者和创始人的重心常在沟通、判断、协调与跟进；产品、研究和咨询人员更多在搜集、分析、讨论与形成方案；工程师和设计师长期停留在专业创作环境；销售和运营则围绕关系、承诺、业务系统与持续跟进展开。

因此，不存在一个对所有知识工作者都同样重要的单一执行界面。更稳定的共同结构是：工作会跨越多个表面，而人负责维持它们之间的连续性。

## 四、为什么最终选择日历 + 待办作为入口

日历与待办的核心优势不是信息量最大，而是它们面向未来。

浏览器知道用户已经开始做什么；文档知道用户正在写什么；通讯工具知道别人刚提出了什么。日历和待办则知道用户未来承诺要完成什么，以及什么时候需要结果。

日历提供时间结构、参与者和社会承诺；待办提供任务、交付物和 deadline。两者结合起来更接近一份未来工作的 Agenda。

核心判断是：

> 日历不是过去工作的记录，而是一份面向未来的承诺账本。

进一步说：

> 传统日历安排的是人什么时候开始工作；Agent 日历安排的是结果什么时候需要就绪，以及哪些部分可以在此前由系统持续完成。

因此，产品不只是 AI Calendar，而是一个以时间为坐标的人机委托协议。

## 五、两个最初洞察的精确版本

### 洞察一：日历能够理解用户的工作与生活轨迹

日历会暴露固定会议、周期职责、协作对象、项目阶段、出行、忙闲节奏和长期模式。

但要精确表述：日历知道的是用户声明、计划或承诺过的轨迹，不是完整真实生活。临时工作、线下思考、未记录活动、突发打断和计划变化仍然可能缺失。

所以它的价值不是天然拥有全部 context，而是为未来事项提供稳定的时间索引和意图锚点，使邮件、文档、会议、消息和历史成果可以围绕这个事项聚合。

### 洞察二：创建待办近似于指派任务，并给出 deadline

创建待办通常表达了目标和期限，有时还包含参与者、地点、附件和成果形式，因此天然接近一份 assignment brief。

但它仍然是一份初步委托，不是完整授权。标题可能模糊，也可能缺少成功标准、资料范围、风险边界和外部行动权限。

创建事项可以默认授权低风险准备，例如研究、整理、起草和试做；不应默认授权发送、发布、付款、审批和对外承诺。

## 六、最深层的产品洞察

传统日历调度的是人的时间。Agent 日历可以同时调度两类资源：

- 人的注意力，用于判断、创造、关系处理和承担责任；
- 机器劳动，用于搜索、整理、比较、起草、试做和持续跟进。

这改变了 deadline 的含义。

过去，deadline 是提醒人必须在此之前完成任务；在 Agent 日历里，它更像一个结果交接点：系统应在此之前把工作推进到适合人介入的位置。

产品真正优化的不是“按时提醒”，而是“用户接手时的工作准备度”。

核心体验是：

> 用户打开一项工作时，不再从零开始，而是直接面对已经准备好的材料、成果和需要自己判断的问题。

更长远地看，人不再只是把未来工作安排给未来的自己，而是把目标放进一个会在时间中持续工作的环境。

## 七、产品定义

工作名：`会自己生长的日历`、`Agent-native Agenda` 或 `日历 + Agent`。

一句话定义：

> 一个把未来承诺转化为持续推进工作的 Agenda。用户写下需要什么、什么时候需要；系统在此前完成可以代劳的部分，并在真正需要判断时把工作交还给用户。

它以日历和待办为入口。用户继续用熟悉的方式创建事项，每个事项随后成为一个持续演进的工作对象。

Agent、workflow、工具调用和执行过程默认退到后台。用户在前台看到的是任务目前准备到了哪里、已经形成什么成果、还缺什么信息、哪些部分需要自己决定。

日历负责表达未来意图、组织工作和展示准备度。文档、邮箱、会议、IDE、设计工具及其他专业软件继续承担正式创作和执行。

## 八、核心价值

用户负责表达未来要完成什么，系统负责在 deadline 前把可以代劳的部分逐渐准备好。

当事项轮到用户处理时，它不再是一条空提醒，而是已经进入判断、修改或确认阶段。

产品价值不主要体现在“帮用户管理时间”，而体现在三个变化：

1. 计划与执行不再完全割裂。任务一旦被创建，准备工作就开始发生。
2. AI 不再需要被显式调用。创建事项就是自然输入。
3. 用户把时间留给判断、创造和责任，而不是重复恢复背景与搬运信息。

## 九、产品主对象：会生长的 Work Item

日历中的事项不能继续只是标题和提醒。它应成为一个随工作推进而变化的工作对象。

用户打开后看到：

- 当前目标与 deadline；
- 系统对事项的理解；
- 相关背景、历史和参与者；
- 已准备的证据、草稿、方案或 Demo；
- 当前阻塞与依赖；
- 需要用户判断的问题；
- 被接受的结果和后续事项。

任务卡片的主内容是成果与判断面，不是 Agent 的聊天记录、运行步骤或工具调用。

## 十、完整工作生命周期

每个事项都有前、中、后三个阶段。

### 开始前：提前准备

系统恢复背景、聚合相关资料、发现缺口和依赖，形成研究、比较、草稿、方案或可丢弃 Demo。

### 进行中：理解变化并实时辅助

如果事项是一场会议，参与者继续自然谈话。出现事实问题时，系统准备带依据的答案；出现足够具体的想法时，系统形成方案、图表或 Demo；讨论改变方向时，已有成果随之修正。

### 结束后：把结果接续到未来

被接受的结论进入正式成果；未解决问题和后续承诺进入新的事项；新的判断更新相关项目，使下一次工作不再从零开始。

## 十一、核心产品功能

### Agenda 工作主页

以今天、本周和未来事项组织工作。它不是普通任务清单，而是展示哪些事项尚未准备、正在生长、已有成果、等待判断、存在阻塞或已经完成。

主页优先呈现真正需要用户注意的工作，不把所有后台活动转化为通知。

### 自然事项创建

用户像平时一样输入简短目标和 deadline，不需要选择 Agent、编写 prompt、配置 workflow 或填写复杂委托表。

系统尽量从已有背景补全理解，只在缺少关键目标、成果形式或权限时询问用户。

### 主动准备

根据事项类型，系统可以搜集并核对资料、恢复历史讨论、形成比较分析、起草文档与邮件、准备方案和 Demo、发现依赖与风险。

目标不是擅自完成全部工作，而是尽量把事项推进到需要人类判断的位置。

### 项目连续性

不同日程、待办、文档和讨论可以继承同一项目的背景、结论、失败尝试和用户判断。完成事项产生的新信息继续影响未来工作。

### 周期事项学习

周报、经营分析、客户回访、产品评审和季度规划等重复事项，能够逐渐复用被用户接受的结构和判断。用户不需要显式创建自动化，重复发生本身就是工作流形成过程。

### 跨事项理解

系统理解多项任务之间的共享资料、先后依赖、阻塞关系和容量冲突。它可以让一份研究服务多个事项，也可以识别某个未决判断正在阻塞后续工作。

### 自然反馈

用户通过修改任务、调整 deadline、编辑成果、采纳内容、延期、取消和创建后续事项来修正系统，不需要额外评分或训练 Agent。

### 计划与执行偏差学习

如果主要办公活动已经通过 AI、文档、IDE、会议和业务工具发生，系统可以把这些工作痕迹关联到同一个 `Work Item`，观察计划承诺与实际推进之间的偏差，并校准下一轮计划。日历提供事前的目标、时间窗口和 deadline；执行轨迹提供事后的状态变化、人工介入、返工、阻塞和成果。二者结合后，系统可以逐渐学到同类工作通常需要多少准备、在哪些阶段容易卡住、应该提前多久启动，以及什么时候需要为人的判断预留时间。

这里不能把“AI 运行了多久”直接当作“任务花了多久”。至少要区分机器主动执行时间、人的阅读与判断时间、等待外部依赖的时间，以及从创建到完成的自然流逝时间。统计单位也应是跨多次会话和工具的 `Work Item`，而不是单个聊天线程或 Agent run。

因此，这一能力更准确的闭环是：

```text
日历中的计划承诺
→ Work Item 的执行与状态事件
→ 计划值与实际结果的偏差
→ 更新同类任务的时间估计和启动时点
→ 建议调整后续 Agenda
→ 用户确认高影响的日历变更
```

它的价值不是生成更精确的工时报表，而是让计划逐渐接近真实工作：系统知道哪些任务总被低估、哪些等待可以与机器工作并行、哪些事项应当提前启动、缩小、延期或取消。

这仍是待验证假设。很多思考、线下沟通和临时工作不会留下完整数字轨迹，Agent 日志也可能把等待误算成执行。首版必须保留置信度、允许用户纠正任务归属，并避免把可见活动时长误写成生产率或绩效判断。

### 用户控制

用户可以查看成果依据、纠正系统理解、暂停主动准备、限制上下文范围、丢弃临时成果和接管事项。重要外部行动必须由用户明确决定。

## 十二、三个代表性场景

### 场景一：研究任务

用户周一创建“周五完成新能源汽车竞品分析”。系统在数日内逐渐准备资料、比较框架、信息冲突和分析草稿。周五用户打开任务时，直接进入判断与修改。

### 场景二：产品会议

日历中有“周四讨论新产品定价”。会议前，系统恢复历史讨论、更新市场信息并准备候选方案；会议中，事实问题触发证据，具体想法触发 Demo；会议后，结论进入方案，未决事项进入未来 Agenda。

### 场景三：周期性工作

用户每月需要准备投资人更新。第一次系统只能粗略起草，用户大量修改；后续月份逐渐复用有效结构、数据来源和表达边界。稳定部分自动发生，例外与判断保留给用户。

## 十三、为什么日历入口具有结构性优势

### 它能提前行动

系统在任务到期前拥有准备时间，而不是等用户开始后才响应。

### 时间表达优先级

事项占用时长、参与者、冲突、延期和 deadline，比静态优先级标签更接近用户真实注意力分配。

### 日历有自然生命周期

创建、开始前、进行中、结束后、延期、取消和完成，为系统提供了清楚的工作阶段和自然反馈。

### 周期事项天然暴露稳定工作流

重复事项让系统围绕同一目的学习，而不是仅从相似点击猜测流程。

### 时间能连接分散上下文

日程主题、参与者和项目时间点为邮件、文档、会议和历史成果提供共同索引。

### 参与者揭示社会结构

同一成果面向工程师、管理层、客户或设计团队，需要不同背景、表达和决策材料。日历提供了受众与协作关系。

### 它具有主动出现的正当性

用户已经接受日历在正确时间提醒。产品可以在事项开始前带回准备结果，在进行中提供辅助，在空档集中展示需要判断的内容。

### 它能观察任务组合

相比只看到当前页面的工具，Agenda 可以发现跨任务依赖、重复研究、阻塞决策和超出容量的承诺。

## 十四、Agent 隐藏的交互原则

Agent 隐藏不等于完全没有 UI。消失的主要是调用 Agent 的输入界面，而不是人判断成果的输出界面。

前台应围绕工作对象和结果，而不是围绕 Agent：

- 不要求用户选择 Agent；
- 不以聊天作为默认入口；
- 不展示 workflow editor；
- 不用运行日志占据主要界面；
- 不让用户持续审核每个后台步骤。

同时，成果需要能够被理解和检查：

- 什么已经准备好；
- 为什么这样理解；
- 依据来自哪里；
- 哪些内容仍不确定；
- 哪些行为需要授权；
- 用户如何接管。

核心原则是：

> 后台可以积极准备和试做，前台必须克制打扰；低风险成果可以主动出现，外部承诺仍需明确的人类决定。

## 十五、产品不是痛点驱动，而是原型驱动

用户没有体验过“创建待办后，工作会自己发生”，因此很难在访谈中直接表达这个需求。单纯进行痛点访谈，容易得到更好的提醒、排程、会议纪要或任务管理，而不是新的委托范式。

当前阶段更适合通过原型探索：如果用户创建普通待办后，事项在 deadline 前自行长出资料、草稿或 Demo，用户是否会形成新的使用行为？

原型的核心 magic moment 是：

> 我还没有正式开始，这项工作却已经推进到了需要我判断的位置。

原型驱动不等于只做一次炫酷生成。需要验证的是一个可重复循环：

```text
表达未来目标
→ 系统持续准备
→ 用户回来时工作已经推进
→ 用户判断和修正
→ 系统继续推进
```

## 十六、最重要的产品验证信号

真正的强信号不是用户说“这个功能很酷”，而是行为发生变化：

- 用户开始因为希望系统提前工作而主动创建更多事项；
- 用户把尚未成熟但希望推进的目标放进 Agenda；
- 用户反复回来查看事项准备到了哪里；
- 用户减少向 AI 重述背景；
- 用户实际采用、修改并继续使用系统准备的成果；
- 用户逐渐扩大系统可以自主准备的低风险范围；
- Agenda 成为用户每天查看工作准备状态的入口。

如果用户只是围观一次结果，之后仍然回到聊天框逐项下指令，那么只证明生成能力存在，没有证明新的产品关系成立。

## 十七、首批用户假设

日历入口不是对所有知识工作者同样有效。当前较强假设是：首批用户应当是日程密集、跨项目协调、工作具有明确交付时点且准备成本较高的人，例如创始人、产品经理、管理者、顾问、销售、客户成功和部分研究人员。

工程师、设计师和实验型研究人员可能长期停留在专业工作面中。日历对他们仍可作为意图入口，但未必适合成为主要判断界面。

这只是当前 ICP 假设，尚未被真实用户行为验证。

## 十八、首版事项范围

首版更适合处理有 deadline、可以形成数字成果、低风险准备占比较高的事项，例如：

- 资料研究和信息准备；
- 文档、方案和报告草稿；
- 产品想法与可丢弃 Demo；
- 会议前准备、会议中辅助和会议后延续；
- 周期性汇报、复盘与跟进。

不应一开始承诺处理所有生活与工作事项，也不应默认完成高风险外部行动。

## 十九、主要失败模式

### 把模糊标题当完整意图

“处理项目问题”可能不足以支持任何高价值行动。过度推断会制造噪音和信任损耗。

### 把主动性做成通知

后台每完成一步就提醒，会把节省下来的执行劳动重新变成审核劳动。

### 要求用户精细维护 Agenda

如果每项任务都要填写复杂目标、验收标准和权限，创建待办会退化成新的 prompt engineering。

### 把 Agent 隐藏成黑盒

用户看不到依据、风险与接管入口，会削弱信任和自主性。

### 过度读取私人生活

工作与生活节奏可以改善主动性判断，但可读取不等于应被无差别使用。隐私分区属于产品定义，而不是后置设置。

### 只优化任务关闭率

高价值知识工作可能需要改变问题、推翻计划或取消任务。更高效地完成错误目标不是价值。

### 退化成普通 AI 日历

如果产品主要提供排程、提醒、会议摘要或聊天问答，就没有验证“未来工作自行生长”的核心范式。

### 退化成全能工作平台

如果首版开始重做文档、邮箱、通讯、设计和项目管理，产品会失去聚焦，并把 Agent 的独特价值埋在传统软件功能中。

## 二十、日历与会议作为同一长期 Work Item 的双入口

最新产品假设不是在“日历 + Agent”和“会议 + Agent”之间二选一，也不是把二者做成两个并列产品。更准确的统一结构是：

> 日历负责声明未来承诺并创建长期 `Work Item`；会议转录负责把高密度事实、判断、决定和承诺持续写入这个 `Work Item`；后台 Agent 在两次人类活动之间继续推进工作。

```text
日程 / 待办：目标、参与者、deadline、提前工作的时间
                     ↓
              Persistent Work Item
                     ↑
会议转录：事实变化、方向修正、决定、承诺、即时反馈
                     ↓
        Long-running Agent Runtime
  wake / context refresh / execute / verify / checkpoint
                     ↓
       evidence / draft / demo / decision request
                     ↓
       用户采纳、修改、拒绝与正式授权
                     ↓
            Delegation Method Library
```

### 日历入口主要验证什么

日历提供的是 `ex ante intent`。它在工作开始前暴露目标、期限、参与者和准备窗口，因此最适合验证：用户是否愿意把创建事项当作初步委托；Agent 是否能跨小时或跨天保持任务状态；系统是否能在 deadline 前持续更新 context、分配预算并把工作推进到可判断状态；结果应该在什么时候重新出现才不会制造打扰。

日历的弱点是语义稀疏。一个标题通常不足以构成完整委托。因此首版不应让所有事项自动运行，也不应要求用户填写复杂表单。更稳的切法是从一类用户明确选择过的周期事项开始，例如客户会议、产品评审、经营复盘或固定汇报。系统可以对这一类事项默认做低风险准备，只在缺少关键目标或权限时询问。

日历入口的 magic moment 是：

> 事项还没开始，但工作已经推进到了需要我判断的位置。

### 会议入口主要验证什么

会议提供的是 `in situ context`。转录比日历标题拥有更高语义密度，可以暴露问题为什么重要、哪些想法只是探索、方向如何变化、谁做出了什么承诺，也能提供即时纠正。

会议入口最适合验证：系统能否从自然对话中区分事实缺口、可物化想法、正式决定和随口讨论；能否在不要求 prompt 的情况下触发搜索、分析或可丢弃试做；用户能否用继续说话、否定、修改和采纳自然 steering 后台工作；会议结束后，已确认决定能否转化为持续 assignment，而不是只生成摘要和 action items。

它的主要风险是退化成会议纪要产品。真正的产品边界不应是“会议开始到会议结束”，而应是工作对象的完整生命周期。会议只是一次高带宽校准点：它可以创建、更新、暂停或改变后台工作，但工作应在会议结束后继续，并在下一次 deadline 或会议前形成新的成果。

会议入口的 magic moment 是：

> 我们只是在正常讨论，关键问题却已经开始变成证据、方案或可操作作品；会散以后，工作没有停。

### 最强首个切口：周期会议的完整生命周期

如果必须选择一个同时验证两种入口和底层长期能力的切口，当前更强的候选不是通用日历，也不是通用会议助手，而是一类高价值周期会议。

日历事件提前创建 `Work Item`，后台 Agent 在会前恢复背景并准备材料；会议转录在进行中更新事实、方向和承诺；会后被确认的决定变成持续 assignment；Agent 在两次会议之间继续研究、起草、试做和跟进；下一次会议开始前，用户看到的是已经推进的成果、阻塞和待判断问题。

这条路径同时提供时间、上下文、反馈和重复 episode。它比纯日历更容易获得真实语义，比纯会议更能证明长时间自主运行，也天然产生同类任务的多轮样本。

产品可以先在一个具体 ICP 中选择一种周期会议。若优先验证体验，可以从产品评审、研究讨论等容易产生证据与 Demo 的会议开始；若优先验证企业付费，可以进一步收缩到客户成功、销售或经营管理中准备成本高、数据来源明确、结果具有经济价值的会议。

### 长期后台运行是能力核心，委托方法库是语义资产

长期自主后台运行能力是这个产品成立的必要底座。它至少需要承载：持久 `Work Item`、事件触发与定时唤醒、跨 session 状态、context refresh、budget、checkpoint、steering、取消、失败恢复、artifact、独立验证和人工门禁。

但通用的 agent loop、session 和 sandbox 会逐渐成为平台能力，因此它们单独未必构成长期壁垒。更值得积累的是 runtime 围绕真实工作形成的语义资产：什么事件构成委托，什么上下文是权威的，哪些动作可自主执行，什么叫准备完成，什么时候必须询问，结果应该写回哪里。

这可以逐渐形成 `Delegation Method Library`。它不是一开始设计出的通用 schema，也不是从转录中直接抽取的 prompt 模板，而应按下面的路径晋升：

```text
真实 episode
→ 保存 context、动作、artifact、用户修改与最终结果
→ 发现同类任务中的稳定结构
→ 形成候选 delegation method
→ 在后续 episode 中验证
→ 才晋升为可复用方法
```

一个成熟方法最终应包含适用条件、目标与 ready condition、context resolver、工具与权限、checkpoint 策略、artifact 类型、evaluator、人工接管和 writeback。模型特定 prompt 应由这些结构在运行时生成，而不是成为知识库本体。

尤其要避免从“会议里说过什么”直接推断稳定方法。真正有资格进入委托库的信号，应主要来自用户实际采纳、修改、拒绝、授权和最终业务结果。这样积累的不是一堆自动化猜测，而是经过结果修正的组织工作方法。

## 二十一、在 AI 产业链中的位置：从委托编译层收缩到 Delegation System of Record

“少写 prompt”不是一个可以独占的产业层，而是整条技术栈共同产生的体验结果。模型会提高意图理解，Harness 会提供 memory、sandbox、checkpoint 和长任务恢复，办公套件会掌握邮件、日历、会议、文件、权限与默认分发，用户也会逐渐学会更清楚地委托。任何一家只把价值定义成“替用户少写几句话”的公司，都会把自己的差异化交给上游进步消解。

2026 年的公开产品已经把这个风险变得很具体。OpenAI 的模型指导称，模型已经能更好地推断用户目标，不必逐步规定过程，但领域上下文、硬约束、授权边界和成功标准仍需保留。与此同时，OpenAI Agents SDK 正把可配置 memory、sandbox orchestration、snapshot 和 rehydration 做成通用能力。更大的威胁来自办公平台：Microsoft Work IQ 已把邮件、日历、会议、文件、组织关系、personal memory、skills、权限和长期 workspace 组合成 Agent 基础层；ZoomMate 也把会议上下文持续转成文档、表格、项目计划和业务系统更新；Google Gemini Spark 则直接定位为接入 Workspace 的 `24/7` Agent。

这意味着，`context compiler + long-running runtime + meeting-to-deliverable` 仍是必要能力，但已经不足以定义一家独立公司。更稳的产品位置必须再向具体业务结果收缩：

```text
日历 / 会议 / 邮件                     现有工作入口与信号源
             ↓
某个业务职能的 Delegation System of Record   公司必须掌握的对象
  commitment / authority / evidence / state / artifact / outcome
             ↓
可替换的模型、Harness、办公平台 API          能力供应商
             ↓
CRM / 工单 / 文档 / 财务等 system of record   执行与结果写回
             ↑
用户决定、修改、采纳与最终业务结果            学习闭环
```

这里的核心对象不是 transcript、prompt 或 Agent session，而是长期 `Work Item` 及其事件账本。它需要持续回答：组织究竟承诺了什么，谁授权了哪些动作，当前依据是什么，哪些成果被采纳，最终产生了什么业务结果，以及这次 episode 是否足以改变下一次的委托方法。模型拥有推理，Harness 拥有通用执行，办公平台拥有原始工作数据；产品要拥有的是某类业务承诺从产生到兑现的完整生命周期。

### Work Item 是必要的事实角色，不是天然护城河

“长期 `Work Item` 及其事件账本是核心”需要分成三个层次理解。作为系统中的逻辑角色，它很难消失：长程任务总要有一个比单次模型调用更持久、可恢复、可审计的事实源。但它不一定需要成为独立数据库，也不一定必须由本产品物理保存。Microsoft Work IQ、CRM、项目系统或更广义的 context platform 都可能把这项能力包含进去。若某个 memory 系统能够保存原始事件、版本、来源、权限、授权和副作用，并支持 replay，它实际上已经在内部实现了事件账本，而不是让这个职能消失。

需要保持的是语义分层：

| 层 | 回答的问题 | 类比 |
|---|---|---|
| 模型权重 | 一般情况下会做什么、怎样推理 | 通用解释器与先验 |
| `Skill` | 某类工作通常应该怎样做 | 程序、SOP、方法 |
| `Work Item` | 这一次具体要完成什么、现在到哪里 | 运行中的任务实例 |
| 事件账本 | 用户和系统实际上做过什么、授权过什么 | transaction log / event sourcing |
| Memory | 从过去事件中提炼出哪些稳定事实与经验 | 缓存、索引、派生知识 |
| Context | 这一轮模型当前应该看到什么 | 当前工作集与 materialized view |

因此，`Work Item` 不是 `Skill`。Skill 是可复用的“怎样做”，Work Item 是一次具体的“正在做什么”，事件账本是“实际上发生了什么”。同一个“准备客户复盘”Skill 可以服务几十个客户的 Work Item；每个 Work Item 都拥有不同的事实、参与者、授权、进度和结果。

它们之间更准确的关系是：

```text
事件账本 → materialize 当前 Work Item 状态 → Context Engine → 模型
                              ↑                    ↓
                         Skill / policy        动作与成果
                              ↑                    ↓
                    结果与用户修正 ← 新事件写回账本
                              ↓
                     更新 memory、eval 与 skill
```

模型可以逐渐内化通用方法、领域常识和一部分 Skill，也可以更好地根据上下文推断下一步。但每个任务中不断变化的事实、最新承诺、权限、外部副作用和业务结果不适合进入模型权重：它们更新太快、属于特定组织、需要删除与权限控制，也需要被人审计和纠正。即使未来模型拥有可写的持久内部状态，只要企业要求 provenance、版本、权限、撤销和 replay，这个内部状态也会在功能上重新变成外部可治理的事实层。

所以，事件账本是长程系统的必要底座，却不是公司单独的护城河。更准确的可积累核心是：`canonical delegation state + outcome-labeled episodes + skill/eval 演化 + 工作流嵌入`。账本提供可信经历，Skill 把重复结构变成可执行方法，结果反馈决定方法是否真的变好。任何一项单独拿出来，都可能被平台商品化。

产品也不必复制所有上游数据。更合理的做法是让 CRM、日历、文档等继续保存各自的权威事实，本产品只保存跨系统的委托引用、授权、状态转换、成果、人工决定与结果关联。它要争取拥有的不是全部 memory，而是“这项委托为什么存在、现在能做什么、做到了哪里、最后是否兑现”的 canonical semantics。如果这部分也由办公平台完整拥有，那么本产品就会退化成运行在平台上的一个垂直 Skill；这是一种可能的产品形态，但不再是独立的 `Delegation System of Record`。

### 真正的侵蚀边界

模型训练会吞掉模型特定措辞、步骤分解和一部分工具选择。Harness 会吞掉 session、sandbox、重试、checkpoint 和通用长期运行。办公平台会吞掉通用 context、组织权限、会议摘要、日程操作和横向 Agent。用户培训会吞掉“因为用户不会描述需求”而产生的产品价值。

这些变化不会自动吞掉组织特定的成功标准、授权记录、例外处理、跨系统承诺和结果反馈。但办公平台也有能力继续向这些位置扩张。因此，只做横向的“委托控制层”仍然偏危险。它更可能成为平台标准，而不是天然形成一家公司的市场。

### 独立公司的成立条件

更可行的路径是先纵向穿透一个部门结果，再把委托编译层作为内部引擎。产品要连接的不只是日历和会议，还要连接该职能的权威数据与结果系统；不只是生成成果，还要知道成果是否被采纳，以及最终结果是否改善；不只是辅助一次任务，还要成为周期会议中默认查看和推进工作的对象。

例如从客户成功或销售的周期账户会议切入，日历只负责提前创建账户 `Work Item`，会议负责更新风险、决定和承诺，后台 Agent 从 CRM、支持工单和产品使用数据中持续准备材料并推进已确认事项，结果写回 CRM 与客户文档，下一次会议再检验续约风险、问题关闭和方案采纳。此时公司卖的不是“无 prompt 会议助手”，而是“客户承诺如何被持续推进并兑现”。即使 Zoom 或 Microsoft 提供更强的通用 Agent，它们仍然只是可利用的输入、执行与分发能力。

这条路径需要同时满足四个条件：在一个有预算的业务职能里拥有明确结果；让长期 `Work Item` 成为用户反复返回的主对象；从执行、采纳和最终结果获得闭环反馈；保持模型与 Harness 可替换，并能跨多个工作套件工作。跨平台本身不是壁垒，真正的壁垒是跨平台之后形成的业务语义、授权历史、评测集和经过结果校准的组织委托方法。

### 委托方法库应该怎样理解

通用的 `Delegation Method` schema 很可能会成为公开标准，不能把它本身当作护城河。真正有价值的是某个业务和组织中经过真实结果修正的方法实例：什么时候适用，哪些数据权威，什么动作允许自动执行，什么叫 ready，用户通常改哪里，哪些例外必须升级，以及使用后业务结果如何。

因此，方法库在早期应该是产品的内部学习资产，而不是先卖一个横向 Agent Builder。更合理的演进是：先用垂直应用获得完整 episode；再把稳定结构沉淀为内部委托引擎；只有当多种工作面反复请求同一能力时，才把它开放成 API 或平台。顺序应是“垂直产品 → 内部平台 → 可嵌入能力”，而不是先造横向平台等待场景。

### 对长程 Agent 的押注：正向凸性，不是必然获益

这个产品确实在押注长程 Agent 会成为主要能力形态，但“产品必然随之获益”需要附加条件。更准确的表述是：产品应当对长程 Agent 能力具有正向凸性。Agent 越能长期、自主、低成本地推进工作，系统能够覆盖的 `Work Item` 越多，每项工作可自主完成的比例越高，用户监督和错误修复成本越低，产品价值会加速上升。

可以粗略写成：

```text
产品可实现价值
≈ 可覆盖的 Work Item 数量
× 每项工作的自主推进比例
× 单项业务价值
− 用户监督成本
− 错误与失控成本
```

长程 Agent 的进步会同时扩大前面两项，并压低后面两项。但价值能否被公司获得，取决于产品究竟拥有哪一层。如果主要价值是替今天较弱的模型拼接 session、补 prompt、重试和恢复，那么 Agent 与 Harness 变强会直接删除这部分差异化；这是一层会被进步消灭的补偿。如果产品拥有长期 `Work Item`、业务委托契约、授权记录、结果评测和用户反馈，底层 Agent 变强就意味着同一个工作对象可以被推进得更远、更久、更便宜；这是被进步放大的互补资产。

因此，早期脚手架应该被设计成可替换、可删除的实现，而不能成为产品身份。一个很实用的架构检查是：每次模型或通用 Harness 升级后，系统是否可以删除一部分补偿代码，同时增加自主推进的范围。如果升级反而摧毁产品价值，说明公司拥有的是旧模型的 failure pattern；如果升级降低成本并扩大可交付范围，说明公司拥有的是稳定业务对象。

这里的“长程”也不应理解为同一个模型进程连续思考数天。更可能的成熟形态是：`Work Item` 长期存在，Agent 按事件和时间被反复唤醒，每次读取最新状态，执行一段工作，留下 checkpoint 和 artifact，再等待新的信息、权限或 deadline。底层执行可以由许多短 session、不同模型甚至不同 Harness 完成。真正长寿的是委托状态和责任链，不是某次推理调用。

所以产品不必等“真正长程 Agent”出现后才能成立。当前可以用持久 `Work Item`、短程执行、定时唤醒和人工 checkpoint 先实现连续性；随着底层能力成熟，再逐步延长无人监督区间。它真正押注的不是某个未来 Agent 产品形态，而是智能供给会持续改善，并且越来越多长期工作可以被接入一个稳定的委托与结果系统。

### 一个最严厉的长期测试

可以假设未来模型聪明十倍、通用 Harness 接近免费、用户都学会了高质量委托。如果产品的价值随之归零，它只是过渡期补偿层。如果届时客户仍需要一个地方保存承诺、授权、证据、成果、例外与结果，并让同类工作越做越符合本组织的方法，它才占住了长期位置。

所以，这个方向在产业链中的准确定位不是新的模型公司、通用 Harness、AI 日历或会议 Agent，而是：

> 以日历和会议为分发与感知入口，以模型和 Harness 为可替换供应商，以业务系统为执行与结果来源，成为某类高价值周期工作的 `Delegation System of Record`。

## 二十二、当前仍未决定的问题

以下内容不应被新项目中的 Codex 擅自锁死：

1. 最终产品更接近独立 Agenda、现有日历的增强层，还是跨表面的工作入口。
2. 日历与待办在产品中如何组合，哪些事项只影响注意力，哪些事项应成为主动 Work Item。
3. 首批用户究竟应当是创始人、产品团队、管理者、顾问、销售还是研究人员。
4. 首个 magic moment 应优先验证研究准备、会议实时辅助、成果草稿，还是周期工作自动生长。
5. 系统在什么情况下可以直接开始准备，什么时候必须先询问。
6. 成果应该主要出现在日历事项中，还是回到原有文档和专业工作面。
7. 用户如何理解“准备度”，以及怎样避免 Agenda 变成新的项目管理负担。
8. 如何区分真实目标、探索性想法、私人事项和不应采取行动的提醒。
9. 产品应覆盖个人工作与生活，还是先严格聚焦工作场景。
10. 哪些自然行为足以支持系统学习稳定工作流，哪些仍需要用户明确纠正。

这些问题适合通过高保真原型和真实使用逐步发现，不应仅靠抽象讨论一次性决定。

## 二十三、新项目 Codex 的协作要求

1. 先保真理解这个产品直觉，不要立即把它压成已有类别、竞品或常规效率工具。
2. 不要把产品重新解释为 Agent Builder、workflow mining、会议纪要、聊天助手、浏览器侧栏或通用项目空间。
3. 讨论产品时始终把人的工作和成果放在前台，把 Agent 视为后台能力。
4. 不要过早要求技术选型、架构方案或完整字段设计。先保持产品体验和待验证命题清楚。
5. 提出收缩方案时，要说明它验证了哪条核心假设，不能为了容易实现而丢掉 magic moment。
6. 区分已确认信念、当前假设和开放问题，不要把推测写成确定需求。
7. 可以挑战想法，但要指出具体风险、触发条件和对核心体验的影响，不能只用“太通用”“市场已有”“做不了”结束讨论。
8. 用户希望的是原型驱动探索。早期任务是做出足以改变用户行为参照的体验，而不是先证明一个传统痛点市场。
9. 保留用户最终判断权。Agent 隐藏不意味着不可解释、不可接管或无限授权。
10. 衡量产品时优先看行为变化，而不是功能数量、Agent 数量或一次性生成质量。

## 二十四、给 Codex 的最短背景摘要

如果上下文窗口有限，可以只提供下面这段：

> 我们正在探索一个“会自己生长的日历”。它不是 AI 排程工具、会议纪要、Agent Builder 或聊天助手。用户像平时一样创建日程和待办，这个动作被系统理解为一份带目标与 deadline 的初步委托。日历负责创建长期 `Work Item`，会议转录等事件持续更新事实、方向、决定与承诺；后台 Agent 在事项开始前、会议进行中和两次人类活动之间持续恢复上下文、研究、整理、起草和试做。用户不需要选择 Agent、写 prompt 或搭 workflow，前台只看到工作准备度、已形成成果、风险和需要自己判断的部分。创建待办和会议中提到想法都不等于授权正式发送、发布或承诺，低风险准备可以主动发生，外部行动仍需明确确认。核心 magic moment 是：用户回来时发现自己还没有正式开始，工作已经推进到了需要判断的位置，而且一次会议结束后工作仍在继续。模型、通用 Harness 与办公平台都视为可替换供应能力；若要形成独立公司，必须从一个有预算的业务职能纵向切入，拥有承诺、授权、证据、成果与结果的长期事件账本，逐步成为该类周期工作的 `Delegation System of Record`。当前阶段是原型驱动探索，最重要的验证信号是用户是否开始把创建事项和自然讨论当成委托与 steering，并反复依赖这种持续推进。
