# 持续委派中间层：日历与 Agent 之间缺失的责任层

## 来源

- [ChatGPT 分享：持续委派中间层](https://chatgpt.com/share/6a618220-3a28-83ee-a9b8-b62e64c07576)

## 核心理解

“日历 + Agent”之间的中间层，不是把日历事件转发给 Agent 的连接器，也不只是保存更多个人信息的 Context Engine。

它承担的是一项工作跨越时间、工具和多次执行时的持续责任：

> 日历记录用户作出的未来承诺，Agent 提供某一步的执行能力，中间层负责把承诺转化为长期任务，维护上下文、状态、时间线、权限和下一步，并持续持有它直到完成。

最简洁的表达是：

> 日历捕捉承诺，Agent 提供劳动力，中间层持有责任。

## 为什么现有日历和 Agent 之间确实缺一层

日历知道未来什么时候发生什么，但它通常不负责把事项推进到完成。Agent 能够搜索、写作、编码和调用工具，但它通常只在收到请求后执行一轮。

现实任务却不是一轮请求，而是一段时间中的连续过程：

```text
承诺产生
→ 准备材料
→ 补齐信息
→ 事件发生
→ 形成结论
→ 推动后续
→ 确认真正完成
```

目前用户仍然负责在这些阶段之间重新想起任务、恢复背景、调用 Agent、检查结果、决定下一步和追踪关闭。因此，即使单次 Agent 执行已经很强，委派本身仍然没有持续成立。

中间层要转移的不是某一个动作，而是四种责任：

- 时间责任：什么时候应该开始准备、更新、检查和交付；
- 状态责任：现在做到哪里、阻塞在哪里、下一步是什么；
- 上下文保管责任：完成任务需要的材料、决策、口径和历史由谁持续维护；
- 完成责任：什么条件代表任务真正结束，是否仍有未关闭的后续。

用户价值因此不只是“AI 提前做了一点”，而是：

> 这件事已经被系统持有，我不再需要持续记住应该如何推进它。

## 核心产品对象不是日历事件，而是持续委派对象

日历事件只描述一个时间点，聊天线程只记录一段交互，文件只承载某个材料。它们都不足以表达一项长期工作的完整状态。

中间层需要拥有一个比它们更稳定的对象，可称为 `Delegation Object`、持续任务空间或委派任务包。

这个对象回答：

- 任务为什么产生，预期结果是什么；
- deadline、关键节点和参与者是谁；
- 已经使用过哪些材料，当前有效口径是什么；
- 做过哪些尝试和决定，哪些方案已经被否决；
- 当前处于什么阶段，有什么阻塞；
- 下一步应调用什么能力；
- 哪些操作可以自动完成，哪些需要用户批准；
- 什么条件代表可以关闭。

Agent 可以更换，日历和工作软件也可以迁移，但这个对象必须保持连续。它才是产品真正积累的资产。

## 中间层的本质不是存储，而是状态驱动的责任编排

如果中间层只是复制文件、保存聊天和定时运行 prompt，它仍然只是数据仓库加自动化。

真正的持续委派要求系统根据剩余时间、当前进度、材料完整性、外部变化、上一步结果、风险和审批状态，判断下一步应该发生什么。

这和固定自动化的差别是：

```text
普通自动化：条件满足 → 执行预设动作

持续委派：读取当前任务状态
        → 判断此刻最需要解决的问题
        → 选择合适 Agent 或工具
        → 检查结果是否推进任务
        → 更新状态并决定下一步
```

时间只是判断输入之一。真正驱动系统的是任务是否正在向完成条件前进。

## 中间层在产品生态中的位置

```text
日历 / 邮件 / 会议 / 项目系统
          ↓ 产生承诺
持续委派中间层
  - 长期任务对象
  - 上下文与状态
  - 时间线与下一步
  - 权限与人类介入
  - 完成判断
          ↓ 调度执行
Codex / ChatGPT / Claude / 专业 Agent
          ↓ 读写成果
文档 / 邮箱 / GitHub / Notion / CRM 等现有工作系统
```

因此，它不需要重新做日历、通用 Agent 和所有工作软件。它拥有的是这些系统之间缺失的长期任务连续性。

日历是最好的首个承诺入口，但不是长期产品边界。未来委派也可能来自邮件承诺、会议决定、Slack 任务、文档行动项和项目 milestone。更稳定的产品边界是“以时间为骨架的持续委派系统”。

## 如果面向公共使用：时间模块与 Agent 协议

如果这套能力要供不同用户和不同 Agent 使用，可以把它实现成一个独立的时间协调模块，但“时间”只是共同坐标，不是完整语义。模块不能只回答几点启动哪个 Agent，还必须知道这项工作为什么存在、做到哪里、何时需要人介入，以及怎样才算完成。更准确的技术定位是 `temporal delegation layer`，而不是通用定时器或 Agent 路由器。

它可以采用 `core + adapters` 的结构：

```text
日历 / 待办 / 邮件承诺 / 项目 milestone
                    ↓
       Temporal Delegation Core
  Work Item / deadline / state / dependency
  human window / permission / ready condition
  execution event / estimate / outcome
                    ↓
          Agent Adapter Contract
                    ↓
 Codex / Claude / ChatGPT / 专业 Agent / workflow
```

核心层拥有稳定的 `Work Item` 和事件语义。不同 Agent 不需要暴露内部推理，只需要能够接收任务包，并回传 `accepted`、`started`、`progressed`、`blocked`、`needs_judgment`、`delivered`、`completed` 或 `failed` 等状态事件，以及预计就绪时间、成果引用和权限请求。日历、任务系统和业务软件继续保存各自的权威数据；中间层只保存跨系统的委托状态、时间约束、授权、结果和计划偏差。

对用户而言，前台不应变成“选择和管理多个 Agent”。用户仍然面对事项、成果、风险和时间承诺；选择执行者、切换 Agent、重试与接力属于后台适配。只有当不同 Agent 的能力、成本、数据边界或权限会改变用户决定时，才需要显式展示。

如果直接把它做成“所有 Agent 都可以接入的平台”，会同时遭遇两侧冷启动：没有真实任务就无法证明时间协调价值，没有 Agent 接入又无法形成任务闭环。更稳的路线是先保留窄协议，但用一个日历、一类周期任务和两种执行器完成端到端产品。只有当同一个 `Work Item` 能在更换 Agent、调整 deadline 和跨多次执行后仍然保持状态，并且计划估计确实变准，公共模块才有被抽出来的依据。

因此，公共化的顺序应是：

```text
先做一个用户愿意反复使用的时间协调产品
→ 从真实 Work Item 中稳定事件与适配接口
→ 开放 Agent adapter
→ 再开放通用 temporal delegation protocol
```

这保留了“可以接各个 Agent”的长期方向，同时避免先做一个没有用户结果、只能展示连接数量的横向平台。

## 产品形态不是唯一的：先固定语义核心

“Web Agenda + Coordination Service + Local Connector”只是适合公共 SaaS 的一种部署拓扑，不是产品必然形态。此前把 `Coordination Service` 写成“核心”并不准确。真正稳定的核心是一项可恢复的时间委派职能：

- `Work Item` 在单次 Agent run 结束后仍然存在；
- 状态、deadline、依赖、权限、成果和完成条件有权威记录；
- 系统能够在未来被唤醒，继续推进或请求人类判断；
- 重试、Agent 切换和设备变化不会让责任链丢失；
- 计划与实际结果可以形成下一轮估计。

这组语义可以运行在本地进程、云服务、混合架构或现有平台内部。后台服务只有在需要设备关闭后继续运行、跨设备同步、多用户协作和集中集成时，才成为自然选择。

### 部署拓扑的主要选择

| 形态 | 实现方式 | 优点 | 代价与限制 | 更适合 |
|---|---|---|---|---|
| 本地桌面应用 / daemon | 状态库、定时器、Agent adapter 和 UI 都在用户设备 | 隐私强；直接访问本地文件、IDE 和 Codex；离线可用；V0 最简单 | 设备休眠后无法推进；跨设备和团队协作弱；分发与升级需要客户端 | 个人用户、本地 Agent、概念验证 |
| 云端 SaaS / control plane | 云端保存 Work Item、运行定时器并调用云 Agent | 24/7；跨设备；多用户；日历和业务系统集成集中 | 敏感数据与凭证风险更高；需要运维；本地执行仍要 connector | 团队、云端 Agent、持续在线任务 |
| 本地优先 + 云端协调 | 本地保存敏感内容并执行，云端只保存时间、状态和最小任务元数据 | 兼顾本地能力与跨设备、后台唤醒；长期产品形态较完整 | 一致性、离线合并、权限和调试最复杂；不适合最早验证 | 已证明需求后的公共产品 |
| 嵌入式 SDK / 插件 | 模块运行在现有日历、项目工具或 Agent runtime 内 | 用户不必迁移；容易利用宿主的身份、数据和分发 | 被宿主 API、权限与界面限制；难以拥有跨平台权威状态 | 作为第二分发形态或平台合作 |
| 自托管服务 | 用户或企业自行部署协调服务 | 数据控制与可定制性强；适合合规场景 | 安装、升级、监控和支持成本高；版本容易碎片化 | 技术团队与企业客户 |

### 状态与调度层也有不同实现

| 运行时实现 | 优点 | 代价 | 适用阶段 |
|---|---|---|---|
| `SQLite/Postgres + worker + timer` | 容易理解和调试；开发快；没有重型基础设施 | 重试、幂等、补偿和长等待语义需要自己维护 | V0 与小规模 Beta |
| 事件日志 + 状态机 | 每次变化可审计、replay 和重新物化；适合计划偏差学习与多 Agent 接力 | 事件 schema 演化、重复事件和投影视图增加复杂度 | 产品已证明需要可靠历史之后 |
| Durable workflow engine | 原生支持长计时器、重试、暂停、人工介入和失败恢复 | 学习、部署和迁移成本高；容易过早让基础设施主导产品 | 长任务量和可靠性要求已经明确时 |
| Actor / 每任务进程模型 | 每个 Work Item 独立持有状态，隔离和并发关系自然 | 分布式生命周期、持久化和观测更难 | 大量并发且任务相互独立时 |
| Serverless 事件函数 | 空闲成本低，外部事件接入方便，弹性好 | 长等待、顺序一致性、本地 Agent 和端到端调试较别扭 | 无状态触发器和外围 adapter，不宜先承担全部核心 |

### 当前更小的技术建议

若目标是先验证自己的真实工作，最小版本不需要独立后台服务。可以做成一个本地常驻应用：

```text
本地 daemon
  ├─ SQLite：Work Item、事件、估时与结果
  ├─ timer worker：到点唤醒与状态检查
  ├─ calendar adapter
  ├─ 一个 Agent adapter
  └─ 本地 Web UI 或桌面窗口
```

这版允许“电脑休眠时不工作”，因为首要问题是验证任务是否真的被持续持有、执行记录是否能校准计划，而不是先证明云端高可用。数据模型最好保留 append-only event 和窄接口，例如 `create / wake / update / request_judgment / complete`，但不必一开始引入完整 event sourcing 或 durable workflow 平台。

如果本地闭环成立，再根据真实缺口演进：用户需要跨设备和关机后继续运行，就把时间与状态控制面迁到云端；需要团队协作，就增加多租户和权限；需要其他产品接入，再开放 adapter 或 SDK。这样技术形态由已出现的约束推动，而不是由“以后可能给所有人用”提前决定。

## 它如何修正此前“会自己生长的日历”定义

此前的核心体验是：用户创建待办后，事项在 deadline 前自动长出资料、草稿或 Demo；用户回来时，工作已经推进到需要判断的位置。

持续委派中间层把这件事解释得更完整。

“自己生长”不是不断生成内容，而是系统在长期持有一项责任：

- 知道为什么要生成这些内容；
- 保存实际使用过的证据和用户修正；
- 发现当前步骤没有推进任务时重新规划；
- 在会议发生后继续追踪结论和行动；
- 不因更换 Agent、移动文件或关闭聊天而丢失任务；
- 直到完成条件满足才结束。

因此，日历只是让委派尽早发生的自然入口。产品真正拥有的是“从承诺到完成”的连续责任。

## 与 Agent 隐藏式产品愿景的一致之处

这套中间层与 Agent 隐藏式工作平台高度一致：

- 用户仍然通过创建日程、作出承诺和推进工作表达意图；
- Agent 是可替换的执行者，不成为前台主语；
- 用户面对的是任务状态、成果、风险和需要判断的问题；
- 系统负责上下文组织、Agent 调度和多阶段跟进；
- 正式成果回到原有工作系统，不强迫用户迁移到封闭套件。

它还补上了此前定义中的一个空缺：只说“后台主动准备”还不够，必须明确谁在一次准备结束后继续负责。持续委派中间层就是这个责任主体。

## 与原愿景之间仍存在的张力

分享内容中的第一版建议包含“委派给 Agent”开关、任务详情空间、执行记录、权限设置和大量状态字段。这对冷启动、信任和调试有意义，但也可能重新制造用户管理 AI 的元工作。

长期体验仍应坚持：创建承诺是主要动作，系统默认推断和准备，只在高影响歧义、关键判断和权限边界处询问。用户需要看得见并能接管，但不应被迫经营一个复杂的委派后台。

另一个风险是把“持续委派基础设施”先做成过大的平台。这个概念很容易诱导团队先建设通用状态机、连接器、权限系统和 Agent 调度，再寻找用户价值。更符合当前原型驱动方向的顺序是：先证明一种现实任务可以让用户产生“它已经被持续持有”的感觉，再抽象中间层。

## 最重要的验证变化

此前较强的验证信号是：用户是否开始把创建待办当成委托行为。

中间层思路又增加了一条更深的信号：

> 用户是否真的不再需要记住、重新解释和催促这件事如何继续。

一次优质 brief 或 Demo 只能证明单次 Agent 能力。持续委派成立，需要用户经历整个闭环后感到：

- 系统没有在一次输出后失去责任；
- 新信息出现时，任务状态会继续更新；
- 事件结束后，后续行动没有重新掉回自己脑中；
- 更换执行 Agent 不会导致任务失忆；
- 系统知道什么时候应该问自己，什么时候可以继续推进；
- 最终能够解释为什么任务已经完成或仍未完成。

## 当前产品判断

“持续委派中间层”比“Agent 日历”更准确地定义了长期产品边界，也比“项目现场”更具体。它明确产品不拥有所有工作软件，也不依赖某一个 Agent，而是拥有任务跨越时间和执行者时的连续性。

但面向用户时，不宜把“中间层”或“基础设施”作为主要价值表达。用户真正感知的承诺仍然应该是：

> 把事情放进日历之后，系统会一直替你持有和推进，直到真正完成；你只在需要判断和承担责任时回来。

对第一版而言，最重要的不是证明中间层包含多少组件，而是证明一项具体任务能够完成以下闭环：

```text
创建承诺
→ 轻量确认委派
→ 自动聚合并保管任务上下文
→ 在合适时间调用现有 Agent 准备成果
→ 根据结果和变化继续推进
→ 只在关键节点请求用户介入
→ 追踪后续直到关闭
```

只要这个闭环没有成立，产品仍然只是日历触发的 Agent 自动化；闭环成立后，中间层才具有独立产品价值。
