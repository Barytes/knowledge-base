# AI 知识系统的产品定义信念

## 摘要

`llm-wiki` 和 `context-infrastructure` 的共同点，不在于它们都用了 markdown、schema 或 agent，而在于它们都把“从原始数据里提取高价值信息，并把这些信息变成可持续复利的中间层”当成核心任务。

两者都拒绝把 LLM 只当作一次性问答器。它们都希望让 LLM 持续处理原始材料，提炼出更高密度、更可复用的信息结构，再把这些结构沉淀为未来提问、推理与协作的基础设施。

但两者面对的数据分布、失败模式、优化目标和架构设计并不相同：

- `llm-wiki` 处理的往往是更结构化、更清晰表达、噪音更少的外部知识材料。
- `context-infrastructure` 处理的则是更杂乱、更时序化、噪音更高的个人生活与工作痕迹。

正因为原始数据和核心问题不同，它们才长出了不同的信息提取层次和不同的 agent workflow。

## 共同本质：把信息提取变成复利过程

如果只看表面，`llm-wiki` 像知识库，`context-infrastructure` 像 prompt + memory + workflow 系统。

但从更底层看，它们在做的是同一类事情：

- 从原始数据中提取高价值信号
- 把信号写入更高密度的中间层
- 让中间层在后续任务里反复复用
- 随时间积累，把一次提炼变成多次收益

所以它们可以被看成两种不同的“知识蒸馏机”。

区别不在于是否蒸馏，而在于：

- 蒸馏的对象是什么
- 要滤掉什么噪音
- 最终想保留什么信号

## 原始数据分布不同

### `llm-wiki` 的原始材料

`llm-wiki` 更接近一套面向外部知识的编译系统。

它的典型输入包括：

- 论文
- 文章
- 报告
- 书籍章节
- 团队文档

这些材料虽然也会有偏差、冲突和质量差异，但通常具备几个特点：

- 表达意图相对清晰
- 主题边界相对明确
- 结构相对稳定
- 单条材料本身已经是高信号密度文本

所以它面对的主要问题不是“信号太少”，而是“信号太分散，难以持续综合”。

### `context-infrastructure` 的原始材料

`context-infrastructure` 更接近一套面向个人判断与工作风格的蒸馏系统。

它的典型输入更像是：

- 聊天记录
- 录音与会议纪要
- 邮件
- 日常工作痕迹
- 碎片化观察

这些材料的特点则接近：

- 时间上连续积累
- 单条记录的信息密度不稳定
- 噪音很多
- 表达常常不完整
- 有价值信号往往埋在大量琐碎表述里

所以它面对的主要问题不是“知识分散”，而是“如何从高噪音流里筛出稳定、少量、但极有辨识度的个人信号”。

## 两者共同想解决什么

你的一个核心判断是准确的：两者都希望把原始数据里的有用信息抽出来，沉淀成未来可复用的资产，而不是每次从原始数据重新开始。

这意味着它们都反对一种默认模式：

- 用户每次提问
- 系统每次临时去 raw data 里抓相关片段
- LLM 每次重新拼装理解
- 问题结束后几乎没有留下持久增益

它们想做的恰恰相反：

- 原始材料先被逐步处理
- 关键结构被提前写出来
- 未来任务站在这些结构之上
- 每次摄取与每次查询都能让系统变得更强一点

这就是它们的复利逻辑。

## `llm-wiki` 的产品定义信念

### 核心目标

`llm-wiki` 的目标，是为 LLM 建立一个知识中间层，让它在面对大范围、多来源、长时间跨度的信息时，不必每次都从原始材料重新综合。

它要解决的核心不是“LLM 不会回答”，而是：

1. 上下文窗口有限，无法直接承载大面积知识。
2. 传统 RAG 每次临时检索，无法把理解真正积累下来。
3. 人类不想把大量时间花在维护 wiki、补链接、改摘要、做结构整理上。

所以它的产品定义信念可以写成：

> 知识管理真正稀缺的，不是存储原始材料，而是把分散知识持续编译成一个可导航、可维护、会复利的中间层，让用户把注意力放在提问、分析和方向上。

### 它最在乎的结果

在这个定义下，`llm-wiki` 更看重的是：

- 能否扩大 LLM 的有效工作上下文，而不只是增加 token 数量
- 能否让复杂综合不必每次从零开始
- 能否让知识库在长时间上持续维护，而不是再次荒废
- 能否把知识维护负担转移给 LLM

Karpathy 这类高信息摄入者的真实痛点，很可能不是“没有信息”，而是“信息太多，来不及维护结构，更无法把所有零散阅读稳定编译成一个长期可查询的体系”。

### 为什么它只有较少层次

你说 `llm-wiki` “只有两层（raw 和 wiki）”，这个方向是对的，但更精确地说，它其实是：

- raw sources
- wiki
- schema

只是其中真正承载信息提取的核心层，确实主要是 `wiki` 这一层。

这是因为它面对的原始材料通常已经比较“可直接总结”了。
对这类数据来说，很多时候不需要经过 observation -> pattern -> axiom 这种多级去噪，LLM 可以直接把材料编译进主题页、实体页、概念页和比较页。

换句话说，`llm-wiki` 不是不需要抽象层，而是原始信号已经足够清晰，所以中间提炼层可以更薄。

### 它与传统 RAG 的差别

你说它“不是依赖向量相关性的固定算法，而是交给 LLM 利用 agentic 能力自己探索”，这个判断基本成立，但最好稍微收紧。

更准确地说：

- `llm-wiki` 并不是在否定检索本身
- 它是在把主要价值从“即时检索”转向“提前编译后的结构化中间层”
- 未来查询仍然可能需要返回 wiki 或 raw
- 但系统不再完全依赖一次性的相似度召回来组织知识

所以它更像是在说：

> 不要把知识组织工作全部推迟到 query time，而要尽量在 ingest time 和 maintenance time 先做掉。

如果一定要借 “bitter lesson” 做类比，也只能说它更偏向“让通用 agent 在文件系统上自己探索”，而不是把知识访问强绑定到一套固定检索算法；但这个类比不是核心，点到为止更稳妥。

## `context-infrastructure` 的产品定义信念

### 核心目标

`context-infrastructure` 的目标，不只是让 agent 知道更多，而是让 agent 越来越像某个人。

它真正想解决的核心问题包括：

1. 大量个人生活与工作痕迹里，真正有价值的个人信号极少，却混在大量噪音里。
2. 一次性 prompt 注入无法长期稳定地保留个人偏好、风格与判断方式。
3. 如果不做渐进蒸馏，agent 输出会越来越平、越来越共识化，逐渐失去个人味道与边界感。

所以它的产品定义信念可以写成：

> 个人 AI 系统真正稀缺的，不是更多外部知识，而是把长期生活和工作痕迹中那些少量但稳定的反共识信号蒸馏出来，变成 agent 可继承的判断与行为基础设施。

### 它最在乎的结果

在这个定义下，`context-infrastructure` 更看重的是：

- agent 是否越来越贴近用户本人
- 能否持续蒸馏出偏好、风格、品味、判断倾向
- 系统能否抵抗噪音污染
- 日常痕迹能否逐步升级成更稳定的 observation、pattern、axiom、skill 或规则

它最关心的不是通用知识覆盖率，而是高辨识度的个体化控制面。

### 为什么它需要更多层

你说它有四层 `raw -> observation -> pattern -> axiom`，这个理解抓住了核心，即它需要多级信息提炼来反复滤噪。

如果再更准确一点，可以把它理解成两种层次同时存在：

- 信息蒸馏层次：raw -> observation -> pattern -> axiom
- 运行控制层次：rules / memory / skills / periodic jobs

也就是说，`context-infrastructure` 不只是“更深的知识抽象树”，它同时还是一个控制 agent 行为的 operational harness。

之所以要有 observation、pattern、axiom 这样的多层抽取，是因为原始数据噪音太大，不能从一两条记录直接升级成高置信度规则。

这一点和 `llm-wiki` 的区别非常大：

- `llm-wiki` 更像“把清晰知识编译成可导航页面”
- `context-infrastructure` 更像“把高噪音痕迹逐层蒸馏成稳定人格与判断信号”

### 关于“高维数据处在低维流形上”的联想

这个联想是有启发性的，但更适合作为类比，而不是字面上的系统定义。

可以保守地说：

- `context-infrastructure` 的确隐含一个假设：大量表面上杂乱的行为痕迹背后，存在较少但稳定的个人特征和判断模式。
- 这些模式不会在单次记录里完整出现，而是需要跨时间累计后才能显现。

这和“高维观测由更少潜在结构生成”的直觉是相通的。
但如果直接把它说成严格的“低维流形”假设，就有点过工程隐喻化了。

更稳妥的写法是：

> 它假设高噪音个人记录背后存在较少但稳定的潜在偏好与判断结构，而系统的作用就是把这些潜在结构逐步提纯出来。

### 关于“online learning”的联想

这个联想也基本是对的，但同样更适合做启发式类比，而不是严格等同。

准确之处在于：

- 数据是按时间不断到来的
- 系统是增量更新的，而不是一次性离线训练
- 新观察会改变系统之后的行为
- 强信号会逐步被晋升为更稳定的规则

所以把它看成一种“面向个人上下文的在线增量蒸馏流程”，是有帮助的。

但它和标准机器学习里的 online learning 仍然不同，因为：

- 它不是在优化一个明确数值损失函数
- 它的更新单位不是参数梯度，而是文本规则、技能、观察和工作流
- 更新过程包含大量人为定义的语义判断

所以更好的表述是：

> 它在系统行为上接近一种在线增量学习，但实现上更像一个持续进行的语义蒸馏与规则升级流程。

## 两者在工作流上的差异

### `llm-wiki` 更需要 agentic 探索

你的一个重要判断是：`llm-wiki` 更依赖 agentic 能力来回到 wiki 或 raw 中补足信息。

这基本成立。

原因是它的中间层虽然已经很有用，但它的目标不是把所有细节都压缩掉，而是保留一个高密度入口，让 agent 之后可以沿着结构继续探索。

因此它的典型工作流更像：

- 先看 wiki
- 沿页面链接走
- 有需要时回 raw 验证
- 在查询中继续组合和扩展

也就是说，wiki 不一定是终点，更像高质量起点。

### `context-infrastructure` 更偏向线性蒸馏闭环

你说它“似乎基本不需要向下追溯到原始数据”，这个判断有一半对，一半要收紧。

对的部分在于：

- 一旦 observation、pattern、axiom 足够成熟，很多任务确实不必回 raw
- 它追求的正是把可复用的人格与判断信号提前提纯出来

需要收紧的部分在于：

- 它仍然需要周期性回到原始生活痕迹里继续抽取新信号
- 如果高层规则和当前行为出现偏差，也需要重新看原始证据

所以更准确的说法是：

> `context-infrastructure` 希望尽量减少日常任务中对 raw 的依赖，但为了持续蒸馏与纠偏，它仍然必须周期性返回原始痕迹。

从 workflow 看，它确实比 `llm-wiki` 更接近一个线性的“观察 -> 反思 -> 晋升”闭环，但这并不意味着它不需要 agentic 能力。

它依然需要 agentic 能力来：

- 扫描复杂工作区
- 判断哪些痕迹值得提炼
- 决定应该升级到哪一层
- 在不同 rules、skills、memory 之间做路由

所以更准确的结论是：

- `llm-wiki` 更强调开放式知识探索
- `context-infrastructure` 更强调受控的渐进蒸馏

两者都需要 agentic 能力，只是 agentic 的用途不同。

## 为什么会长出不同架构

这正是你大纲里最有洞见的一点。

两者架构不同，不只是风格差异，而是被不同问题和不同数据分布倒逼出来的。

### `llm-wiki`

它面对的是：

- 高信号但分散的知识材料
- 需要跨来源、跨时间做综合
- 用户希望少做维护，多做分析

所以它最自然长成：

- raw source
- maintained wiki
- schema-guided ingest/query/lint

其核心任务是“把知识编译进可导航中间层”。

### `context-infrastructure`

它面对的是：

- 高噪音、时间流式到来的个人痕迹
- 需要从琐碎记录中找出少量稳定的人格与判断信号
- 用户希望 agent 越来越像自己，而不是只知道更多事实

所以它最自然长成：

- raw traces
- observation
- pattern
- axiom
- 再加 rules、skills、memory、periodic jobs 组成控制平面

其核心任务是“把个体信号从噪音中多轮蒸馏出来，并稳定注入 agent 行为”。

## 更完整的综合判断

如果把两者放到同一张图里，可以这样理解：

- `llm-wiki` 是“世界知识的复利系统”
- `context-infrastructure` 是“个人判断的复利系统”

前者主要解决：

- 有太多知识，但无法长期综合和维护

后者主要解决：

- 有太多生活痕迹，但无法从中稳定提炼出自己真正独特的部分

所以它们的共同母题是：

> 不要把 LLM 用在每次重新理解世界，而要把它用在持续提炼、沉淀和放大那些以后还会反复有用的信息结构。
