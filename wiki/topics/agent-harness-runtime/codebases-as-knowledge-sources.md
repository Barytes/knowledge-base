# 代码库作为知识来源

## 简短回答

代码库应该被纳入知识库，但通常不应该以“整仓库直接变成 wiki”的方式纳入。

更好的做法是把代码库视为一种高价值原始证据源，再把其中可复用的工程实践提炼成维护过的知识页与桥接页。

## 为什么代码库重要

和文章或博客相比，代码库有两个独特价值：

- 它暴露了工程实践在真实约束下到底是如何落地的。
- 它能区分“作者宣称的做法”和“系统真正执行的做法”。

如果你想理解像 harness engineering 这样的实践，代码库往往比理念文章更接近真实机制。

## 但不要天真摄取

直接把整个代码仓库都当成 wiki 内容，通常会带来三个问题：

- 变动太快，维护成本会失控。
- 实现细节太多，会淹没真正可迁移的模式。
- 你会把项目特定约束误当成通用原则。

所以代码库更适合当证据层，而不适合直接变成维护层。

## 推荐分类方式

### 第三方仓库

如果你研究的是别人的仓库，它最接近 `raw/external/` 的角色。

知识库真正关心的不是把整个仓库复制进来，而是保存：

- 仓库地址与观察时间
- 关键 commit 或 release
- 相关文件路径
- 少量必要摘录或结构说明

### 自己的仓库

如果你研究的是自己的仓库，它通常属于 mixed evidence。

- 代码与配置里可观察的机制，仍然可以抽成世界层面的工程知识。
- 你反复采用的取舍方式，才应该逐步沉淀到 `wiki/self/`。
- “这个项目该如何借鉴这些实践” 这类结论，更适合写进相关 `wiki/topics/` 页面。

## 该从仓库里提炼什么

当你想理解工程实践时，不要按“文件类型”平均阅读，而应该按“控制机制”抽样。

对于 harness engineering，优先看这些证据面：

- 任务入口：`AGENTS.md`、system prompts、skill definitions、planner configs
- 状态外化：progress files、task specs、structured plans、scratchpads
- 协调机制：worker orchestration、queues、state machines、mailboxes、branching rules
- 验证机制：tests、evals、judges、review bots、sandbox rules、permission gates
- 失败恢复：retries、resets、rollback scripts、checkpoints
- 环境约束：CI、linters、repo rules、directory contracts
- 演化痕迹：PR、commit、issue、ADR、postmortem

这比“从头到尾读源码”更像是在阅读一套制度。

## 最佳写回形状

我建议把代码库实践写回成三类页面，而不是一种。

### 1. 仓库笔记页

记录某个仓库里到底存在什么机制。

适合放在相关 `wiki/topics/` 目录，偏描述性。

推荐结构：

- 这个仓库要解决什么问题
- 它用了哪些关键机制
- 这些机制分别在防什么失败模式
- 哪些部分明显依赖项目上下文

### 2. 实践主题页

把多个仓库里反复出现的机制提炼成主题知识页。

例如 `Harness Engineering` 这类页面，重点不是某个函数怎么写，而是：

- 常见控制层有哪些
- 每一层在补偿什么能力缺口
- 哪些设计是通用模式
- 哪些 tradeoff 最常见

### 3. 桥接分析页

把“某个仓库里的实践”翻译成“对你当前项目意味着什么”。

这类页面适合放在相关 `wiki/topics/` 目录，因为它混合了：

- 代码库里的客观机制
- 你当前项目的目标与约束
- 你的取舍偏好

## 一套好的提炼流程

### 第一步：冻结观察范围

先限定仓库、版本和问题，不要泛泛地说“研究这个 repo”。

例如：

- 看 `2026-03` 到 `2026-04` 的 harness 相关变更
- 只研究权限门控与验证闭环
- 只看 coding agent，不看产品功能层

### 第二步：建立机制清单

不要先总结价值观，先列机制清单。

每条机制至少回答四个问题：

- 它控制什么
- 它防什么失败
- 它依赖什么前提
- 它的代价是什么

### 第三步：把机制和原则分开

例如：

- “使用 JSON task spec” 是机制
- “不要让执行者同时定义完成标准” 是原则

知识库应尽量把这两层分开保存。

### 第四步：跨仓库或跨时间比较

真正有价值的实践通常来自比较，而不是单点摘录。

可比维度包括：

- 同一仓库在不同时期的变化
- 两个仓库如何分别解决同一失败模式
- 同一机制在模型能力提升前后的增删变化

### 第五步：写出可迁移结论

最后写回时，重点不应该是“这个 repo 里有这些文件”，而应该是：

- 什么问题值得加 harness
- 哪类机制适合什么规模
- 什么是暂时补丁，什么是更稳定的约束
- 哪些做法对你的项目值得试，哪些只是别人的负担

## 对本仓库的实际建议

如果你以后想系统研究某个代码仓库的工程实践，我建议在这个知识库里这样落：

- 仓库事实和机制观察 -> `wiki/topics/`
- 你反复偏好的工程取舍 -> `wiki/self/`
- “基于这个仓库，我该怎么设计自己的系统” -> `wiki/topics/`

原始 repo 本身不必完整拷入，只要保留能支撑结论的证据面、路径、版本与少量关键摘录就够了。

## 一句话规则

把代码库当作“可执行制度的证据库”，而不是“需要全文转写进 wiki 的内容库”。

## 双 Skill 工作流

如果要把这件事自动化，最自然的拆法就是两个 skill。

### 1. `repo-map-ingest`

负责第一次阅读 repo，并产出一张稳定的仓库地图。

它的职责是：

- 先把 GitHub 或本地 repo 的最小原始证据保存到 `raw/external/`
- 自动生成 `wiki/topics/` 下的 repo map 初稿
- 自动刷新 `wiki/index.md` 与 `wiki/log.md`
- 冻结研究范围
- 建立 architecture map
- 记录机制清单
- 留下 evidence anchors

### 2. `repo-practice-query`

负责带着具体问题回到 repo，只补读必要证据。

它的职责是：

- 从 repo map 起步
- 命中相关锚点
- 提炼 portable practice
- 写回 `wiki/topics/`

这个拆法比“一个大 skill 同时做全仓理解和按需取证”更稳，因为第一次广度工作和后续定向深挖，本来就不是同一种任务。
