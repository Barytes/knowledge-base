# 课题组公共研究知识库的产品化与评测策略

## 摘要

本页是 `oh-share-it` 的产品化与评测支撑页。主入口见 [oh-share-it 公共知识库产品](oh-share-it公共知识库产品.md)。

如果把当前这套 `raw -> wiki` 架构直接理解成“一个能回答问题的知识库”，它的价值会被低估，也会很快在产品定义上卡住。对课题组研究场景来说，更准确的理解是：

它首先不是问答系统，而是一个把未来会反复进入研究判断的信号，提前提炼成公共可路由工作面的系统。

这样一来，产品化后的核心任务就不再只是“答得准不准”，而是：

- 能否让学生更快获得领域入口与多视角起点
- 能否让导师更快识别张力、空白与不值得做的方向
- 能否把组会、试错、负知识和研究判断持续沉淀成跨成员、跨时间可复用的资产

这也解释了为什么这个场景很难直接照搬通用 QA 的 test set、准确率和幻觉率。因为课题组真正关心的，往往不是单跳事实问答，而是方向判断、研究筛选、视角编排、失败经验传承和下一步行动建议。这些任务的好坏，不能只靠“是否命中标准答案”来衡量。

## 一、这份讲义对当前 `raw -> wiki` 架构意味着什么

### 1. 当前架构方向是对的，但产品定义还应该再往前走一步

从仓库已有页面看，当前架构已经抓住了一个关键点：

- `raw/` 保留不可变证据
- `wiki/` 承担维护过的中间层
- 查询不是唯一工作面，摄取和维护同样重要

这和 `llm-wiki` 式的“知识编译”方向是一致的。

但如果要把它变成课题组公共产品，仅仅有 `raw -> wiki` 还不够，因为课题组的高价值任务并不只有“把文献总结出来”。它至少同时服务两类工作：

- 面向学生的基础理解获取
- 面向导师的研究判断

前者更接近知识编译，后者更接近判断蒸馏。

所以产品化之后，`wiki` 不该只是一个单一层，而应被理解成至少两类公共工作面：

- `基础工作面`
  领域入口、方法谱系、标准比较、经典 tradeoff、必要背景
- `判断工作面`
  哪些方向值得看、哪些假设常常无效、哪些失败模式反复出现、什么问题值得先证明或先实验

这意味着你现在的 `raw -> wiki` 架构，本质上应该从“知识编译系统”升级成“知识编译 + 研究判断蒸馏”的双生产线。

### 2. 不要把“问答”当主产品，要把“可路由工作面”当主产品

这份 context intelligence 讲义最重要的启发是：

真正要设计的不是检索链路，而是未来工作默认站在哪一层上发生。

放在课题组场景里，这句话可以改写成：

> 你的系统不该只在有人提问时回答，而应该在多数研究任务开始前，就把最常用的领域入口、多视角材料和研究判断提到可路由工作面上。

如果新成员每次还要从论文堆重新判断一个领域的主线，或者导师每次还要靠记忆回想“这个结构以前为什么不值得做”，那说明系统虽然存了很多材料，但公共可路由工作面还没有真正形成。

所以，公共产品化后的目标，不应该优先定义成：

- “让任何人都能问问题”

而应该更像：

- “让课题组里最常反复发生的研究判断，不必每次从原始材料重新来一遍”

### 3. `raw -> wiki` 之后，还需要加入“判断沉淀回路”

你现在的 MVP 描述里有一句很重要：

> 在问答中产生并沉淀新的判断。

这其实已经超出了普通知识库，而更像一个 research memory system。

如果把这句话认真落地，系统工作流就不该只有：

- ingest raw
- 编译 wiki
- 回答问题

而应该变成：

- ingest 原始论文、笔记、组会记录、实验记录
- 维护公共入口层 wiki
- 在查询和讨论中产生新的 gap、tradeoff、反共识和失败模式
- 把其中高价值部分回写成判断层页面
- 让之后的新问题先站在这些判断层上继续工作

也就是说，真正开始复利的，不只是“知识越来越多”，而是“研究判断越来越可调用”。

### 4. 公共产品化后，最需要新增的是边界，而不是功能

如果面向课题组所有人，系统反而更需要分层和边界。至少有三种边界会变重要。

第一，`证据边界`

- 论文、报告、公开资料
- 组会记录、内部讨论、实验日志
- 失败尝试、尚不成熟猜想

这些材料都可以进系统，但可信度、公开范围和可回写方式不应一样。

第二，`受众边界`

- 面向新成员的 onboarding 页面
- 面向课题推进者的项目上下文
- 面向导师的方向判断与 screening 页面

第三，`置信度边界`

- 已经形成组内稳定判断的内容
- 只是某次讨论里出现的观察
- 明确需要复核的 speculative insight

如果没有这些边界，公共产品会很快把“已知”“猜想”“个人意见”“负知识”混在一起，最后既不可信，也不好用。

## 二、你现在这份产品定义，强在哪里，缺口又在哪里

### 强的地方

你现在的产品定义已经抓到了真正高价值的问题，不是“资料太多不好存”，而是：

- 很难从已有工作里快速判断什么值得做
- 组内高价值判断传播带宽太低
- 研究过程中的资产不能复利
- 入口层和判断层缺少共同工作面

这几个问题比“做一个文献问答系统”强很多，因为它们更接近研究组织真正的效率瓶颈。

尤其是第四条很重要。你已经明确看见：

- 学生更需要入口和多视角
- 导师更需要张力、空白和反共识

这说明你已经意识到，产品不是面对一个同质用户群，而是在服务两种不同的认知任务。

### 还缺的一步

当前定义还差一个再收紧的动作：

你还没有明确，MVP 第一阶段最优先服务的是哪一种高频任务。

现在的描述同时想覆盖：

- 文献整理
- 问答
- 经验沉淀
- 研究判断
- 代际传承

这些都对，但如果 MVP 全一起抓，系统很容易变成一个“什么都应该支持”的大容器。

更稳的做法是，把第一阶段定义成一个更窄的主任务。例如：

- 方向一：`Research Onboarding Surface`
  让学生快速获得某方向的入口、多视角和阅读起点
- 方向二：`Conjecture Screening Surface`
  让导师和高年级学生更快判断某个方向/问题值不值得深入
- 方向三：`Project Memory Surface`
  让每个课题的试错、组会判断和阶段性结论不再流失

这三者最终都应存在，但 MVP 最好只选一个作为主北极星，其他能力先做配套。

## 三、为什么这个场景很难做传统 QA test set

你的直觉是对的。因为这个系统最重要的任务，并不是“有标准答案的问题回答得对不对”。

困难主要有四个原因。

### 1. 用户问题空间事先不可枚举

研究问题不是客服 FAQ。用户到底会问什么，不仅开放，而且会随着项目阶段、研究方向、用户资历而变化。

### 2. 好答案往往不是单一事实

研究场景里，很多高价值回答本身就是：

- 一个有依据的比较
- 一个有边界的判断
- 一个对 tradeoff 的解释
- 一个下一步该怎么推进的建议

它们不等于某个可精确匹配的字符串答案。

### 3. 用户真正要的常常不是答案，而是“更好的下一步”

比如导师问一个问题，未必是在要最终结论，而是在找：

- 哪条线索值得继续
- 哪类机制先别做
- 应该先补哪块背景
- 当前卡点更像理论问题还是实验问题

这类输出更像 decision support，而不是 fact lookup。

### 4. 研究判断天然带有时间性和开放性

一个今天“合理”的判断，未来可能被新证据推翻。系统的重要能力不只是“说对”，还包括：

- 表明依据
- 显示置信度
- 区分已知和猜想
- 支持后续修正

所以如果只用“准确率/幻觉率”来定义成功，会错过最重要的产品价值。

## 四、那应该怎么评测

更合适的做法，不是追求一个统一 test set，而是按任务族设计评测。

### 任务族 1：基础理解获取

代表问题：

- 这个方向的经典问题设定是什么
- 常见方法路线怎么分
- A 和 B 方法的关键 tradeoff 是什么

这类任务可以较接近传统 QA，但重点不只是答对，还包括：

- 是否引用到了正确来源
- 是否覆盖了关键比较维度
- 是否遗漏明显已知内容

### 任务族 2：研究筛选

代表问题：

- 这个方向还有哪些值得做的空白
- 某个想法为什么可能不值得继续
- 这个问题更应该先证明还是先实验

这类任务不适合单一标准答案，评测更适合看：

- 是否给出可追溯依据
- 是否明确区分已知与推断
- 是否提出了真正可行动的下一步
- 导师或高年级成员是否认为“这帮助了判断”

### 任务族 3：项目记忆与传承

代表问题：

- 这个项目之前试过什么，为什么没继续
- 某类失败模式在组内是否反复出现
- 新成员能否在更短时间内接上已有上下文

这类评测可以不以问答为中心，而看：

- 重复解释次数是否下降
- onboarding 时间是否缩短
- 组会里“重新回忆上下文”的时间是否减少

### 任务族 4：沉淀质量

因为你的系统有“问答后回写”的目标，所以还要单独评测沉淀层。

看的是：

- 回写内容是否真的有复用价值
- 是否和原证据建立了清楚关联
- 是否把已知、判断、猜想混在一起
- 后续查询是否真的开始优先调用这些中间层

这部分其实很关键。很多系统会“记住很多东西”，但未来没人用，等于没有形成复利。

## 五、你可以怎么写第一版 OKR

如果你现在写不出 OKR，通常不是因为你不会写，而是因为产品目标还放得太大。对这个项目，更稳的是先写“工作面形成”的 OKR，而不是“万能问答”的 OKR。

下面是一版更适合 MVP 的写法。

### Objective 1

让课题组成员能更快获得某一研究方向的入口层理解与多视角理解，而不必从原始论文堆重新开始。

可选 Key Results：

- 针对 1 到 2 个具体研究方向，建立可维护的基础工作面，覆盖问题设定、方法脉络、关键比较与经典 tradeoff。
- 选取 10 个由学生高频提出的“入门型问题”，其中大多数问题的回答都能定位到明确来源，并被导师或高年级学生评为“足以作为起点”。
- 新成员在进入一个方向时，达到“能继续提更具体问题”的时间明显缩短。

### Objective 2

让组内已有的研究判断、失败经验和阶段性结论不再主要依赖口头传播。

可选 Key Results：

- 对 3 到 5 个在研项目，形成项目记忆页，记录关键判断、试错、失败原因和下一步分流。
- 对历史组会或讨论中反复出现的高价值判断，提炼出一批可复用的判断页或 bridge 页。
- 在后续问答或项目推进中，这些沉淀内容能被实际再次引用，而不是只被归档。

### Objective 3

让系统在“研究判断支持”上可用，但不伪装成确定性裁判。

可选 Key Results：

- 系统生成的方向判断类回答，能够显式区分“已知”“来自组内经验的判断”“当前推断与不确定点”。
- 在一组真实研究讨论样本中，多数回答都能给出被认为有帮助的下一步行动建议。
- 对明显超出证据边界的问题，系统能够保守回答或明确暴露不确定性，而不是自信编造。

## 六、第一版评测不要追求“标准答案”，而要追求“代表性工作样本”

你现在最适合做的，不是造一个大而全的 benchmark，而是先做一个小型 `evaluation portfolio`。

可以由三部分组成：

### 1. 高频真实问题样本

直接从过去组会、学生聊天、导师常问问题里抽一批问题。

不要求覆盖全部，只要求覆盖最常见的任务类型。

### 2. 关键场景任务单

不要只写“问题”，还要写“用户当时其实想完成什么任务”。

比如：

- 新成员进入新方向，想快速建立背景
- 导师判断一个点子值不值得继续
- 学生卡在方法选择上，想知道常见 failure mode

因为同一句问题，在不同任务背景下，好答案标准不同。

### 3. 小规模专家打分

让导师或高年级学生按几个维度打分，而不是只判对错。比如：

- 有无明显事实错误
- 依据是否清楚
- 是否区分了已知与推断
- 是否给出有效下一步
- 是否比手动翻材料更省时间

这类评测不如标准 QA 干净，但更接近你产品真正想解决的问题。

## 七、一个更适合你的最小评测闭环

如果想现在就开始，我会建议你先用下面这套最小闭环：

1. 选一个具体方向，而不是整个课题组所有方向。
2. 只服务两类任务：`新成员建立基础理解` 和 `导师/高年级做初步方向筛选`。
3. 收集 15 到 20 个真实问题，不追求标准答案，只给出参考依据和理想回答特征。
4. 对每个回答只看五件事：
   - 有没有依据
   - 有没有明显幻觉
   - 有没有混淆已知与判断
   - 有没有给出下一步
   - 用户是否觉得省了时间
5. 把高价值回答回写成页面，再观察后续是否真的被再次调用。

这样做的好处是，你评测的不是“系统像不像一个百科问答机”，而是“它有没有开始形成课题组的可路由工作面”。

## 一句话收束

对课题组公共知识库来说，`raw -> wiki` 不是终点，它只是第一条生产线。

如果要变成真正的公共产品，这套系统还需要长出第二条生产线：把组内研究中反复出现的高价值判断、失败经验与方向筛选规则，也逐步提炼成可共享、可引用、可修正的公共工作面。

而这也决定了，第一版 OKR 和评测不应围绕“万能问答准确率”展开，而应围绕：

- 是否更快获得基础理解
- 是否更好支持判断
- 是否真的沉淀并复用了研究经验
