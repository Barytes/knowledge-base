文字全双工 Agent 的最小 MVP

先校准：前一版其实主要是 steer

如果系统只是允许用户在 Agent 运行中加入新指令、取消当前片段并继续，这主要是 mid-flight steering。它可以是全双工系统的一部分，但本身不足以构成新的全双工产品体验。

steer 是一种操作：修改当前 run 的方向。全双工是交互拓扑：用户交互流和 Agent 工作流同时保持开放，而且可以相对独立地推进。用户输入不只可能是改方向，也可能是补充 context、回答 Agent 的问题、询问当前依据，或者提出不应打断主工作的旁路问题。

修正后的验证猜想

当 Agent 正在执行一项持续一分钟以上的工作时，如果用户可以继续和它交流，而 Agent 又能在没有必要时保持主工作继续，用户是否会从“等待结果后纠错”转向“和一个持续工作的对象共同推进任务”？

这个 MVP 仍不验证语音、多人协作、长期记忆或复杂多 Agent。它验证的是：对话继续时，工作也继续 是否带来不同于 steer 的价值。

精髓不是什么

输入框在模型输出时仍可打字，不等于全双工。新消息如果只是排队到当前回复结束，系统仍是普通多轮聊天；每次输入都停止并从头重跑，只是可打断；每次输入都被解释为修改当前 run，则只是 steer。

最小但有效的文字全双工必须做到：用户事件流和 Agent 工作流并行存在；runtime 能区分哪些消息需要 steer，哪些只需补充 context 或回答；主工作不因每次交流自动停止；只有真正改变当前步骤的输入才取消或重算相关工作。

最小场景：Live Memo

只做一个场景：用户给出几页杂乱笔记，让 Agent 在一到三分钟内形成一页产品 memo、研究摘要或方案草稿。

界面只有三个部分：正在演化的文档、始终可用的对话输入、极简工作状态。Agent 工作时，用户既可以说“不要写成聊天机器人”来 steer，也可以问“你为什么先写验证指标”，或补充“这里还有一份背景材料”。系统应该分别处理：steer 会改变相关步骤；问题由前台对话回答，但主工作继续；新增 context 被登记到后续步骤，不必取消当前不相关工作。

MVP 只支持四类消息：改变当前方向的 steer、供后续使用的 context、用户对 Agent 问题的 answer、不应中断主工作的 query，以及显式的“暂停、继续、结束”。不支持多个主任务，也不执行邮件、付款或数据库写入。

最小 runtime

系统维护一份共享任务状态，但运行两个循环：前台 conversation loop 持续接收、分类和回应用户消息；后台 work loop 持续推进文档。两者通过当前文档、有效约束、待处理事件、未决问题和版本号协作。

后台 work loop 不进行一次很长的阻塞式生成，而是按小片段循环工作：读取最新状态，完成一次有限修改，提交一个新版本，再进入下一片段。每个片段控制在约三到八秒。

用户事件到达时，conversation loop 立即写入事件队列并给出回执。query 可以根据当前 snapshot 单独回答，work loop 继续；context 加入后续可见状态，只有确实影响当前片段时才重算；answer 解除相应未决问题；只有 steer 默认使受影响的未提交片段失效。已经提交的版本始终保留。

每个工作片段携带自己的 intent_version。提交前若发现版本已过期，结果被丢弃；否则生成新 revision。事件生效后记录 event_id -> applied_revision，问题回答则记录 event_id -> response_id。

文本 MVP 不强制使用 WebSocket。前端用 POST /events 提交消息，用 SSE 同时接收对话和文档事件已经足够。最小实现可以复用同一个模型，但至少需要两个并发 model call 通道：一个短而快的 conversation coordinator，一个持续工作的 worker。不要先做 planner、subagent、复杂 diff、长期 memory 或通用 workflow engine。

一条完整关键路径

用户提交材料和目标后，Agent 产出第一个文档版本并继续加工。用户先问“为什么采用这个结构”，conversation loop 给出简短回答，文档工作不停止；用户再补充一条背景信息，系统把它用于相关后续部分；最后用户明确说“不要讨论市场，只谈交互机制”，这时才 steer 并使受影响的片段重算。

第一次明确价值感知不只是“随时能纠正”，而是用户可以继续交谈、补充和回答，同时看到 Agent 没有因为每句话都停工。人不再只能在“等它做完”和“打断它”之间二选一。

验证方法

先用真实工作 dogfood 十次，修到消息不丢失、主工作不会被无关对话误停、版本不回退、事件能追踪。然后找五到八名经常用 Agent 写方案、总结材料或生成文档的人，做组内对照：普通模式只能等待或停止；steer 模式可以中途改变方向，但每次输入都作用于当前 run；全双工模式还允许 query、context 和 answer 与主工作并行。

任务中应自然包含至少两次方向变化。可以由用户自己发现，也可以在预定时间给出新增约束，避免因为任务太短而根本没有干预机会。

只看三个主指标：用户交流期间主工作的有效推进时间；系统把非 steer 消息错误转成中断的比例；用户下一次是否主动选择全双工而不是 steer-only。日志同时记录每条消息的类型、是否中断 worker、对应回答或生效版本。

如果用户只使用 steer，而几乎不在工作进行时提问、补充或回答，那么 steer 已经足够，“全双工”没有额外价值。如果用户会自然进行这些交流，并明显反感 steer-only 带来的频繁停工，才出现独立产品信号。

最重要的产品判断

Steer 的核心是让用户可以改变正在执行的任务。全双工的核心是把“交谈”和“工作”拆成可并行的两条流，steer 只是其中一种需要改变 work loop 的消息。

如果对话与工作并行没有产生独立价值，这个产品就应被诚实地称为更好的 steer 机制，而不是全双工 Agent。只有当用户能在 Agent 持续工作时自然交流，且系统能选择性吸收而非一律打断，才值得扩展到代码、研究、工具调用或语音。
