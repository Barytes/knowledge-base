Codex 与 AI 产品工作的实现廉价化

当 AI 让实现和原型成本下降后，产品工作的稀缺点转向品味、策展、系统嵌入、媒介选择和模型能力时机判断，而不是简单取消 PM / 设计 / 工程角色。

核心判断

这篇访谈的核心不是“AI 会不会替代 PM / 设计 / 工程”，而是：当实现成本骤降之后，产品工作的稀缺点从“把东西做出来”转向“判断什么值得做、怎样嵌入系统、什么时候该做、用什么媒介表达”。

原型、代码、文档都变便宜以后，团队会同时产生大量看似可发布的方案。真正昂贵的是筛选、整合、命名、边界判断和系统嵌入能力。这里的 taste 不只是审美，而是产品方向、系统关系、交互语义、组织协同和投入优先级的综合判断。

1. 实现廉价后，产品流程被反转

传统产品流程默认“实现昂贵”：先研究、写 PRD、做设计、做原型，尽量在工程投入前消除风险。AI 编程工具让实现本身变得更便宜，导致多人可以并行做出大量高保真原型。

这会带来一个反直觉变化：过去稀缺的是工程产能，现在稀缺的是策展能力。团队不再只问“能不能做出来”，而要问：

  • 这些方案里哪个真正有价值？
  • 哪个体验可以进入系统，而不是停留在演示？
  • 这个点子应该是独立功能、现有功能的一部分，还是更大主题下的一个交互？
  • 哪些实现只是看起来成熟，但其实还没有经过需求、研究和系统一致性的验证？

所以，“人人都能做原型”并不会自动带来更好的产品，反而会放大判断力差异。

2. PRD 与原型不是新旧之争，而是媒介选择

访谈反对简单的“PRD 已死，原型当立”。当每一种表达媒介都变便宜以后，关键不再是固定崇拜某一种媒介，而是为不同问题选择正确媒介。

如果问题是模糊领域中的产品清晰度，文档仍然有价值，因为它能迫使团队澄清目标、边界、假设和未解问题。如果问题是交互是否成立、用户是否能自然完成任务，原型更合适，因为它能让人直接感受行为和反馈。

危险在于高保真原型会制造“已经快上线”的错觉。一个视觉上接近正式产品的东西，可能只是早期探索；如果团队忘记标注它在流程中的真实阶段，就容易被外观锚定，提前锁死方向。

3. taste 是系统判断，不只是审美

文章里的 taste 可以拆成几层：

  • 审美层：视觉、动效、节奏、质感是否匹配语义。
  • 交互层：某个动作、反馈、布局是否让用户自然理解。
  • 系统层：这个功能如何嵌入现有产品，是否应该和其他能力合并或分离。
  • 方向层：这个点子属于哪个更大的产品主题，是否值得投入。
  • 组织层：团队在大量并行探索中如何筛选、组合、停止和推进。

这和本库里的 Taste：感受良质的能力 可以互相补充：AI 让产出变多以后，taste 的价值不是“我喜欢什么”，而是能否在过剩方案中识别出更高质量的结构。

4. 角色不会简单消失，而是边界重叠

访谈中最值得保留的组织判断是：AI 会让 PM、设计、工程的边界更重叠，但不会让专业能力消失。工程师可以更快做原型，PM 可以更快验证交互，设计师可以更深地进入实现；但这不等于所有人都变成同一种“builder”。

取消 PM 或轻视设计，往往是把“能生成东西”误认为“能定义正确的东西”。AI 让角色之间的交接成本下降，但产品判断、研究敏感度、系统设计、工程抽象、组织协调仍然需要专门能力。

更合理的组织形态不是“无角色”，而是：

  • 高自主性 IC 需要有产品感。
  • 产品和设计要能理解实现边界。
  • 工程要能参与产品判断，而不是只接需求。
  • 管理者要帮助团队在大量原型中形成一致方向。

5. 产品时机越来越受模型能力曲线约束

访谈提醒：AI 产品的成败不只取决于想法，还取决于底层模型能力是否刚好跨过可用阈值。同一个产品形态，可能在几个月前不可用，几个月后突然成立。

这意味着 AI 产品判断需要把“当前模型能力”和“未来能力曲线”同时纳入视野：

  • 当前跑不通的功能，不一定是坏主意，可能只是模型能力还没到。
  • 当前可演示的功能，不一定能成为产品，可能只是局部 demo。
  • 团队可以提前构建一些未来能力测试件，用来等待模型越过阈值。
  • 产品发布时间、交互形态和容错设计，要跟模型能力匹配。

这和 AI 产品六层与 L3-L6 能力分层 的判断相连：AI-native 产品不是把已有软件套上模型，而是围绕模型能力、任务委托深度和运行时边界重新定义产品。

6. Codex 的信号：工作底座，而不是单一聊天框

文章里最有启发的 Codex 信号，是它不只被理解为“写代码工具”，而被理解为一种能进入现有工具链、读写文件、调用浏览器、连接外部系统的工作底座。

这和“所有工作都塞进聊天框”的方向不同。更强的 AI 产品不是逼用户迁移到一个新界面，而是沿着用户已有工具和材料渗透：项目文件、浏览器、设计稿、剪辑软件、知识库、内部系统都可能成为 agent 的操作对象。

因此，未来的产品问题会从“用户怎么逐字写 prompt”转向：

  • 用户如何监督多个 agent 的工作？
  • agent 如何在现有工具里安全行动？
  • 系统如何让用户可中断、可检查、可回滚？
  • 哪些个人 workflow 应该沉淀成通用产品能力？
  • 产品如何避免把复杂度转嫁给用户自己搭一套外部系统？

这与 Agent 时代的人机交互新命题 和 Coding Agent Harness Comparison 直接相关。

对本库的意义

这篇材料可以作为 AI 产品定义的一条基准线：当实现成本下降，产品工作不能退化成“谁都能做 demo”，而要升级为“谁能在 demo 过剩中定义正确系统”。

对之后判断 AI 产品时，可以优先问四个问题：

1. 这个产品的稀缺点到底还是实现，还是已经转向判断、策展、系统整合？

2. 当前用的是文档、原型、代码还是 demo？这个媒介是否匹配它要回答的问题？

3. 这里的 taste 是审美判断、交互判断、系统判断，还是方向判断？

4. 这个产品是否依赖模型能力继续上升？如果是，当前版本是在服务用户，还是在等待未来阈值？
