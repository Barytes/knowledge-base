多人协作知识治理（含 routed context）：对外一页纸版本

一句话产品定义（Product Definition Belief）

当一群人开始共享 context 时，关键不在于先统一成某个版本，而在于如何把每个人的认知、判断和经验都放进一个公共空间，并在回答具体问题时，把合适的视角、证据和差异带到提问者面前。系统需要处理的不是“先选出一个赢家”，而是“这次该把哪些认知带出来给这个问题看”；否则，公共空间要么变成彼此看不到的知识茧房，要么在使用时把多样性抹平。

这类问题更像**把多人的 context 放进公共空间（share）+ 按问题编排这些差异（route）**，而不是单纯“知识库整理”。

这里说的“隐性知识”，不是还停留在脑中的 tacit knowledge，而是**已经外化到个人电脑、文件、笔记、聊天记录和 agent 工作流里，对本人已经显性、但对其他人仍然隐性**的知识。产品要做的，不是把脑中的东西挖出来，而是把这些“局部显性、全局隐性”的知识放进公共空间，并在具体问题上把它们路由给需要的人或 agent。背后的假设也不是“context 越多越好”，而是**越相关、越有区分度、越保留多样性的 context，越能帮助 agent 做出更好的回答与行动**。

ICP（第一版先求窄）

  • 任意 5–200 人的协作群体：公司团队、开源社区、兴趣小组、读书会、行业社群、课程社区、研究组等
  • 群体成员已经各自沉淀了自己的 context（判断、经验、笔记、版本、反例），这些内容对本人已经显性可用，但还分散在个人文档、群聊、仓库、本地文件或 agent 工作流中，尚未很好地进入一个可共享的公共空间
  • 已出现过因为大家各自理解不同，导致返工、误解、争论成本、决策偏离，或彼此的认知和经验没有真正互相借鉴起来
  • （可选但会显著放大问题）这些 context 正在被 LLM/Agent/自动化工作流使用，用于生成内容、回答问题、执行流程或辅助决策

核心问题（他们为什么会真的在意）

1. **冲突不可避免**：冲突往往不是“谁对谁错”，而是“哪个场景用哪个定锚”。

2. **公共空间一旦被过度压平，执行就会失去多样性和可控性**：简单 merge 或 majority-wins 会让少数但关键的场景知识消失，导致人或 Agent 在关键任务上做出不一致的判断与行动。

3. **中心化审核不可扩展**：审核越重，知识更新越慢，最后大家绕过系统继续口头对齐。

4. **只有公共空间 + 个人空间还不够**：缺少第三层——**routed context**（使用时路由与冲突策略）。

核心洞察（你要验证的因果链）

  • 很多“操作知识”的差异，背后并不是谁对谁错，而是不同人对概念、规则、口径和经验的定锚不同。
  • 团队系统必须允许：

- 多版本作为公共空间里的资产被保留下来（shared）

- 分歧、反例和局部经验作为一等公民被保留（private / tension）

- 使用时按人、任务与场景，把相关差异路由出来（routed context）

  • 你真正要验证的，不是“能否形成统一答案”，而是：**当更多局部显性的知识进入公共空间，并被更好地路由给 agent 时，agent 的表现是否真的变好。**

方案形状（MVP 的最小形态）

一个 **routed context compiler**（CLI 或极简 Web 皆可）。

  • 输入：

- shared（公共空间中的知识源：wiki/文档/规范/FAQ 等，允许并存多个版本、观点和反例）

- private overlay（某个人/角色的补充理解、例外规则与偏好）

- task spec（任务类型、目标与约束）

  • 输出：

- 本次应加载的上下文包（给人或 Agent 的 context / prompt 片段）

- 路由说明（这次带出了哪些视角、差异和证据，为什么）

MVP 的目标不是“做成产品”，而是跑通一次最小验证闭环。

关键路径（最小验证闭环）

入口（短文/一页纸/定向外联）

→ 对方愿意给 1–2 个真实冲突案例（首个真实成本）

→ 你用 compiler 产出一次 routed context + 冲突解释（首次价值）

→ 对方愿意拉同事再看一次/在真实任务里试一次（继续推进）

信号标准（Pre-PMF）

强信号（要追）：

  • 愿意给脱敏样例/冲突案例
  • 愿意约 15–30 分钟深聊，并愿意拉第二个同事
  • 愿意让你对接他们现有知识源（哪怕只是导出一份文档/知识片段）
  • 愿意在一个真实场景里试用（哪怕手工方式：把这套路由/冲突报告当作群体的“公共借鉴生成器”）

弱信号（只记录，不当进展）：

  • “很有启发”“不错”“建议你做成产品”
  • 点赞转发但不投入任何时间/数据/推进动作

非目标（避免发散）

  • 不替代现有 wiki/文档工具（Notion/Confluence/GitBook/GitHub 等），只做知识治理与路由层
  • 不做完整 agent orchestration
  • 不把冲突强行合并成一个“单一答案”
  • 不在无强信号前进入企业级权限/合规/部署全家桶

---

2 周 Pre-PMF 冲刺

目标：在 2 周内验证“是否存在可重复的强信号”，而不是把系统做完整。

过线标准（Go / No-Go）

**Go（继续投入）的最低证据**（满足其一即可，但越多越好）：

  • A. 在同一 ICP 中拿到 **≥2 次** 15–30min call（讨论真实案例与现有协作流程/治理方式）
  • B. 拿到 **≥2 份** 脱敏冲突样例（定义/规则/口径冲突 + 具体任务）
  • C. 出现 **≥1 次**“继续推进动作”（拉同事、给更多数据、愿意试点一次）

**No-Go / 需要校准**：

  • 触达 ≥15 个潜在 ICP 后，仍拿不到任何样例与通话；或反馈集中在“有意思但我们不想投入任何成本”。

每天的最小动作（14 天）

原则：每天只做一个最小推进动作，保证路径不断档。

  • Day 1：把本页压成可外发的 PDF/图片（1 页）+ 准备 1 段 150 字外联文案。
  • Day 2：发给 1 个种子用户（如 Joey；只推一次）：3 个具体问题 + 15 分钟请求。
  • Day 3：列出 15 个潜在 ICP（公司/团队/联系人），写下“你为什么认为他们痛”。
  • Day 4：定向外联 3 人（不求多，求准），同一套一页纸。
  • Day 5：把短文发到一个公开渠道（Superlinear/LinkedIn/公众号其一即可），结尾明确“征集冲突案例 + 约访谈”。
  • Day 6：外联再 3 人；并对已读不回者做一次 follow-up（只一次）。
  • Day 7：整理本周信号分层：强/弱/噪音；写下主卡点初判（只选一个）。
  • Day 8：做一个“手工 demo”模板（Markdown 即可）：输入样例 → 输出 routed context + 冲突报告。
  • Day 9：完成第 1 次 call（若尚未约到，继续外联 3 人，并把请求改成“只要 1 个冲突样例也行”）。
  • Day 10：基于 call/样例，把一页纸改 1 处（只改一个主变量：ICP/表达/路径/价值其一）。
  • Day 11：外联 3 人（用更新后的版本），重点找“相似 ICP”，测试重复性。
  • Day 12：完成第 2 次 call 或拿到第 2 份样例；把样例转成匿名化的“冲突模式库”（先 3 条）。
  • Day 13：提出一个“下一步推进动作”请求：拉同事、给更多样例、或让你对接他们现有知识源。
  • Day 14：做 2 周复盘：信号摘要、主卡点、下一轮只优先改什么、下周过线标准。

复盘模板（每周一次即可）

  • 本周强信号有哪些（带行为证据）？
  • 最大卡点出在哪一步（ICP / 表达 / 路径摩擦 / 价值强度 / 转化门槛）？
  • 下周只改一个什么？希望看到什么变化？
