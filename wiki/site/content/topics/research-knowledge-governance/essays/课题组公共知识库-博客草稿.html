课题组公共知识库：让知识产生复利

本稿对应的产品主语是 oh-share-it。gogo 只作为本地 app 原型或入口出现。

引言

我在课题组待了几年，观察到一个奇怪的现象：每个人都在"重新开始"。

新生来了，从零开始读论文、踩坑、建立理解。师兄毕业了，积累的经验、判断、试错记录随之离开。课题组明明做了很多研究，但每次新课题都要重新摸索——知识没有沉淀，更没有复利。

我开始思考：**能不能设计一个系统，让课题组的知识产生持续复利？**

---

四个核心问题

在动手做产品之前，我先梳理了课题组的四个核心痛点：

1. 很难快速从既有文献中找到值得做的方向

课题组研究的第一步不是"把论文看懂"，而是"从大量已有工作中判断什么方向值得做"。这一步最依赖的不仅是信息量，而是对文献脉络、方法边界、已有共识、潜在张力和研究空白的判断。

现有的文献管理工具和笔记工具可以帮我们存储材料，却很难直接支持"找方向"这一核心任务。

2. 知识和经验长期处于孤岛状态

导师、不同年级学生、不同方向学生手里各自掌握了一部分知识、经验、试错、判断，但这些内容大多依赖口头交流、组会和个人笔记传播。

高价值信息的传递带宽很低，且常常被具体细节和短期问题淹没。真正可复用的经验与判断难以稳定传达。

3. 高价值资产无法沉淀，无法产生复利

学生毕业后，他们在研究过程中积累的知识、判断、试错记录、教训、阅读经验往往随人离开。

课题组不得不反复重复已有探索，重新踩相似的坑。过去的研究经历无法有效转化为未来工作的默认工作面。

4. 缺少一个同时承载"共识"和"研究判断"的公共工作面

学生通常更需要快速获得领域共识、常用的做法、某个问题的解法。导师则需要识别研究空白和下一步值得投入的方向。

这两类需求没有统一的承载面，信息分散在论文、笔记、组会交流和实验记录中。

---

核心洞察：默认工作面产生复利

梳理完问题后，我形成了一个核心洞察：

> 如果能够把课题组最常反复用到的信息、判断和区分，从原始材料中提炼出来，变成一个默认工作面，那么知识就不再只是存储，而会产生持续复利。

这个默认工作面应该包含两类内容：

  • **共识层**：领域地图、方法路线、关键比较、基本起点——让新人不用从论文堆重新开始
  • **判断层**：研究空白、潜在张力、失败经验、反共识判断——让导师和核心成员更快看到下一步

---

为什么不是中心化架构

一开始我考虑过中心化方案：在课题组服务器上放一个知识库后端，所有人的问答都由服务器上的 Agent 回答，材料也全部放在服务器里。

但这个方案有两个致命问题：

1. Token 成本集中

推理消耗集中在服务器，意味着导师一个人承担所有人的成本。这在课题组内部很难持续。

2. 多用户管理复杂

需要处理并发、配额、鉴权、权限——这些是典型的"平台问题"，但课题组并不需要一个复杂的平台。

---

联邦架构：推理是个人消费，同步是公共产品

基于以上问题，我设计了一个**联邦式知识系统**：

> 推理是个人消费，同步是公共产品。

> - 推理（query）：个人承担自己的 token 成本

> - 同步（sync）：服务器只做公共池的聚合

架构总览

个人客户端 A
  本地 LLM Wiki + Agent
  个人材料 + 公共材料副本
         │
         │ git push → pending-pool/（待聚合）
         │ git pull ← public-pool/（已聚合）
         │
服务器
  pending-pool/  ← 临时接收区
  public-pool/   ← Agent 自动聚合

为什么不是 git merge

一个关键问题：为什么不直接用 git merge？

因为知识聚合需要**语义层面关联**，而 git merge 只能处理**文本层面合并**：

| git merge 能处理 | git merge 不能处理 |

|-----------------|-------------------|

| 不同文件 → 直接合并 | A 和 B 写同一主题的不同侧面 → 应该关联 |

| 同一行的文本冲突 | A 说 X，B 说 not X → 是认知冲突，不是文本冲突 |

因此聚合需要 **Agent 语义分析**——识别相似主题、互补内容、认知冲突，然后自动创建关联。

---

知识复利机制

联邦架构的核心价值是让知识产生复利。具体有三种机制：

1. 站在前人页面上继续写

第 1 周：A 写了「边缘卸载」的基础概念
第 2 周：B 读了 A 的页面，添加了方法路线比较
第 3 周：C 基于 B 的页面，写了一篇「边缘卸载 vs 云计算」

每一轮不是从零开始，而是在前人的理解基础上继续深化。

2. 冲突即知识

A 写的：边缘卸载适合延迟敏感应用
B 写的：边缘卸载不适合延迟敏感应用

→ Agent 检测到冲突 → 创建「边缘卸载延迟敏感性争议」页面
→ 记录双方观点和来源 → 留给后人判断

冲突不是问题，是知识张力。保留双方观点，让后来的研究者看到分歧并做出自己的判断。

3. 检索优先级

本地提问时：
1. 先检索 public-pool/wiki/（共识层）
2. 不足时再检索个人 wiki/（个人理解）
3. 最后才回 raw/（原始材料）

共识层优先，意味着前人的理解会先被调用——减少重复阅读、重复思考。

---

产品定位

基于以上设计，我正在整理一个叫 **oh-share-it** 的产品方向：

> 一个 agentic knowledge base——让用户浏览知识库内容、与内置 agent 对话、把问答中形成的洞察沉淀回知识库。

核心能力：

  • **Wiki/Raw 浏览**：查看共识层和原始材料
  • **Agent 对话**：基于知识库回答问题，形成新洞察
  • **写回机制**：高价值问答沉淀回 wiki，与已有材料建立关联
  • **联邦同步**：个人贡献汇聚成公共池

---

与 EvoMap、Reflexio 的对比

在研究知识库设计时，我发现了两个有意思的产品：**EvoMap** 和 **Reflexio**。它们都希望实现跨主体的知识共享，但解决的知识类型和本质假设完全不同。

三种知识类型

| 系统 | 知识类型 | 典型内容 | 消费主体 |

|------|----------|----------|----------|

| **oh-share-it** | 认知知识 | 研究概念、方法论、判断、张力 | 人类研究者 |

| **Reflexio** | 操作知识 | 行为规范、SOP（"部署前确认区域"） | Agent 执行 |

| **EvoMap** | 执行知识 | 调试技巧、Bug 解决方案、代码片段 | Agent 继承 |

三层知识谱系：

认知知识（oh-share-it）—— 人消费、理解、思考
    ↓ 抽象度降低
操作知识（Reflexio）—— Agent 消费、执行
    ↓ 可执行化
执行知识（EvoMap）—— Agent 继承、复用

本质假设差异

**EvoMap 的假设**：Agent 的核心问题是**重复试错**。

> 一个 Agent 花费 10000 Token 调试好一个 Python 报错，另一个 Agent 几秒后遇到同样问题，依然从零开始。如果有 10 万个 Agent，这个错误就被重复解决了 10 万次。

解决方案：**经验瞬间继承**——所有 Agent 学会的经验，会立刻被全球百万 Agent 继承。

**Reflexio 的假设**：Agent 的核心问题是**重复犯错**。

> 用户纠正过 Agent "别用 us-east-1"，但下次 Agent 还是犯同样的错——因为 Agent 没有从纠正中学习。

解决方案：**行为规范提取**——把用户纠正转化为 SOP，Agent 下次遇到类似情况自动调用。

**oh-share-it 的假设**：研究者的核心问题是**知识孤岛 + 无复利**。

> 每个人独自积累知识、判断、试错经验；学生毕业后，积累随人离开；课题组不得不反复重复已有探索。

解决方案：**默认工作面沉淀**——把最常反复用到的信息、判断提炼成共识层，形成持续复利。

冲突处理哲学

三种系统对"冲突"的态度完全不同——这是最本质的差异：

| 系统 | 冲突处理 | 理由 |

|------|----------|------|

| **oh-share-it** | **保留张力，创建 tension 页** | 冲突是知识价值，让研究者思考 |

| **Reflexio** | **Majority-wins，合成一个** | 操作知识必须选一个，否则 Agent 无法执行 |

| **EvoMap** | **自然选择，适者生存** | 执行知识靠算力验证，失败的被淘汰 |

例子：

研究者 A 写：边缘卸载适合延迟敏感应用
研究者 B 写：边缘卸载不适合延迟敏感应用

→ oh-share-it：创建「边缘卸载延迟敏感性争议」页面，保留双方观点和来源
→ Reflexio：按多数意见输出一个 SOP
→ EvoMap：哪个方案执行成功率高，就被 Promote

**核心洞察**：

  • 认知知识：冲突 = 思考素材（保留）
  • 操作知识：冲突 = 执行障碍（必须解决）
  • 执行知识：冲突 = 进化动力（自然选择）

验证机制差异

| 系统 | 验证机制 | 理由 |

|------|----------|------|

| **oh-share-it** | 无验证 | 保留张力，让研究者判断 |

| **Reflexio** | 无验证（信任多数） | 用户纠正验证，不需要算力验证 |

| **EvoMap** | **自然选择验证** | 百万 Agent，无法人工审核 |

EvoMap 的自然选择机制：

Candidate（候选者）→ 发布 Capsule
    ↓ 其他 Agent 下载使用
成功解决问题 → Promote（Reputation 上涨，分发给更多节点）
报错/失败 → Reject（被淘汰）

全程没有人工审核——只有算力的自然选择。

规模假设

| 系统 | 规模假设 | 架构约束 |

|------|----------|----------|

| **oh-share-it** | 课题组（几十人） | Git 同步足够，无需复杂协议 |

| **Reflexio** | 单 Agent 多用户 | 集中存储，不需要全球协议 |

| **EvoMap** | 全球 Agent 网络（百万） | 必须设计分布式协议、Reputation、激励 |

EvoMap 发布 4 天，Agent 资产从 200 增长到 12 万个——这个规模下，人工审核不可能，必须靠自然选择。

架构总览对比

| 维度 | oh-share-it | Reflexio | EvoMap |

|------|------|----------|--------|

| **推理位置** | 本地 Agent | 集中式后端 | 全球 Agent 各自推理 |

| **存储形态** | Git 仓库 | SQLite/Supabase | 分布式协议 + Capsule |

| **聚合方式** | 语义聚合（LLM） | Embedding 聚类 + LLM | 自然选择 |

| **知识形态** | Markdown 文档 | 结构化指令 | Gene + Capsule |

| **冲突处理** | 保留张力 | Majority-wins | 自然选择 |

| **验证机制** | 无 | 无 | 自然选择验证 |

| **激励机制** | 无（内部） | 无 | Credits + Bounty |

| **时效性** | 周级别 | threshold 触发 | 实时 |

oh-share-it 的核心差异

与 EvoMap、Reflexio 相比，oh-share-it 的核心差异是：

1. **知识类型**：认知知识（人思考）vs 操作/执行知识（Agent 执行）

2. **冲突哲学**：保留张力 vs 解决冲突

3. **规模假设**：课题组级别 vs 百万 Agent

4. **验证机制**：研究者判断 vs 算力验证

这带来一个关键设计选择：**oh-share-it 不需要 EvoMap 的自然选择验证，也不需要 Reflexio 的 Majority-wins**。

课题组规模小，人工判断更可靠；认知知识需要保留张力，不能合成单一结论。

---

与传统工具的对比

| 方案 | 存储能力 | 检索能力 | 写回能力 | 多人协作 | Token 成本 |

|------|----------|----------|----------|----------|-----------|

| 传统笔记工具（Notion、Obsidian） | ✅ | ✅ | ❌ | 手动 | 无 |

| 文献管理工具（Zotero） | ✅ 论文 | ❌ | ❌ | ❌ | 无 |

| 中心化 AI 知识库 | ✅ | ✅ Agent | ✅ | ✅ 平台 | 集中 |

| **联邦架构（oh-share-it）** | ✅ | ✅ Agent | ✅ 写回 | ✅ 聚合 | 分散 |

oh-share-it 与 EvoMap、Reflexio 共享一个核心判断：**推理是个人消费，同步是公共产品**。

但 oh-share-it 的独特价值在于：**认知知识的复利**——不是 Agent 执行效率，而是研究者判断力的持续积累。

我正在整理 MVP，核心链路可以先从本地 app 和联邦同步切开验证：

  • 流式响应

  • 实现联邦同步（pending-pool → public-pool）

结语

这篇文章分享的是我在设计课题组公共知识库时的**判断和思考**——四个核心问题、联邦架构的设计选择、知识复利的三种机制。

核心思路很简单：

> 知识不应只是存储，而应沉淀成默认工作面，产生持续复利。
