被持续委托的工作主体

摘要

这页原本想抓住一个重要直觉：用户真正想长期协作的，不是某个 runtime、某个 session，也不是某次 prompt 的输出，而是“那个我一直在和它合作的 agent”。

但如果把这个概念写成“被持续委托的工作主体”，也很容易滑偏。最常见的误解就是把 agent 和它手上的某项工作绑死，仿佛一项工作结束，这个 agent 也就跟着结束。

更准确的说法应该是：

> agent 不是工作本身，而是可以持续持有多项工作、并与用户保持长期协作关系的对象。

因此，这页真正要澄清的，不是“agent = 某个持续中的工作”，而是：

> 为什么今天的 agent 产品还没有把 agent 做成一个可被持续委托、持续找到、持续接回、持续接管的协作对象。

这个概念真正有价值的地方

1. 它指出用户真正想找回的不是进程，而是协作对象

用户离开原设备之后，真正焦虑的通常不是：

  • 某个 PID 还在不在
  • 某个 websocket 还通不通
  • 某个 terminal session 能不能 resume

用户真正想知道的是：

  • 这还是不是原来那个 agent
  • 它还记不记得我和它怎么协作
  • 它手上还拿着哪些我交给它的事
  • 我现在能不能继续和它一起推进这些事

所以这个概念最有价值的地方，在于它把问题从 runtime 连续性提升成了 collaboration continuity。

2. 它要求把几个常被混掉的对象分开

这页最重要的澄清，就是下面这几个对象不能再混为一谈。

  • device 是算力位置
  • runtime 是执行环境
  • session 是某次交互或执行的上下文容器
  • assignment 是用户当前交给 agent 的某一项工作
  • agent 是那个可以持有多项 assignment、并与用户保持持续关系的协作对象

这层区分一旦成立，很多混乱都会消失。

用户说“还是不是它”，问的不是同一个 session 还在不在，而是同一个 agent 还在不在。

用户说“我还能不能接回来”，问的也不是终端能不能续上，而是我能不能重新回到这个 agent 和我之间那段协作里。

3. 它强调的核心不是单项工作连续，而是委托关系连续

真正应该被持续的，不是某一项工作本身，而是委托关系。

一个 agent 可以：

  • 完成一项工作
  • 暂停一项工作
  • 取消一项工作
  • 同时持有多项工作
  • 在不同时间切换工作的优先级

但这些变化都不意味着 agent 消失。真正持续的是：

  • 这个 agent 还是“它”
  • 你和它的默认合作关系还在
  • 它仍然承接着你交给它的一组 assignments
  • 你可以回来重新进入、检查、调整和接管

所以更准确的主线不是“被持续委托的工作”，而是“被持续协作和持续委托的对象”。

今天的 agent 产品距离这个概念还有哪些 gap

1. 对象层 gap：系统里更稳定的单位仍然不是 agent

从当前本地材料看，不管是 terminal-first harness，还是像 multica 这样的管理平台，系统里更稳定的对象通常仍然是：

  • terminal session
  • runtime
  • task
  • issue lifecycle

而不是一个高于这些对象、能把关系、委托与接回统一起来的 agent。

这会导致一个很具体的问题：系统里有很多状态，但用户未必真的知道自己面对的还是不是“它”。

2. 身份层 gap：agent identity 仍然深度附着于执行位置

今天很多 agent 一旦换设备、断 session、重启 CLI，就会表现得像一个新壳。

用户重新进入时看到的常常是：

  • 一个新的聊天窗口
  • 一个新的终端状态
  • 一串需要自己重新拼接的日志

这说明身份连续性还没有被独立建模。agent 仍然太像 runtime 的影子，而不是一个高于 runtime 的协作对象。

3. 关系层 gap：长期合作关系没有被显式承接

和人类同事协作时，真正稳定的不只是“你认识他”，而是你们之间有默认合作方式。

比如：

  • 他知道你通常怎么提需求
  • 你知道他通常怎么推进工作
  • 你们对何时汇报、何时自主决策有默认预期

今天很多 agent 产品在这里仍然很弱。它们也许有一点长期记忆，但还没有把这种合作关系本身做成可依赖的对象层。

4. assignment 层 gap：工作还太像 prompt，不像持续委托

今天不少 agent 交互仍然停留在：

  • 我说一句
  • 你做一点
  • 你回一句

这更像短回合对话，而不是持续委托。

如果要接近“持续在岗的同事”，assignment 至少要能承接：

  • 目标
  • 当前状态
  • 成功条件
  • 阻塞点
  • 最近行动
  • 下一步预期

否则用户回来时面对的就仍然是一串消息，而不是一组可继续协作的工作。

5. re-entry gap：今天多数系统解决的是 reachability，不是 re-entry

很多系统已经能让你：

  • 联系到 agent
  • 给它发消息
  • 看到它是否在线
  • 看到它完成或失败

但这不等于真正的 re-entry。

真正的 re-entry 是：你回来时可以直接进入当前协作状态，快速判断发生了什么，并继续委托、修正方向、暂停或接手，而不是先把上下文重新拼一遍。

6. 可见性 gap：很多可见性仍停留在结果层，而不是工作现场层

很多系统已经能显示：

  • 开始了
  • 结束了
  • 成功了
  • 失败了

但这和“我看见它此刻怎样在工作”仍然差得很远。

真正支撑 re-entry 的可见性通常还需要：

  • 它为什么走这条路径
  • 当前卡在哪个子步骤
  • 最近改了什么
  • 测试为何失败
  • 当前状态值不值得继续信任

这类信息不足，用户就很难真正把 agent 当成一个能持续协作的对象。

现有产品各自更接近哪一层

terminal-first coding agent

像当前知识库里总结的 Claude Code、Codex、pi 这类 terminal-first harness，强项在本地工作面的直接性和局部可观察性。

但它们的基本单位通常还是：

  • terminal
  • session
  • repo 工作面

所以它们更像“带状态的本地工作会话”，还不是“高于执行位置的持续协作对象”。

multica 这类 managed agents 平台

multica 已经往前走了一步。它承认 agent、runtime、task lifecycle 都是不同对象，也更重视任务分配和回报。

但从当前本地材料看，它更强的是“把 agent 纳入团队任务系统”，不一定已经完整解决：

  • 高于 runtime 的 stable identity
  • 长期合作关系的显式承接
  • 强 re-entry 语义
  • 工作现场级的高分辨率可见性

所以它离这个概念更近，但还不是同一个问题的终点。

clawhouse 最值得 bridge 的是什么

1. 先把 agent 这个对象定义清楚

clawhouse 最值得做的第一件事，不是先设计 launcher，而是先把对象层定义清楚：

  • agent 是什么
  • assignment 是什么
  • session 和 runtime 各自是什么
  • 它们之间如何关联

如果这一步不先清楚，后面的网络层、UI 层、可见性层都会继续混掉。

2. 给 agent 一个比 session 更稳定的 identity

如果想让用户真觉得“还是它”，系统就需要有一个比 session 更稳定的 identity 层。

这层至少要承接：

  • 它是谁
  • 它通常怎么工作
  • 它当前可在哪些设备上运行
  • 它现在依附于哪个 runtime
  • 它手上还有哪些 assignments

3. 把 assignment 从 prompt 提升成显式对象

这一步不是为了把 agent 变成工作本身，而是为了让 agent 能稳定持有工作。

用户回来时，看到的应该不是一串 message history，而是一组 assignment：

  • 每项工作是什么
  • 做到哪了
  • 卡在哪
  • 下一步是什么
  • 现在建议用户做什么

4. 把 “re-enter / inspect / continue / take over” 做成一等语义

这可能是 clawhouse 最独特的地方。

很多现成系统都在做：

  • connect
  • chat
  • monitor

clawhouse 更值得做的是：

  • re-enter
  • inspect current assignments
  • continue collaboration
  • take over

也就是把“重新接回这段协作”本身做成显式交互，而不只是“重新连上一个入口”。

5. 把设备退到算力层，让 agent 站到主语层

在产品语义上，一个很关键的翻转是：

  • 用户先看到的是 agent
  • 再看到它当前借用了哪台设备、哪个 runtime

而不是先看设备列表，再猜每台机器上到底跑着什么。

这会让系统更接近“持续在岗的同事”，而不是“很多散落的 agent 进程”。

一句收束

如果把这页压成一句最有用的话，我现在会写成：

> 真正值得追求的，不是“同一个持续中的工作”，而是“同一个可以持续持有工作、并被用户持续协作与持续接回的 agent”。

这句话比旧版更稳，因为它既保留了对象层洞察，也避免了把 agent 误写成工作本身。
