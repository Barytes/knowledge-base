Clawhouse：多设备 Agent 上下文同步

问题描述

你手头有很多设备：

  • 实验室台式机
  • 宿舍的游戏本
  • MacBook Air
  • 腾讯云的 VPS

每台设备都可以跑 coding agent（Codex、pi、Claude Code 等），项目的静态文件可以用 GitHub 或 iCloud 同步。

**问题是：** 当你离开一台设备后，想用手机或 iPad 继续工作时，无法接上之前的对话上下文。你得：

  • 回到原来那台设备的位置
  • 或者记下来，晚点再弄
  • 要么用远程桌面
  • 要么背着 MacBook 到处走

**现有方案的局限：** 如果用聊天软件接入 agent（如 OpenClaw），工作过程变成黑盒——你只能看到 agent 反馈的内容，看不到它实际做了什么。

---

核心目标

> **同步和恢复不同设备间的动静态上下文，让人可以在任何设备上继续工作。**

两层上下文

| 层级 | 内容 | 同步方式 |

|------|------|----------|

| **静态上下文** | 代码状态、文件内容、项目结构 | GitHub / iCloud 等已有同步 |

| **动态上下文** | 对话历史、agent 知道的信息、当前做到哪了 | 需要新解决 |

**静态上下文已经解决了。** 项目的代码、文件可以用 Git 同步，这在你的工作流里已经是现成的。

**动态上下文是 clawhouse 要解决的。** 具体来说：

  • 当前项目里开了多少个对话
  • 每个对话的历史记录是什么
  • 每个对话当前聊到哪了
  • agent 已经知道了什么信息

---

最小可行方案

核心思路

> 直接同步 coding agent 导出的对话历史文件。

不同 agent 都有某种形式的对话存储：

| Agent | 存储位置 | 格式 |

|-------|----------|------|

| **Codex** | .codex/ 目录 | JSON |

| **Pi** | ~/.pi/agent/sessions/ | JSONL（树状结构，支持分支） |

| **Claude Code** | 待调研 | 待确认 |

方案描述

1. 把这些对话文件同步到共享存储（GitHub、iCloud、或简单的后端服务）

2. 移动端读取这些文件，恢复对话上下文

3. 可以继续对话，新的记录再同步回去

**优点：**

  • 不需要改造 agent 本身
  • 利用现有的文件同步机制
  • 实现简单

**需要解决的问题：**

  • 不同 agent 的格式可能不同
  • 需要处理并发（如果在两个设备同时对话）
  • 文件可能会很大，需要增量同步

交互界面的核心挑战

两种极端方案

| 方案 | 优点 | 缺点 |

|------|------|------|

| **聊天窗口**（OpenClaw 风格） | 阅读友好，适配移动端 | 黑盒，控制力弱 |

| **终端**（Termius + tmux 风格） | 完全掌控 agent | 移动端体验太差 |

中间态的可能性

能否抽象出 coding agent 交互界面的**本质要素**，提供一个中间态的交互界面？

**可能的本质要素：**

1. **输出/反馈** — agent 产生的内容（代码修改、命令结果、文件变化等）

2. **过程可见性** — agent 正在做什么、做到了哪一步

3. **控制能力** — 干预 agent 工作过程（中断、批准/拒绝、重试等）

4. **上下文** — 当前工作的背景（项目状态、对话历史、当前任务目标）

**目标：** 在"足够的信息量"和"友好的移动端呈现"之间取得平衡。

---

使用场景

典型场景

> 你正在实验室台式机上跟 Codex 一起改一个功能，聊了 30 轮，Codex 改了 5 个文件。

> 这时你要出门，只带 iPad。

> 打开 clawhouse，能看到：

> - 当前项目有哪些对话

> - 最近那个对话聊了什么、聊到哪了

> - Codex 刚完成了什么、下一步准备做什么

>

> 你可以继续对话，让 Codex 继续改下一个功能。

不做什么

clawhouse **不是**：

  • 远程桌面替代品（不流式传输整个终端）
  • 团队任务系统（第一性问题是单用户多设备）
  • 完整的 agent OS（不试图统一管理所有 agent）
  • 聊天插件（聊天只是交互壳，不是产品本体）

技术实现思路

基于 Pi Agent 的 JSONL 格式

Pi 的对话存储格式很适合做同步：

{"id": "abc123", "parentId": null, "role": "user", "content": "...", "timestamp": "..."}
{"id": "def456", "parentId": "abc123", "role": "assistant", "content": "...", "timestamp": "..."}
{"id": "ghi789", "parentId": "def456", "role": "user", "content": "...", "timestamp": "..."}

**特点：**

  • JSONL 便于增量追加和读取
  • 树状结构支持分支管理
  • 自带 compaction 机制处理长对话

同步流程

1. **监控文件变化**

- 监听 ~/.pi/agent/sessions/ 目录

- 检测到新文件或文件修改时触发同步

2. **同步到共享存储**

- GitHub：通过 Git 自动提交

- iCloud：直接同步目录

- 自建后端：HTTP API 推送

3. **移动端读取**

- 从共享存储拉取最新的 JSONL

- 解析树状结构，恢复对话上下文

- 提供继续对话的界面

4. **冲突处理**

- 利用 Pi 的树状结构特性，支持分支

- 或者移动端只读，避免并发修改

与 OpenClaw 的关系

OpenClaw 用**人格锁定**解决上下文问题：

  • 给 agent 赋予人格（SOUL.md、对话风格）
  • 用户因为情感连接而愿意一直用同一台设备
  • 上下文自然堆积在那里，不需要复杂的同步机制

clawhouse 用**同步机制**解决上下文问题：

  • 不锁定用户到单一设备
  • 用户可以在任何设备上接回对话
  • 上下文跟着用户走

Why not both？

人格化和同步不是对立的，而是**互补的**：

| 层级 | OpenClaw | clawhouse |

|------|----------|-----------|

| **表现层** | 人格化（对话风格、人格设定） | — |

| **基础设施层** | — | 上下文同步 |

如果两者结合：

  • 用户感受到"这是同一个 agent"（人格化）
  • 用户在任何设备上都能接回对话（同步）
  • **增强效果**：同步让人格化更有说服力——"它真的记得我们之前聊过什么"

---

更深层的抽象：工作面

**核心洞察：** 人类默认的工作面是**项目的现状**，而不是工具。

> 就像用微信时想的是聊天内容，而不是用哪个设备打开。

你在电脑上工作时：

  • 想的是 clawhouse、课题组知识库、Stackelberg game 论文
  • 不会想"我要用这的 Claude Code"或"那的 Codex"

所以 clawhouse 的长期愿景可能是：

  • 把设备、agent 的摩擦封装起来
  • 还原最基本的工作面
  • 用户只关心项目，不关心用的是哪台设备、哪个 agent

但这需要先把基础的同步问题解决好。

产品定位反思（2026-04-16）

云端产品已经天然解决的问题

| 问题 | 云端产品如何解决 |

|------|------------------|

| 去到哪都能接回 agent | ✅ 天然解决 — 数据在云端，任何设备登录即同步 |

| 持久记忆 | ✅ 云端存储，跨 session 持续存在 |

| 多渠道访问 | ✅ Web + App + API，随时接入 |

| always-on | ✅ 云端运行，不依赖本地机器在线 |

**云端产品（Kimi Claw、MaxClaw、腾讯云 Hermes、阿里云 OpenClaw、Slock）已经天然解决了"去到哪都能接回 agent"这个问题。**

clawhouse 可能的独特方向 vs 是否刚需

| 方向 | 云端产品的局限 | 是否足够刚需 | 判断 |

|------|---------------|-------------|------|

| 本地数据隐私 | 代码、对话上传云端 | 对部分用户是刚需，但多数人不介意 | 小众刚需 |

| 模型自由 | 云端绑定自家模型 | 对想用其他模型的用户是刚需，但普通用户不关心 | 中度刚需 |

| 成本控制 | 云端按次收费，不可控 | 重度用户在意，普通用户不敏感 | 中度刚需 |

| 透明度/可诊断性 | 云端 agent 是黑盒 | 对开发者是刚需，对普通用户不重要 | 开发者刚需 |

| 可定制性 | 云端封闭，不能改代码 | 极客/开发者在意，普通用户不需要 | 小众刚需 |

诚实的判断

**clawhouse 作为独立产品的独特性很弱。**

云端产品已经天然解决了核心问题，剩下的"本地优先"价值是小众刚需，不足以支撑一个有存在意义的商业产品。

定位转变：从"解决痛点"到"足够酷、足够个性"

放下"价值和痛点"的负担，回归做产品的本质乐趣。

**新的追求**：

| 追求 | 说明 |

|------|------|

| 学习 | 通过做，理解 agent 系统的核心概念 |

| 表达 | 把自己对"理想工作面"的理解变成可触摸的东西 |

| 创造乐趣 | 做出自己觉得有意思的东西，本身就是价值 |

| 验证直觉 | 你的直觉是"项目应该是主语"，做出来验证 |

| 个人工具 | 做一个自己真正愿意用的东西 |

"足够酷"可以是什么

| 方向 | 具体是什么 |

|------|-----------|

| 极致的移动端体验 | 不是"能用"，而是"用起来爽"——流畅、简洁、有设计感 |

| 独特的工作面抽象 | 不是设备列表、不是聊天窗口，而是"项目作为主语" |

| 可视化 agent 思维 | 能看到 agent 的思考过程、决策路径 |

| 实验性交互 | 尝试别人没做过的交互方式 |

| 极简但精准 | 不堆功能，只做几个核心动作，但做到极致舒服 |

一个具体方向：项目级工作台

**核心抽象：项目作为主语，agent 退到幕后。**

用户看到的不是：

  • "我有 3 个 agent 在线"
  • "这个 agent 的对话历史是什么"

而是：

  • **"这个项目现在是什么状态"**
  • 当前做到哪了
  • 最近改了什么
  • 下一步该做什么
  • agent 正在做什么、为什么

**这可能是一个没人做过的工作面抽象。**

最小但酷的版本

1. **项目 dashboard**

- 不是 agent 列表，而是项目状态概览

- 最近 activity、当前进度、下一步建议

- 简洁、有设计感

2. **对话历史可视化**

- 不是纯文本列表，而是有结构的呈现

- 分支、关键节点、决策点

3. **移动端优先**

- 做一个真正好用的手机/Pad 界面

不做什么

  • 不做团队协作（Slock/multica 已经做了）
  • 不做任务系统（multica 已经做了）
  • 不做人格化（OpenClaw 已经做了）
  • 不做云端同步（云端产品天然解决）
  • 不做 chat UI（太常见了）

收束

**clawhouse 不需要 claim 痛点，不需要打败竞品。**

它只需要：

  • 做一个**你自己觉得酷**的东西
  • 做一个**你自己愿意用**的东西
  • 做一个**表达你对理想工作面的理解**的东西

如果最后发现"这个抽象确实有意思"，那就是学习成果。

如果最后发现"这个方向其实不对"，那也是学习成果。

**做就是了。不是为了产品成功，而是为了创造和学习。**
