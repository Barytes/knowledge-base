Agent 系统求职与项目路线图（2026-05）

摘要

当前阶段的主目标不是继续增加项目数量，而是把已有项目收束成一个市场可识别的 Agent Systems Engineer 证据包。

目标岗位主线可以继续压成：

> 围绕 agent context / harness / evaluation / reliability，设计、构建并持续改进可靠 agent 系统。

这条主线已经和 gogo、oh-share-it、my-little-agent-loop、clawhouse 连得上。真正缺的不是方向，而是更硬的系统证据：

  • 可部署
  • 可观测
  • 可评测
  • 被真实使用
  • 有失败驱动的迭代记录

因此，下一阶段更合理的节奏是：选一个旗舰项目，把它做深；用一个真实试点补足 deployment / adoption / eval；用公开文章和定向外联把这些证据转成求职信号。

一、当前主线判断

你的项目不应该被解释成“四个不同方向”，而应被解释成同一条 agent systems 主线的四个层面。

| 项目 | 最适合承担的角色 | 当前优先级 |

|---|---|---|

| gogo | 个人 llm-wiki 工作台、agent context workbench、旗舰系统候选 | 高 |

| oh-share-it | 多人公共知识库、routed context、真实课题组试点 | 高 |

| my-little-agent-loop | 自己掌握的 agent harness / runtime ownership 载体 | 中高 |

| clawhouse | 多设备 agent 工作面探索、项目作为主语的产品表达 | 中低 |

压缩判断：

> gogo 适合作为作品集主入口，oh-share-it 适合作为真实使用试点，my-little-agent-loop 适合作为 runtime ownership 补强，clawhouse 暂时更像个人工作面探索，不应抢主线资源。

二、第一优先级：把旗舰项目补成证据包

从求职 north star 看，最需要补的是 eval / regression / deployment / observability / real usage。这比再开一个新项目更值钱。

推荐把未来 6 到 8 周的第一主线定义为：

> 让 gogo + oh-share-it 形成一个可展示的 agent context infra 试点系统。

这里不一定要把两者合并成一个 repo。更稳的是明确关系：

  • gogo 是个人本地知识工作台和展示入口；
  • oh-share-it 是多人知识治理、联邦同步、routed context 与 agent-facing tools；
  • my-little-agent-loop 只在需要掌握 agent 内核时进入，不要一开始替换所有东西；
  • clawhouse 暂时不作为求职主证据，除非它能非常直接证明 multi-device agent session / state sync。

第一轮最小成果应该包括：

1. 一个能跑的课题组试点路径。

2. 一套最小 eval/，覆盖 context retrieval、route quality、answer grounding、writeback quality。

3. tracing / logging / failure taxonomy，能展示系统如何失败。

4. 一篇 case study，记录一次真实使用如何暴露问题、如何改进。

5. README / portfolio 页面把这些证据压成岗位语言。

三、gogo 的改进方向应该收窄

你想给 gogo 做大量 context 存储、深度研究 agent、日程计划管理、生产级 context infra。方向都对，但第一轮不应全做。

更稳的优先级是：

1. **context storage / retrieval / routing 架构**

- 这是和目标岗位最贴近的核心。

- 重点不是“能存更多”，而是不同 context 层如何被选择、压缩、引用和回写。

2. **eval 与 observability**

- 这是当前公开履历最大缺口。

- 需要把 context 改造前后的质量收益做出来，而不是只写设计文档。

3. **deep research agent 机制**

- 可以作为第二阶段。

- 第一版可先做 narrow research workflow：query decomposition、source plan、evidence table、answer synthesis、writeback。

4. **日程、计划、个人工作流**

- 暂缓。

- 它们会把产品从 agent context infra 拉向个人 productivity app，容易冲散求职主线。

四、oh-share-it 应该先服务真实试点

oh-share-it 最有价值的不是再写一轮架构，而是把课题组部署跑起来。

第一版试点不需要完整平台。可以只验证两类任务：

  • 新成员能否更快获得一个方向的入口、多视角和阅读起点；
  • 导师或高年级能否更快筛选一个想法是否值得继续。

最小评测组合：

  • 15 到 20 个真实问题；
  • 每个问题记录用户场景，而不只是问题文本；
  • 评分维度只看五件事：

- 是否有依据；

- 是否有明显幻觉；

- 是否区分已知、判断、猜想；

- 是否给出下一步；

- 是否真的省时间。

这会同时补上两个缺口：真实使用与 evaluation。

五、my-little-agent-loop 的定位

my-little-agent-loop 不应被当成另一个产品主线，而应被当成你亲自主导 runtime ownership 的训练场。

最值得做深的不是“做一个完整 agent”，而是挑一块 agent harness 的关键机制做成可解释模块：

  • state machine / session policy
  • tool routing
  • task contract
  • offline replay
  • failure recovery
  • trace schema
  • evaluator loop

它的最终作用是让你能在面试和文章里说清楚：

> 我不只是把复杂度交给 Claude Code / Pi / LangChain，也自己实现并评测过 agent loop 的关键部件。

六、clawhouse 暂时放在探索轨

clawhouse 的想象力很强，但从当前求职主线看，它不应成为第一优先级。

原因是云端 agent 产品已经天然解决了跨设备接续的一部分问题。clawhouse 的独特性更偏：

  • 本地优先；
  • 透明可诊断；
  • 项目作为主语；
  • 移动端优先的 agent 工作面。

这适合作为表达 taste 和产品判断的探索项目，但短期不如 gogo / oh-share-it 能直接补 north star 缺口。

更合适的节奏是：每周留很小的固定时间做原型，不把它放进主 OKR。

七、行业学习要变成市场地图，不是无限阅读

你收藏了很多文章、视频、Superlinear 社区分析、机器之心 Pro 内容。这里最大的风险是“了解行业”变成新的无边界任务。

建议把输入改成三类产物：

1. **公司地图**

- agent infra / context infra / eval infra / coding agent / research tools 各列 10 到 20 家。

2. **岗位信号表**

- 记录 JD 反复要求什么：runtime、eval、deployment、context、observability、domain workflow。

3. **联系对象清单**

- 每家公司找 1 到 3 个可公开接触的人，记录他们关心的问题和可切入话题。

阅读材料只有在能更新这三张表时才算完成。否则它只是信息消费。

八、求职动作要和作品推进并行

不要等旗舰项目完全 production-grade 后才开始求职。更好的节奏是作品和市场同步迭代。

可采用三条并行线：

1. **每周 1 次公司研究**

- 只研究一个公司或团队；

- 输出它买什么能力、你如何对齐、缺什么证据。

2. **每周 1 次公开输出**

- 可以是短文、repo update、case study、技术笔记；

- 重点证明同一画像：context / harness / eval / reliability。

3. **每周 1 到 2 次定向连接**

- 不海投；

- 用项目、文章或具体问题开启对话。

求职不是单独阶段，而是项目验证的一部分。

九、先投还是先做项目：先做最小可投递画像，再并行校准

当前有一个具体张力：

  • 选择 1：现在简历很弱、相关履历不足，但先拿去投 agent infra 岗位，用市场反馈校准。
  • 选择 2：先做出更强的 agent infra 项目和证据，再去投 agent infra 岗位。

根据本库现有框架，两个极端都不理想。

直接大规模投递的问题是：当前画像还不够清楚，简历容易被压平成“没有相关履历、没有实习、项目不够标准”的候选人。这样的失败信号很难解释。你不知道是市场不买这个方向、简历没讲清、项目证据不够，还是投错了岗位。

但一直等项目做完再投也有问题。profile-market fit 不是闭门打造出来的。求职和产品验证一样，需要真实市场反馈。否则项目打磨容易退化成自我感觉良好的准备，等真正投出去才发现目标岗位买的不是你补的那块能力。

所以更合理的顺序不是 1 或 2，而是：

> **先做出一个最小可投递画像，再用少量高定向投递和外联校准，同时继续补项目证据。**

这里的“最小可投递画像”不是完整履历，而是一套足够让目标市场看懂你的最小信号包：

1. 一句话定位：Agent Systems Engineer，聚焦 context / harness / eval / reliability。

2. 一个主项目入口：gogo / oh-share-it / my-little-agent-loop 中最能证明主线的页面。

3. 一个可验证证据：能跑的 demo、eval 结果、trace、case study 或真实试点记录。

4. 一页简历：不追求完整，只追求所有内容服务同一个目标画像。

5. 一份目标公司清单：10 到 20 家真正买 agent infra / context infra / eval / research tools 能力的团队。

6. 一套外联话术：用项目和具体问题开启对话，而不是只问有没有岗位。

有了这套最小包，就可以开始少量投递和外联。这里的目标不是马上拿 offer，而是拿回三类反馈：

  • 市场是否看得懂你的画像；
  • 对方最关心你补哪类证据；
  • 你的项目、简历和岗位需求是否 align。

这也解释了为什么“了解市场 - 打造产品 - 利用杠杆”不是严格线性顺序。真实做法更像循环：

1. 用少量市场研究定义一个候选画像。

2. 做出最小可展示产品，也就是项目 + 简历 + portfolio。

3. 小规模推向市场。

4. 根据反馈继续改产品。

5. 再用 leverage 放大。

因此，当前不应该因为“没有任何相关履历”就完全不投，也不应该因为“了解市场很重要”就拿一份明显弱画像去乱投。更好的动作是用 1 到 2 周做出最小可投递画像，然后立刻开始小批量、高定向市场接触。

一个可执行节奏：

  • 第 1 周：把 agent infra 画像、简历、portfolio、目标公司表做成第一版。
  • 第 2 周：发 3 到 5 个定向外联，投 2 到 3 个高度匹配岗位。
  • 第 3 周：根据反馈补项目证据，优先补 eval / trace / deployment / real usage。
  • 第 4 周：再投下一小批，并写一篇 case study。

这个路径保留了选择 1 的优点：尽早接触市场。也保留了选择 2 的优点：不把明显弱信号大规模暴露给高噪音市场。

十、当前去处选择：不要为了填空窗塞进低相关位置

围绕毕业后这段时间，有三个现实选项：

1. 找导师谈，入职当正式研究助理。

2. 跟陈子深 / 郑元杰做教育、咨询、专利、创业比赛等项目。

3. 保留一段可解释的空窗期，把主时间投入 agent infra 项目、履历证据包与定向求职。

根据当前职业主线，更推荐第三个选项。

理由不是“空窗期完全没有风险”，而是风险排序不同。对你来说，第一风险不是简历上多出几个月空白，而是为了消除空白，把时间投到低相关、低兴趣、低资产沉淀的位置里，反而削弱 Agent Systems Engineer 画像。

本页前面已经定义，当前最缺的是：

  • 可部署
  • 可观测
  • 可评测
  • 被真实使用
  • 有失败驱动的迭代记录

正式研究助理只有在能直接补这些证据时才值得认真考虑。否则它更像“有个正式身份”，但未必改善 profile-market fit。如果 RA 的工作仍然主要服务原研究方向、论文收尾、导师项目或低相关执行，它会优化表面连续性，却推迟真正的求职市场验证。

陈子深 / 郑元杰项目也类似。它们可能有真实付费和服务型现金流，但主要训练的是销售、渠道、垂直咨询、政策包装和交付，不直接证明 context / harness / eval / reliability。如果只是为了“有个事做”，它们会把时间从主线里拿走。

因此更合理的判断是：

> **空窗期不是不能接受。不能接受的是空窗期没有产出、没有市场反馈、没有证据包。**

如果这段时间被组织成一个清晰的 profile-market fit sprint，它就不是消极空窗，而是主动转向。它应该产出：

1. 一个 agent context infra 旗舰项目版本。

2. 一套最小 eval / tracing / failure taxonomy / grounding。

3. 一个真实使用或试点案例。

4. 一篇可公开 case study。

5. 一版围绕 context / harness / eval / reliability 的简历和 portfolio。

6. 一张目标公司 / 岗位信号 / 联系对象地图。

7. 每周定向外联和反馈记录。

这比“简历上没有空窗”更接近本库里的求职范式：不是先把自己塞进一个岗位，而是先找到自己的 profile-market fit，再把自己组织成市场能识别、能传播、能背书的产品。

但这里有一个边界：这套判断依赖于 AI / agent infra 市场确实仍然愿意购买强作品、强项目、强方向信号，而不只是机械筛选连续工作经历。当前知识库材料支持这个假设，但没有用最新外部招聘数据验证它。若要降低风险，应该把这段空窗控制成有节奏的 6 到 8 周 sprint，并在第 2 周就开始市场接触，而不是等作品完全打磨好。

因此推荐策略是：

  • 不为了填空窗去做低相关 RA。
  • 不为了“有事做”加入不感兴趣的创业项目。
  • 把空窗命名为 Agent Systems Engineer profile-market fit sprint。
  • 用公开项目、真实试点、文章和外联，把这段时间变成可解释资产。
  • 设定复盘点：如果 6 到 8 周后没有外部反馈、没有面试线索、没有项目证据增强，再重新评估是否需要过渡性岗位。

十一、博弈论与低维结构：放进研究支线

深入学习博弈论、探索博弈数据是否存在低维结构，是值得保留的研究支线，但短期不应和 agent infra 主线争夺主资源。

它更适合承担三个作用：

  • 继续延展论文后的研究兴趣；
  • 训练形式化建模和实验能力；
  • 将来连接到 agent evaluation、multi-agent behavior、mechanism design、incentive-aware routing。

第一步不要设成“大量学习博弈论”，而应设成一个小研究问题：

> 在某一类可生成的博弈数据中，payoff / equilibrium / best-response structure 是否能被低维表示解释或预测？

如果未来能做出实验报告，它会成为 agent systems 履历里的研究能力补充，而不是主线替代品。

十二、推荐的 6 周节奏

第 1 周：收束与基线

  • 给 gogo / oh-share-it 写一页联合路线图。
  • 跑通 oh-share-it 现有测试和部署路径。
  • 定义第一版 eval task schema。
  • 列 20 家目标公司，按子市场分组。

第 2 到 3 周：真实试点

  • 在课题组选一个方向或项目作为试点。
  • 收集 15 到 20 个真实问题。
  • 建立最小 answer + grounding + writeback eval。
  • 记录失败样例。

第 4 周：runtime ownership

  • 在 my-little-agent-loop 或 oh-share-it tools 中实现一块明确的 harness 机制。
  • 优先选 trace / replay / evaluator loop。
  • 写清它和上游 agent 的边界。

第 5 周：公开证据

  • 写一篇技术长文或 case study。
  • 主题建议：Building an eval-first context layer for research agents。
  • 同步更新 README、portfolio、简历项目描述。

第 6 周：定向投递与外联

  • 选 10 个最匹配目标。
  • 每个目标写 3 行定制匹配说明。
  • 开始投递或联系，不等项目完美。
  • 用反馈决定下一轮补强是 eval、deployment、runtime 还是叙事。

压缩结论

当前最优策略不是“把所有项目都做牛逼”，而是：

> 用 gogo / oh-share-it 做一个可部署、可评测、被真实使用的 agent context infra 旗舰证据包；用 my-little-agent-loop 补 runtime ownership；把 clawhouse 保持为低成本探索；行业学习和求职围绕同一画像持续外化。

这样，项目推进、行业理解、公开表达和求职不会互相抢资源，而会共同证明同一个人：

> 一个正在把 agent context / harness / eval / reliability 从原型推向真实系统的 builder。
