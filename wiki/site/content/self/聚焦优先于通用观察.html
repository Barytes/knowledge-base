聚焦优先于通用观察

摘要

在面对"要不要支持更多场景 / 更多能力"时，倾向优先选择守住一个明确的边界并在该边界内做到好用，而不是追求更广覆盖但每个场景都半吊子。

观察证据

2026-04-23：gogo-app 是否要支持 ACP / Codex / Claude Code

看到 agent-client-protocol 后，最初产生"是不是应该把整个 gogo-app 重构成 ACP"的冲动。但经过讨论后，判断：

  • 支持更多 agent 不是 gogo-app 的核心价值
  • gogo-app 的核心是"开箱即用、本地优先、对普通用户更友好的 markdown 知识工作台"
  • ACP / Codex / Claude Code 接入是后续可选增强，不是当下产品定义
  • **结论：不做重构，先把当前版本收口**

2026-04-23：gogo-app 是否要支持任意目录

因 gogo-app 当前绑定 llm-wiki 模式（必须有 raw/wiki/inbox 目录），产生"要不要重构成支持任何目录"的疑问。

经过讨论后，判断：

  • 一旦支持任意目录，产品定义会变成通用文件浏览器 + 通用编辑器 + 通用 agent 壳
  • 这会显著扩大 scope：删掉 ingest、改文件浏览器、补更多文件类型、优化编辑体验
  • 这些改动不一定增强核心价值
  • llm-wiki 模式不是包袱，而是让知识产生复利的工作流约束
  • **结论：不改了。就这样。守住结构化 knowledge workspace 边界。**

关键共鸣时刻

讨论最后形成一句话：

> **不是做完所有功能，不是适配所有场景，而是在自己认定的那个价值点上，做到真的好用。**

这句话触发了明显的情感共鸣，说明它触及了一个稳定的个人判断偏好。

模式分析

这条观察和已有判断的关系

这条观察和仓库里已有的几条判断高度一致：

| 本条观察 | 已有判断 | 关系 |

|---------|---------|------|

| 聚焦优先于通用 | 产品判断力与能力焦虑分离 | 做不出完整系统 ≠ 没有判断力，守住边界也是一种判断力 |

| 聚焦优先于通用 | 用户自主性优先产品取舍 | 给用户清晰边界，而不是围墙花园 |

| 聚焦优先于通用 | 工作面摩擦敏感 | 消除真实摩擦，而不是增加更多功能 |

这条观察想防的失败模式

> 为了"更通用"，把产品拖向"更广覆盖，但每个场景都半吊子"。

典型症状：

  • 看到一个新协议 / 新能力，立刻产生"是不是应该重构"的冲动
  • 开始为假想用户扩 scope
  • 把核心价值稀释掉
  • 产品越做越大，越来越难收口

这条观察给出的纠偏方向

当产生"要不要支持 X"的疑问时，先问：

1. **X 是否增强核心价值？**

2. **X 是否是真实 target user 的阻塞点？**

3. **守住边界并做到好用，是否比泛化更值得做？**

如果三个答案都不明确，优先选择**先不改，先收口，先验证**。
