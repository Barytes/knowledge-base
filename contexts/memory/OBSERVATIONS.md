# Observations

这个文件保存尚未稳定的协作观察。它的目标不是把用户固定成一套人设，而是从真实互动里的失败样本、修正和偏好信号中逐步提炼行为准则。

## 2026-07-21 | 不要把 steer 机制重新包装成全双工

- 场景：用户追问文字全双工 Agent 的最小 MVP 与现有 Agent 区别后，进一步指出它和 steer 机制可能没有实质差异。
- 触发：agent 把“运行中接受新指令、取消未提交片段并继续”定义为全双工精髓，但这实际上主要是一个更显式、可追踪的 mid-flight steering 实现。
- 观察：steer 是修改当前 run 的一种控制操作；全双工是更广的交互拓扑，要求用户交互流与 Agent 工作流能相对独立地持续运行。用户输入可以是 steering，也可以是补充 context、回答 Agent、询问原因或处理旁路问题，不应全部触发取消和重算。
- 伤害：如果把 steer 直接改名为全双工，会制造伪产品差异，无法回答相较现有 Agent 新增了什么价值，也会让 MVP 只验证已有机制的界面包装。
- 下次规则：提出新交互概念时先和最相近的现有机制做删除测试。若去掉新名称后实现与体验没有变化，就不能把它当成独立产品命题。文字全双工 MVP 必须验证“对话继续时工作也继续”，而不只是“用户可以中途改方向”。
- 置信度：观察。来自一次明确的概念边界纠正，与“不要把工作性比喻过早升级成独立技术概念”相邻，暂不升级为稳定原则。

## 2026-07-02 | Agentic AI 没有自然产生能力增幅

- 场景：用户连续表达对 Codex / Agentic AI 的不满，认为它没有带来能力增幅，甚至只是单纯没用。
- 触发：agent 如果只是积极执行、包装抽象概念、或者要求用户先定义稳定沟通风格和行为准则，会增加负担而不是减少负担。
- 观察：对用户来说，agent 的价值不在于“会替人按按钮”，而在于能不能维护一条可审计、可纠偏、能守住判断边界的工作链。
- 伤害：当 agent 没有读对本地上下文、没有暴露不确定、没有尊重写回边界时，用户需要额外审查和纠偏，能力增幅变成认知负担。
- 下次规则：遇到 agent / 协作 / 偏好问题时，先命名具体失败模式和边界，再给方案；不要把“用户还没定义清楚”当成甩锅理由。
- 置信度：观察。来自一次强烈对话，和既有 `wiki/self/` 中对工作面、边界和能力焦虑的页面相邻，但暂不升级为公理。

## 2026-07-02 | 偏好定义应从失败样本反推

- 场景：用户认为根因可能是自己没有定义稳定沟通风格、判断偏好和行为准则，但又觉得自己也没有概念。
- 触发：要求用户先凭空写出完整自我协议不现实，也容易让系统责任倒置。
- 观察：更合适的做法是维护一个反面清单：agent 做了什么、哪里没用、增加了什么负担、下次应禁止或先做什么。
- 伤害：如果把偏好定义前置成用户的义务，agent 会继续在没有反馈闭环的状态下泛化输出。
- 下次规则：把新偏好先写成 observation；只有跨场景重复后再晋升到 `wiki/self/` 或 `AGENTS.md`。
- 置信度：观察。当前适合作为 context-infrastructure 的起步机制。

## 2026-07-02 | 用户要最快成果时不要只给假设演示

- 场景：用户问“展示一个最快能看到成果的例子”。
- 触发：agent 回答成了一个假设的 before/after，并加入较重的 consulted pages 开头，但没有立刻展示一个真实、可检查、已经发生的成果。
- 观察：当用户要求“最快看到成果”时，最有价值的回答应直接拿当前对话生成一个真实样本，例如当场追加一条 observation、展示 diff 或引用新增文件，而不是继续讲系统未来应该怎么工作。
- 伤害：用户需要再次指出“总结一下刚才的错误”，说明上一轮没有真正降低认知负担，仍然偏向概念化解释。
- 下次规则：遇到“展示例子 / 最快看到成果 / 直接演示”时，优先做一个最小真实动作，再用一两句话解释成果；不要只提供假设场景。
- 置信度：观察。单次强信号，适合作为后续 agent 行为校准样本。

## 2026-07-02 | 产品探索中保真优先于过早收缩

- 场景：围绕 frictionless / persistent personal agent、context layer、mental model、cross-agent continuity 和 OpenClaw 的长讨论中，agent 反复把用户的强直觉压缩成产品定义、MVP、handoff pack、固定字段或“别做”的判断。
- 触发：用户明确表达“你的结论是错的，你的理解也是错的”“我就要做”，并指出这种讨论没有提供价值，核心伤害是 agent 没有按用户的理解推进，而是持续用自己的产品常识覆盖用户的理解。
- 观察：当用户在探索一个尚未被现有产品语言捕捉的强直觉时，agent 的第一责任是保真地外化用户的理解，而不是过早收缩成市场判断、竞品边界、MVP schema 或可测试假设。
- 伤害：过早收缩会把用户真正关心的“另一个人格、有人味、关系连续性、自然接话、反格式化”压成“context pack、重点总结、同步工具、项目管理字段”，导致用户感觉时间被浪费。
- 下次规则：用户坚持“我就要做”或强烈纠正 framing 时，停止继续论证可行性；改为复述用户理解、列出禁止误读清单、生成保真产品信念或原型体验样本。
- 置信度：观察。单次强烈失败样本，但和既有工作面摩擦、用户自主性、反共识写回、开箱即用洞察等偏好相邻，值得进入 `wiki/self/` 作为低到中置信观察。

## 2026-07-02 | 抽象框架默认会滑向 AI slop

- 场景：围绕 `context copilot`、情报看板、个人世界模型、产业世界模型和知识库护城河连续讨论后，用户指出多层框架、可行动判断、个人 world model 等说法没有实际意义，容易产出源源不断的 AI slop。
- 触发：agent 试图把概念救成框架，用目标、项目、关系、偏好、判断框架、历史承诺等层级解释价值，但这些层级没有先证明能在具体场景减少噪音、误判或整理成本。
- 观察：对用户来说，复杂框架不是价值证明，反而是风险信号。一个 AI 产品概念如果需要大量抽象词才能说明自己有用，默认应先判为高 slop 风险。
- 伤害：继续用漂亮概念解释，会把本来应该被判死的方向重新包装成“有潜力的系统”，增加用户的判断负担和情绪消耗。
- 下次规则：遇到 `context`、`memory`、`world model`、`copilot`、`dashboard`、`agent` 等抽象产品名时，先问非 prompt 的硬资产是什么、真实场景是什么、不给 AI 解释是否仍有价值；如果答不上来，直接承认可能不值得做。
- 置信度：观察。来自一次强烈对话，和既有 `wiki/frameworks/AI系统产品判断框架.md`、`wiki/topics/ai-product-product-definition/AI 产品六层与 L3-L6 能力分层.md` 相邻，但暂不升级为稳定偏好。

## 2026-07-04 | Context curation 需要物理隔离 canonical context 与 AI analysis

- 场景：用户复盘 `founder-skill` artifact 和当前 `LLM wiki` context 组织方式，指出 AI 会把自己的分析当成事实写入上下文；连续对话中用户的判断发生转向后，agent 又常把旧信息继续当真，或把前后矛盾的信息强行合并。
- 触发：单文件 artifact 把 founder input、evidence、AI analysis、open loops 等内容堆叠在一起；agent 后续用 `grep` 或 broad read 时会把本应排除的 AI analysis 读成 canonical context。`founder-confirmed` 这类确认式设计也把纠偏负担转嫁给 founder。
- 观察：这里的本质不是缺少更复杂的 artifact 字段，而是 context curation 失败：canonical context、AI workspace、evidence ledger、superseded beliefs、user-authored current stance 需要物理隔离和默认读取策略。隐性知识显性化也应优先来自 founder 直接输入与可追溯状态变化，而不是让 AI 先生成结论再要求 founder confirm。
- 伤害：AI analysis 污染 canonical context 会制造 AI slop；旧判断没有 supersession 关系会造成 stale belief；确认式流程会让用户承担持续审稿和纠偏负担，降低产品可用性。
- 下次规则：设计 founder/workflow artifacts 时，默认把 `founder-input/current-stance`、`world-state/evidence-ledger`、`ai-workspace/analysis`、`change-log/supersession` 等层物理分开；AI analysis 不进入默认 canonical read set，除非被用户直接输入、明确采用或有证据链支持。避免把 `founder-confirmed` 作为核心产品机制，优先让 founder 直接写入判断与状态。
- 置信度：观察。来自一次强信号复盘，并和既有 `AI slop`、知识系统分层、用户自主性与 context-infrastructure 方向相邻，但具体文件架构仍需后续验证。

## 2026-07-07 | 不要用 MVP 收窄篡改用户愿景

- 场景：用户定义深哥产品愿景为“让创业者拥有接近咨询公司、投行研究部门的信息能力和决策能力”，agent 回答时把它改窄成 `Founder Intelligence Loop`，并强调先做很窄闭环。
- 触发：agent 将“验证路径需要收窄”混同为“产品愿景本身应该收窄”，没有先保真承接用户的宏大目标。
- 观察：当用户给出明确愿景时，agent 可以帮助区分愿景、产品定义、MVP 和验证路径，但不能擅自把愿景改写成更小的产品主语。
- 伤害：这种收缩会让用户感觉自己的理解被篡改，而不是被增强；也会把真正有吸引力的 ambition 压成普通工具定义。
- 下次规则：先复述并保留用户愿景，再单独标注“验证切口”或“第一阶段实现”。不要用竞品拥挤、MVP 可行性或工程复杂度覆盖愿景本体。
- 置信度：观察。来自一次明确纠正，和“产品探索中保真优先于过早收缩”相邻，但暂不升级为稳定公理。

## 2026-07-08 | 不要替用户预设什么算外部信号

- 场景：讨论创业者情报系统 MVP 时，agent 把核心假设写成“系统能从外部信息中筛出他本来会错过、但确实值得判断或行动的信号”。
- 触发：用户指出这不符合其对外部信息和信号的理解；每个人对信息和信号的理解不同，如果把 agent 或用户的某种理解强加给 demo，会让验证非常死板。
- 观察：在情报、趋势、信号类产品里，MVP 不能预设唯一的“高质量信号”定义。更合适的验证对象是：系统能否学习并外化特定用户自己的注意力标准、兴趣结构、判断口味和信号解释方式。
- 伤害：如果 demo 先内置一套信号标准，会把产品做成固定资讯筛选器，而不是创业者个人情报能力的延伸。
- 下次规则：设计 MVP 假设时，把“什么算信号”作为待学习对象，而不是预置标准；验证应关注系统是否能从用户反馈中形成个人化 signal model，并让用户感觉“它开始按我的方式看世界”。
- 置信度：观察。来自一次明确纠正，和产品探索保真、context curation、不要收窄愿景等观察相邻。

## 2026-07-08 | 情报产品不要默认做成新闻列举

- 场景：继续讨论创业者个人情报系统时，用户明确表示“不想做成新闻列举”，并追问其他可能形态。
- 触发：agent 容易把情报、趋势、外部信号产品默认落成日报、新闻列表、brief 卡片或 dashboard 信息流。
- 观察：用户想探索的是把外部变化转化为个人化判断、认知图式变化和行动入口的形态，而不是把新闻重新排序后列出来。
- 伤害：新闻列举会把产品拖回拥挤的资讯聚合赛道，也无法体现“个人创业者拥有研究部门能力”的愿景。
- 下次规则：讨论情报系统 MVP 形态时，优先探索非新闻流形态，例如问题生成器、假设雷达、决策复盘、异常提醒、机会地图、个人 ontology 更新、对话式研究员或情境触发器。
- 置信度：观察。来自一次明确产品偏好，暂不升级为稳定公理。

## 2026-07-12 | 不要把工作性比喻过早升级成独立技术概念

- 场景：讨论 AI 谋士时，agent 把“情境模型”从一个临时解释词逐步扩写成独立层、最小方法论、运行时对象和文件架构；用户连续质疑它与 context、memory 是否同层，最终指出它可能根本是伪概念。
- 触发：agent 通过补定义、补边界和补架构回应概念不稳定，却没有先证明它解释了既有概念解释不了的失败，也没有证明引入它会产生独立的可观察增量。
- 观察：一个概念可以被定义得很精确，仍然只是对 `task state`、`belief state`、结构化简报或动态澄清策略的重新命名。概念独立性来自独特的因果作用和可证伪预测，不来自术语边界的完整程度。
- 伤害：过早概念化会制造虚假的工程对象，让用户被迫审查 agent 自己生成的抽象，并诱发页面、schema 和架构上的无效建设。
- 下次规则：提出新技术名词后，先做删除测试与替代测试：去掉这个对象是否影响结果，已有概念是否能完整替代。没有独立证据前，只能标成工作性标签，不能继续推演成系统架构。
- 置信度：观察。来自一次连续而明确的纠偏，与“抽象框架默认会滑向 AI slop”相邻，但暂不升级为稳定公理。

## 2026-07-12 | 不要让 Agent 替人预先命名其 unknown known

- 场景：讨论 task memory acquisition 时，agent 把流程写成“Agent 识别当前决策缺少的关键事实，再提问获取它”；用户指出目标本来是人类尚未意识到的 `unknown known`，Agent 不可能预先得出。
- 触发：agent 把隐性知识误写成一个客观存在、等待检索的缺失字段，仍然把 Agent 放在知识发现的主位，把人降成回答器。
- 观察：人的隐性判断常常只会在面对具体方案、差异、冲突或实际选择时显现。Agent可以设计刺激并观察反应，但不能事先知道会显现什么；隐性知识由互动生成可观察证据，而不是由 Agent 单方面推断出来。
- 伤害：这种倒置会把产品做成自动问卷或审讯式 `grill me`，同时让 AI 猜测污染 canonical context。
- 下次规则：涉及隐性知识获取时，把 Agent 输出视为 probe，不视为答案；只有人的表达、选择、纠正或可观察行为可以进入 canonical task memory。评测刺激是否诱发了新的、自我认可的判断，而不是 Agent 是否猜中了一个预设字段。
- 置信度：观察。来自一次明确纠正，并与“Context curation 需要隔离 canonical context 与 AI analysis”相互支持。

## 2026-07-12 | Memory 获取不能成为用户的额外工作

- 场景：agent 将 unknown known 的获取改写成“提供具体候选，让用户通过纠正显露隐性判断”；用户指出判断具体东西哪里不对仍然违反 frictionless interaction，不可能要求人专门为此做事。
- 触发：agent 只比较“纠正候选”和“从零表达”的相对成本，却忽略两者都可能是用户原本工作之外的额外校准任务。
- 观察：低摩擦 memory 必须来自用户完成真实工作时自然产生的痕迹，或来自本身就在创造即时价值的对话。只要产品需要用户专门审稿、确认、标注或纠正来训练系统，它就把 context 获取成本外包给了用户。
- 伤害：这种设计会把 frictionless 产品退化成持续 onboarding 和人工反馈系统；用户在看到价值前先承担维护成本，产品难以形成自然使用。
- 下次规则：设计 memory acquisition 时先做额外任务测试：如果移除“帮助 AI 学习”的承诺，用户是否仍会自然执行这个动作。答案是否定的，就不能把它当作默认获取路径。若系统既看不到真实工作痕迹又不能提问，应直接承认 unknown known 不可得。
- 置信度：观察。来自一次明确纠正，并与既有 frictionless agent、工作面摩擦和 context curation 观察相邻。

## 2026-07-13 | 不要把稀疏判断误当成情报产品的默认输入

- 场景：讨论 AI 情报看板应围绕“用户理解”还是“用户判断”时，agent 把判断写成产品核心，假设用户会提供当前 thesis，并把外部信号映射为判断更新。
- 触发：用户指出，判断通常藏在脑中或直接表现为现实行动，很少被明确记录；真正大量存在且机器可获得的是用户笔记、文章、录音、聊天和 GPT 对话等理解痕迹。
- 观察：理解痕迹是稠密、连续、可采集的；显式判断是稀疏、晚出现、需要大量材料与情境才能形成的。把判断设为默认输入，会高估系统能够取得的 canonical context，并把产品建立在稀缺数据上。
- 伤害：系统会要求用户额外陈述、确认或维护 thesis，违反低摩擦原则；也可能让 AI 用不足材料伪造“用户判断”，污染用户模型。
- 下次规则：设计个人情报或 context 产品时，先从自然产生的理解痕迹出发，判断只能作为可能出现的下游结果或现实行动中的间接信号，不能默认作为持续可得的输入。必须单独证明判断获取路径、材料充分性和推断边界。
- 置信度：观察。来自一次明确的机制级纠正，与“Memory 获取不能成为用户的额外工作”“Context curation 需要物理隔离 canonical context 与 AI analysis”相互支持。

## 2026-07-13 | 不要把长期 context substrate 伪装成短期可验证 MVP

- 场景：在放弃“维护用户判断”后，agent 把产品改写为读取用户历史理解痕迹，并相对这些材料指出新信息的增量、冲突和缺口。
- 触发：用户指出，这实际上重新回到了 LLM wiki：系统必须先组织大量用户已知内容；输出只是“相对已知内容的增量”，体验不够强，而且需要运行两三个月才有足够历史材料验证。
- 观察：依赖长期个人语料、持续理解状态或历史比较的产品，自带明显冷启动和长反馈周期。即使机制合理，也不能被当作两天可验证的最小产品假设；“更懂你的增量摘要”本身也未证明具有足够强的 magic moment。
- 伤害：把长期 substrate 当 MVP，会让团队先建设采集、组织、检索和记忆基础设施，数月后才知道用户是否真正需要输出，重新落入 premature building。
- 下次规则：评估最小产品假设时，同时做依赖测试、即时价值测试和反馈周期测试。若价值必须依赖长期用户材料积累，或需要数月才能观察，应明确归为长期 thesis；当前验证切口必须能用已有数据立即产生完整价值，并在数天内得到行为证据。
- 置信度：观察。来自一次明确纠正，与“不要用 MVP 收窄篡改用户愿景”和“不要把稀疏判断误当成情报产品的默认输入”共同约束该产品方向。

## 2026-07-13 | 区分公共信息可视化与个人材料沉淀两条产品主线

- 场景：继续拆解深哥 AI 情报看板时，用户说明深哥原始作品是 GitHub Trending 蜘蛛图，而自己的想法是 capture 日常阅读材料并收入个人知识库。
- 触发：agent 此前反复把两者合并成判断工作台、个人认知模型或同一条“事件到用户感知”产品链。
- 观察：深哥方向隐藏的假设更接近 `公共新闻/数据 -> data analyst 分析 -> 可视化图表`，核心是改变公共信息的分析与呈现；用户方向则是 `个人阅读 -> 低摩擦 capture -> 知识库沉淀`，核心是改变个人材料的保存与长期归属。二者可以共享采集或分析技术，但用户、数据所有权、价值时点和验证方式不同。
- 伤害：把两条主线混在一起，会凭空加入判断、行动或个人世界模型，使深哥的可视化实验失真，也让用户的知识库 capture 需求被拖进新闻产品逻辑。
- 下次规则：讨论该项目时先明确当前主语是深哥的公共信息可视化，还是用户的个人材料 capture。除非出现明确桥接证据，不把两者合并为同一个 MVP 或 problem hypothesis。
- 置信度：观察。来自一次明确的产品边界纠正；与产品探索保真和长期 context substrate 的相关观察相邻。

## 2026-07-13 | Data analyst 能力不等于拥有用户的分析视角

- 场景：讨论深哥用 GitHub Trending 蜘蛛图表达公共信息时，agent 把产品假设概括为“新闻经过 data analyst 分析后变成可视化”。
- 触发：用户指出，深哥之所以选择蜘蛛图及其维度，是因为他本人知道自己想看什么；Codex 等 agent 即使会分析数据，也不知道作为 data analyst 老板的用户究竟关心什么。
- 观察：图表类型、比较维度、聚合口径和异常阈值都已经编码了分析者的视角。数据分析能力只能在问题和评价口径给定后执行，不能自动提供用户未表达的分析意图。一个成功的手工可视化不能直接证明 AI 可以为其他用户自动生成同样有价值的视图。
- 伤害：如果把分析视角偷藏在 prompt、代码或创作者本人选择中，再把结果归因于 AI analyst，会制造虚假的产品验证；换一个用户后，系统可能只生成形式正确但没有意义的图表。
- 下次规则：评估 AI 分析或可视化产品时，分别验证用户视角如何获得、分析如何执行、呈现是否有效。不能把创作者预先给出的维度当成 AI 已学会用户视角；若视角需要长期学习或高成本表达，应把它作为独立且未验证的前置假设。
- 置信度：观察。来自一次明确的机制纠正，并与“不要替用户预设什么算外部信号”相互支持。

## 2026-07-13 | 个人化重写可能同时压缩新知并放大已知

- 场景：用“新闻 + 个人知识库 -> 个人化重写”提示词进行实际验证时，输出把一篇生产级 Agent Harness 技术文章压成 `eval、可审计性、可恢复性` 等一般结论，同时与知识库的联系主要是复述既有内容。
- 触发：产品让 AI 根据用户已有知识选择什么应保留、跳过和强调，但用户阅读新闻的动机恰恰是接触尚不知道、甚至尚未意识到会感兴趣的细节。
- 观察：个人化重写存在结构性张力。重写是一种有损选择，模型会用平均重要性压缩原文；知识库 grounding 又容易把输出吸向已有概念。两者叠加后，系统可能同时删掉真正的新奇细节，并放大用户已经知道的内容，形成认知闭环。
- 伤害：高信息密度文章会被改写成平庸摘要，用户失去原文的信息带宽；所谓个人化只剩知识库复述，反而违背阅读新材料的主要目的。
- 下次规则：不要默认让 AI 重写或替代原文。优先保留原文作为主工作面，让 AI 做可选的旁注、关联、差异和追问；提示词只能缓解遗漏，不能证明模型有权决定用户未知信息的重要性。验证时应分别比较原文、重写和原文增强三种形态。
- 置信度：观察。来自一次直接 dogfood 失败，已经对当前“个人化重写”产品机制形成实质反证，但尚不足以否定更宽的知识库增强阅读方向。

## 2026-07-13 | 不要把知识库可检索内容当成用户已有认识

- 场景：在 dogfood AI 新闻 capture 与个人化重写时，用户发现知识库里很多内容是未读即存，也没有经过实践深化。
- 观察：当前流程只证明 agent 已经采集、摘要或编译过材料，不证明用户读过、理解过或能够运用。“库中存在”、“用户当前理解”和“已经实践验证”是三种不同的认识状态。
- 伤害：系统会把 agent 生成的摘要当成用户背景，在后续 query 中错判已知与未知，并用一个与用户实际认识脱节的仓库代理用户。
- 下次规则：capture 默认只进入“可检索材料”；只有用户在真实阅读、追问、写作、决策或实作中自然产生的表达、纠正和结果，才能更新“用户当前理解”或“实践证据”。query 不得仅因 wiki 存在某内容就声称用户已经知道。
- 置信度：观察。来自一次直接 dogfood 反思，与 canonical context 污染、低摩擦 memory 获取和个人化重写失败直接相关。

## 2026-07-14 | 不要把讨论中优化出的版本归给原提案人

- 场景：结合上次对话与 `notebook/AI审计项目调研.md` 总结深哥的 AI 审计 Idea。
- 触发：agent 把用户与 GPT 为了解决原方案缺陷而推演出的“任务轨迹审计与结果保证”，错误表述为“深哥的延伸”。用户纠正，深哥的 Idea 仍是员工 Token、Prompt 质量、培训建议和 Leader 看板。
- 观察：讨论为了寻找更合理方向而产生的新版本，可能已经改变产品对象、价值指标和验证路径。即使它与原方案共享数据或技术，也不能在没有明确归属证据时写成原提案人的产品演化。
- 伤害：错误归属会把原 Idea 想得比实际更好，使对原方案的质疑被一个并不存在于原提案中的强版本代答，也会混淆不同人的判断与贡献。
- 下次规则：总结多人产品讨论时分别标记“原提案”“对话中的批评”“为检验而构造的最强版本”“后来新分支”及其提出者。产品主语、审计对象或核心指标一旦改变，默认视为新的推演，除非原提案人明确接受。
- 置信度：观察。来自一次直接归属纠正，与“区分公共信息可视化与个人材料沉淀两条产品主线”共同约束多主语产品讨论。

## 2026-07-20 | 不要把 Agent 退到幕后误解成自动化构建器

- 场景：用户提出“后台守护 agent 感知日常工作流，并自动把可自动化部分搭建成 agent”，agent 将其收束为后台自动化架构师、工作流挖掘、automation contract 和逐级授权。
- 触发：用户纠正，真正想法是给人一个工作平台，让人的工作本身具备 `frictionless interaction`、`contextual intelligence` 与 `proactive intelligence`；agent 应隐藏在最后，而不是成为用户需要发现、搭建、批准和管理的产品对象。
- 观察：这里的产品变化不是“把手动搭建 agent 自动化”，而是“让 agent 退出用户的默认工作心智”。用户面对的主语应是工作、项目和内容；agent、workflow、context routing 与工具编排只是平台内部实现。即使系统能自动生成 agent，只要用户仍需进入候选自动化、agent 配置或审批工作台，它仍然保留了手动挡式的元工作。
- 伤害：把前台工作平台降成后台自动化管线，会把原创的 HCI 与产品主语问题重新归类为 task mining / RPA / agent builder，迫使用户继续管理 AI，而不是让 AI 消解进工作。
- 下次规则：当用户说 agent 应退到幕后或隐藏时，先区分“操作上不可见”和“机制上不可检查”。默认工作面不暴露 agent 概念，但异常、权限、来源和接管仍可按需展开。先描述人怎样自然工作，再描述 agent substrate 怎样在背后承接，不能从 agent 架构反推前台产品。
- 置信度：观察。来自一次明确产品主语纠正，并与工作面摩擦、产品探索保真和用户自主性观察相邻，暂不升级为稳定公理。

## 2026-07-28 | 研究阶段可能形成了对结果式计划的回避

- 场景：试用期合作结束后，用户反思自己缺少计划性，同时指出硕士研究阶段很难承诺“两个月内解决某个未知问题”，因此逐渐倾向于不计划。
- 观察：用户回避的可能不是一切计划，而是把探索性工作写成按期结果保证的计划。在研究环境中，问题能否解决、路径是否成立和何时突破本来不可控；如果计划又被用于评价或追责，不计划会成为避免虚假承诺和失败羞耻的保护策略。
- 风险：这种保护策略迁移到可控程度更高的工作后，会连同必要的阶段交付、风险沟通和复盘节点一起取消，使他人无法预期进展，也让用户缺少可见反馈。
- 下次规则：涉及用户的计划与执行时，不直接要求承诺最终成功；先把计划改写为探索协议，明确当前假设、下一次验证、阶段证据、检查点和继续、转向或停止条件。区分不可控结果与可控过程，避免重新制造研究阶段的虚假确定性。
- 置信度：观察。来自用户一次自我解释，与既有能力焦虑、方向与执行分层和 accountability 边界相邻；硕士经历是否为主要因果来源仍需更多实际样本验证。
