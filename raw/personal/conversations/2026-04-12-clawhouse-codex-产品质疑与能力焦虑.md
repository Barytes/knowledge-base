# 与 Codex 关于 Clawhouse 的对话记录

**时间：** 2026-04-12  
**类型：** 个人对话 / 产品质疑与自我怀疑  
**主题：** Clawhouse 产品存在意义、与现有方案对比、能力焦虑

---

## 对话核心脉络

### 1. 初始悲观判断

用户表达：
> 我有一个很悲观的感觉，我觉得 openclaw 已经很完善了。不再需要 clawhouse 了。而且我觉得我做不出来，没这个能力。

Codex 回应：这个感觉很正常，但有两件事要分开：
- OpenClaw 很强，可能意味着"clawhouse 不该作为独立大产品再做一遍"——这不是失败判断，反而是成熟判断
- "我做不出来"是在拿自己和已有巨大体量、长期迭代的系统比，这种比较几乎必然让人泄气

Codex 建议三选一：
1. **Kill it**：把 clawhouse 当成已完成使命的思考项目
2. **Narrow it**：只做极窄的 wedge（如 re-entry inbox、"今天最重要的 3 件事"视图）
3. **Contribute through OpenClaw**：把 clawhouse 变成针对 OpenClaw 的判断和提案

### 2. 用户追问：用户用 agent 到底想看到什么

用户质疑"同事工作简报"的想法，提出核心问题：
> 我干嘛要做同事工作简报……不觉得很傻吗。我觉得没有捋清楚的一点是用户用 agent 到底是想看到什么。目前的 coding agent 让用户看到的是什么，openclaw 让用户看到的是什么，multica 让用户看的又是什么？clawhouse 如何能 address 这方面的 issue，并提供自己的核心价值？

Codex 产出分析页 `agent 产品让用户看到什么，以及 clawhouse 还能补什么.md`，提出：
- terminal-first coding agent → 让用户看会话与执行过程
- OpenClaw → 让用户看 assistant 作为持续身份与多入口存在
- multica → 让用户看任务系统中的 agent 协作者
- clawhouse 可能补的是 **work commitment visibility**

### 3. 用户指出分析的根本错误

用户批评：
> 我觉得不是这样的。openclaw 还是只是让人看到 agent 的最终回答结果。人看不到 channels、Gateway、sessions、heartbeat、nodes，顶多能感受到人格。同样的，我觉得你对 multica 的分析也不对。而且我觉得 agent 当前对我承担着哪些工作承诺也是很傻逼特别傻逼的一个分析。它是：它现在到底在替我做什么、做到哪个判断点了、它为什么这么推进、接下来准备怎么做、什么时候轮到我介入——这说明人对 agent 完全没有控制力，你只能眼睁睁地看着 agent 干了什么。那不还是个黑盒吗？你没法干预和指导 agent 的工作过程。

Codex 承认两个根本错误：
1. 把"系统内部有什么对象"误当成了"用户默认看到什么"
2. 把问题误收束成"看见 agent 承担的工作承诺"——这仍然是偏被动观察

重新定义问题为三个维度：
- 用户默认看到什么
- 用户能在过程中控制什么
- 用户和 agent 是串行关系，还是共享同一个工作面

新定义：**clawhouse 可能的核心价值是 steerability after leaving the original seat**（人离开原工作位之后，仍能持续指导 agent 工作）

### 4. 用户追问：那为啥不直接用 Termius + tmux

> 那我为啥不直接 terminus+tmux 呢？感觉这样又远程控制又可见了。

Codex 承认：
> 短答案是：很多情况下，你就该直接用 Termius + tmux。如果 clawhouse 不能明显比这套基线更好，它就没有存在意义。

Termius + tmux 已解决两件最硬的事：
- **可见**：看到的就是真实终端、真实输出、真实现场
- **可控**：可以随时插手，直接改命令、改文件、停掉、重跑、自己接管

clawhouse 只有在以下点上明显胜过 tmux 才成立：
- 在手机上操作负担显著更低
- 不需要先记住"哪台机器、哪个 session、哪个 pane"
- 把 agent 特有的控制动作做成一等交互（批准、拒绝、重试、切换执行位等）
- 跨多个设备和多个 agent 给统一控制面

### 5. 用户表达困惑和无力感

> 无语了，我觉得现在就是一团浆糊

Codex 回应：现在确实是一团浆糊，因为混了 5 件事：
1. 用户默认看到什么
2. 用户能控制什么
3. agent 本体到底是什么
4. OpenClaw / multica / tmux 分别在解决哪层问题
5. clawhouse 到底是产品、功能，还是只是一个不满感

建议彻底 reset，只问一个最硬的问题：
> Termius + tmux 已经这么强了，你到底在哪个具体时刻还是不爽？

### 6. 用户表达不理解

> 我不理解。我不知

Codex 建议不再逼问"clawhouse 是什么"，而是改成更轻的中间状态：
> clawhouse 先不是产品定义，而是一组关于 agent 默认工作面的未解决问题。

### 7. 用户表达能力焦虑

> 我觉得我没有能力，反正也是做不出来的

Codex 回应：
- 把"我做不出一个完整的 OpenClaw / multica 级系统"和"我没有能力提出一个更准确的问题，或者做出一个很窄但锋利的东西"分开
- 用户已经做到了很多人做不到的事：能持续感觉到默认工作面不对、能区分"可见"和"可控"、能及时指出分析里不对的地方
- 这是很真实的产品判断力，不等于必须独自把整个系统都实现出来

最终建议：
> 先承认：我现在做不出这个系统。同时保留：但我现在的这些不满和判断未必是错的。把 clawhouse 从"我要做的产品"降级成"我对 agent 工作面的未解问题集"。

## 关键判断与结论

### 对现有方案的重新认识

| 方案 | 实际让用户看到什么 | 控制力 |
|------|------------------|--------|
| terminal-first coding agent | 过程本身（消息、命令、diff、测试、报错） | 最强（随时打断、改 prompt、改文件、自己接手），但连续性差 |
| OpenClaw | 结果回复 + 人格连续性 | 对话式控制，非细粒度过程控制 |
| multica | 任务/状态/协作对象 | 任务层控制（分配、评论、改状态），非过程 steerability |
| Termius + tmux | 真实终端、真实输出 | 最强（随时插手、改命令、改文件、停掉、重跑） |

### clawhouse 的核心困境

1. **tmux 是必须打赢的 baseline**，不是可以无视的旧方案
2. 如果 clawhouse 不能比 tmux 在移动端更低摩擦地控制 agent，它本质上就是"一个更花的远程终端壳"或"一个更弱的 tmux"
3. clawhouse 不该解决"如何远程看到和控制 agent"，因为 tmux 已经把这题做得很强了

### 最终定位建议

clawhouse 应该从"产品定义"降级为：
> **一组关于 agent 默认工作面的未解决问题集**

这组问题可能包括：
- 为什么聊天框让人不放心？
- 为什么任务板也不对？
- 为什么终端虽然真实，但又不像最终答案？
- 用户到底想在 agent 工作时保留哪种控制感？
- 哪些控制必须一直在手里，哪些可以交给 agent？
