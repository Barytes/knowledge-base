**各自的方法**

llm-wiki.md (line 17) 的方法，是把本地知识库做成一个由 LLM 持续维护的 wiki。它主张把系统分成三层：原始资料 raw sources (line 35)、LLM 生成并维护的 wiki 页面 (line 41)、以及规定结构和流程的 schema/AGENTS.md (line 43)。核心流程是三步：ingest (line 45) 时把新资料读入并改写到多个主题页里，query (line 49) 时优先查 wiki 而不是临时从原始文档里现拼，lint (line 51) 时定期检查矛盾、孤儿页、缺失链接等。它强调知识库是一个“持续累积的外部产物”，重点是结构化、交叉链接、可维护。

为什么AI只会说正确的废话，以及怎么把它逼出舒适区.md (line 48) 的方法，则是把“你怎么想”沉淀成 AI 的上下文基础设施。它的三步是：大量积累 (line 52)，把录音、聊天、会议、纠错等真实行为都存成本地文件；分层提炼 (line 62)，用 L1/L2/L3 从观察一路蒸馏到稳定的 axiom；按需加载 (line 74)，针对不同任务加载不同 skill 和原则。它强调的不是“资料怎么组织”，而是“如何把人的非共识判断力注入 AI”。

**相同点**

两者都反对一次性、临时性的 RAG/对话式使用，强调“知识要持续积累，而不是每次重算”。  
两者都把 LLM 视为维护者，而不是单纯问答机。  
两者都依赖本地文件系统和明确结构，让知识能被持续更新、交叉引用、循环生长。

**不同点**

最大的不同是对象不同。  
llm-wiki (line 21) 管的是“外部世界的资料与主题知识”，目标是形成一套可浏览、可引用、可审计的外部 wiki。  
context-infrastructure 这篇 (line 72) 管的是“你自己的判断方式”，目标是让 AI 不只会总结事实，还能带着你的立场做分析。

理念上也不同。  
llm-wiki 追求的是“知识编译”和“文档维护效率”；  
另一篇追求的是“突破 consensus”，让 AI 从正确但平庸，变成有判断力。前者更偏知识工程，后者更偏认知工程。

如果压缩成一句话：  
llm-wiki 是把“你知道什么”整理成外部知识库；另一篇是把“你怎么判断”蒸馏成 AI 可调用的内部上下文。最强的组合方式，其实是前者做资料层，后者做认知层。

所以前者的处理对象（本地维护的文件）是外部的知识，只不过用LLM作为外部知识的“代理”，人不再直接阅读外部知识本身了，而是跟LLM对话获得相应的知识。听起来更客观，面对的是“科学知识”。而后者的处理对象是人真实生活中的各种context，把这些context注入给LLM之后，LLM就会得到和用户一致的判断力。

对，基本可以这么理解，不过我会补两点细化，避免把两者分得过于绝对。

前者确实更偏“外部知识代理”。它处理的主要是外部材料，比如文章、论文、报告、书、会议记录等，然后让 LLM 把这些材料整理成一个持续演化的 wiki。用户以后不必每次都亲自重读原文，而是更多通过和 LLM 对话、查看 wiki 页面来获取知识。这一套更接近“知识编译器”或“知识中间层”。所以你说它更客观、更多面向“科学知识”，这个方向是对的。

但要注意，前者也不等于纯客观。因为它不是机械摘要，而是会做取舍、整合、链接、标注冲突、形成 synthesis。只要有 synthesis，就已经带入某种视角了，只是这个视角主要受“资料本身”和“wiki 结构规则”约束，而不是受“某个人的长期判断偏好”主导。

后者则确实更偏“认知注入”。它的重点不是让 LLM 更完整地知道世界，而是让 LLM 更贴近“你会怎么判断世界”。它收集的是你真实生活和工作中的行为痕迹，再从中蒸馏出稳定的判断原则、偏好、权衡方式，然后按任务类型加载给 LLM。这样出来的结果，不只是“知道相关事实”，而是“会按你的脑回路去分析”。所以你说“LLM 会得到和用户一致的判断力”，这个表达大体成立，不过更准确地说是：它会更接近用户稳定的判断风格，而不是真的完全等同于用户本人。

如果用一句话区分：

前者在解决“知识从哪来、怎么组织、怎么维护”。  
后者在解决“同样的知识，应该按什么立场和判断框架去理解”。

所以前者更像外部知识层，后者更像认知操作系统层。两者并不冲突，反而很适合叠在一起用。

我记得karpathy的llm wiki里面有提到，他会把自己的queries、LLM回答、自己的认识再导入回知识库里。这样是不是也包含了一部分的认知注入？

是的，确实包含，而且这是个很关键的观察。

Karpathy 那套里，用户的 queries、LLM 的回答、以及后续得到的分析结果可以再写回 wiki，这一步已经不只是“外部知识整理”了，而是在把人的关注点、问题意识、比较框架、阶段性理解，逐步沉淀进知识库。所以它不是完全没有认知注入，而是有一层“弱认知注入”或“间接认知注入”。

不过它和后者还是有明显区别。

llm-wiki 里的认知注入，主要是通过这些方式发生的：

- 你问了什么问题
- 你让 LLM 强调什么
- 你认可并保存了哪些分析
- 你如何设计 schema、页面结构、分类方式

这会让 wiki 越来越像“按你的研究路径组织过的外部知识”。

但后者那篇文章想做得更深。它不是只记录“你问过什么、保留了什么”，而是要从大量真实行为里蒸馏出更稳定的“你怎么判断”，比如：

- 你长期如何权衡速度和正确性
- 你做技术选择时优先看什么
- 你在商业判断里反复使用什么标准

也就是说：

llm-wiki 回灌的是“认知产物”。  
后者蒸馏的是“认知机制”。

前者已经开始带入人的视角，但更多还是围绕某个主题知识库在演化；后者则是试图把“人的思维风格本身”抽出来，变成可跨任务复用的上下文。

所以你的理解可以改成一句更准确的话：

Karpathy 的方案不是完全客观中立的知识库，它会随着用户的提问和回灌逐步带上用户的视角；只是这种视角更多体现为研究轨迹和主题理解，而后者追求的是更系统、更显式、更可迁移的个人判断原则注入。

最直接的结论是：**llm-wiki 更像外部知识层，context-infrastructure 更像个人认知层。前者完全可以作为底盘去兼容后者，做成一个双层知识库。**

**怎么融合**

可以把整个系统拆成四层：

1. raw/  
    放原始输入，既包括外部资料，也包括个人行为材料。

2. wiki/knowledge/  
    这是 llm-wiki 那一层，负责提炼“世界知识”。  
    产物是主题页、概念页、人物页、事件页、比较页、综述页。
    
3. wiki/self/  
    这是另一篇文章的核心层，负责提炼“个人判断原则”。  
    产物可以是 observation、pattern、axiom、decision-rule、preference-profile 之类页面。
    
4. schema/skills/  
    统一的调度层。  
    定义什么资料进哪条流水线、什么任务该优先读取哪些页面、回答后要不要回灌、怎样避免把事实和偏好混写。
    

这样一来，一个问题进入系统后，LLM 不再只查“外部知识页”，也会查“个人判断页”。最后回答时同时使用两种上下文：

- 事实层：这个世界里发生了什么
- 立场层：你通常会怎么看、怎么权衡

**谁兼容谁**

如果问“哪个更适合作为总架构去兼容另一个”，我会选 **llm-wiki 作为外壳**，再把“个人判断蒸馏系统”嵌进去。

原因很简单：

- llm-wiki 本来就是一个通用的知识编译框架，强调 raw -> wiki -> schema，扩展性很强。
- 它天然支持多种页面类型、持续 ingest、query、lint、回灌，足够容纳“自我认知页面”这种新页面类别。
- 而 context-infrastructure 更像一套专门解决“个人判断提炼”的管道，它很强，但更像一个垂直模块，不太像完整通用知识库壳子。

所以更自然的融合方式是：

**用 llm-wiki 管整个知识库生命周期，用 context-infrastructure 负责其中“self/axiom”这条特殊生产线。**

**融合后的好处**

这样做之后，系统会比两者单独存在都更强：

- 只有 llm-wiki，你会得到结构化知识，但判断可能仍偏“聪明的平均值”。
- 只有 context-infrastructure，你会得到更像你的 AI，但它对外部世界的知识组织可能不够稳固、可浏览、可审计。
- 两者结合后，AI 既知道“材料里写了什么”，也知道“你通常如何解释这些材料”。

这才更像真正可用的“个人知识操作系统”。

**但有一个关键风险**

融合时最需要防的是：**把事实和偏好混成一团。**

所以架构上最好强制分层：

- knowledge/ 存外部事实、论证、来源、冲突
- self/ 存个人原则、偏好、风格、历史判断模式
- 回答时明确区分：
    - “资料显示……”
    - “基于你的既有判断框架，更可能倾向于……”

否则知识库会越来越“像你”，但也可能越来越不清楚哪些是事实、哪些是偏见。

**一句话总结**

能融合，而且最合理的方式是：**以 llm-wiki 为总框架，兼容 context-infrastructure 作为“个人判断提炼子系统”**。这样能形成一个双轨知识库：一条轨道提炼世界知识，另一条轨道提炼你的判断原则，最后在 query 时汇合。

**四个核心区块**

raw/external/  
这里放外部资料，原则上不可改写，只允许补元数据。它是“外部事实源”。

raw/personal/  
这里放你的原始生活与工作记录，也原则上不可改写。它是“个人行为证据源”。

wiki/knowledge/  
这里提炼外部知识。重点是事实、概念、争议、关系、总结。

wiki/self/  
这里提炼个人判断原则。重点不是“你做过什么”，而是“你反复怎样判断”。

**为什么要加 wiki/bridges/**  
这是融合两套方法时最重要的一层。它负责把“知识”和“判断原则”连起来。

比如：

- topic-lens/ai-agents-through-my-lens.md
- judgments/how-i-evaluate-devtools.md
- applied-analysis/openai-harness-analysis-with-my-axioms.md

它们不是纯外部知识页，也不是纯自我原则页，而是“某个主题在你的判断框架下的解释结果”。

**推荐的页面类型**

wiki/knowledge/source-notes/  
每个原始外部材料一页，记录摘要、主张、证据、关键词、链接到相关 topic/concept/entity。

wiki/knowledge/topics/  
一个主题的综合页面，适合长期累积。

wiki/knowledge/comparisons/  
对两个或多个对象做对比，最好带维度表。

wiki/self/observations/  
从个人原始材料里提取的低层观察，偏流水账，不追求完全稳定。

wiki/self/patterns/  
跨时间重复出现的模式，比 observation 更抽象。

wiki/self/axioms/  
最高层、最稳定的判断原则。数量应该少，质量高。

wiki/self/decision-rules/  
比 axiom 更操作化，比如“做技术选型时先看维护成本，再看性能，再看生态锁定”。

wiki/bridges/judgments/  
把某个问题的外部事实和你的既有原则结合起来，产出“带立场的分析”。

**agent 应遵守的初始准则**

下面这组可以直接作为 AGENTS.md 的第一版核心规则。

``# Initial Principles ## 1. Respect Layer Boundaries - Never modify files in `raw/` except adding metadata when explicitly allowed. - Treat `raw/external/` as source evidence about the world. - Treat `raw/personal/` as source evidence about the user's behavior and judgments. ## 2. Separate Facts From Judgments - `wiki/knowledge/` stores claims about the world. - `wiki/self/` stores claims about the user's recurring preferences, heuristics, and decision principles. - `wiki/bridges/` stores analyses that combine world knowledge with the user's judgment framework. - Do not mix these three layers in one page unless the page type is explicitly a bridge. ## 3. Prefer Incremental Compilation - On every ingest, update existing pages when possible before creating new pages. - Create new pages only when a concept, entity, or principle cannot be cleanly represented in existing pages. - Preserve continuity and cross-links. ## 4. Evidence First - Every non-trivial claim should point to a source. - Mark whether a claim comes from external evidence, personal evidence, or synthesis. - If evidence is weak or indirect, say so explicitly. ## 5. Personal Principles Must Be Stable - Do not create an axiom from a single event. - First extract observations. - Promote repeated observations into patterns. - Promote stable patterns into axioms only when they recur across time or context. ## 6. Record Conflicts, Do Not Hide Them - If two external sources disagree, record the disagreement. - If the user's stated preference conflicts with past behavior, record both. - If an old axiom appears outdated, mark it as under review instead of silently replacing it. ## 7. Query By Need - For factual questions, prioritize `wiki/knowledge/`. - For personal-style or judgment questions, prioritize `wiki/self/`. - For advisory questions, combine both through `wiki/bridges/`. ## 8. Good Answers Are Assets - If a query produces a durable synthesis, save it back into the wiki. - File factual syntheses under `wiki/knowledge/syntheses/`. - File user-specific analyses under `wiki/bridges/`. ## 9. Keep The Knowledge Base Navigable - Update indexes and logs on every meaningful write. - Add cross-links for every page to at least one parent topic, related concept, or related principle. - Avoid orphan pages. ## 10. Be Explicit About Uncertainty - Distinguish between: - observed fact - inferred pattern - stable axiom - generated recommendation - Never present an inferred self-model as certain truth.``

**schemas 和 skills 的区别**

可以这样理解：

schemas 是“宪法和城市规划”。  
它定义的是整个知识库长期稳定的规则，比如：

- 哪些目录分别放什么
- 页面类型有哪些
- 什么叫 axiom
- 什么情况下允许新建页面
- 如何区分事实和判断
- ingest/query/lint 应该怎么做

它偏全局、长期、低频变化。

skills 是“针对某类任务的工具包和作战手册”。  
它定义的是某个具体任务怎么做，比如：

- 做调研时优先读哪些页面
- 写代码评审时调用哪些判断标准
- 写周报时用什么结构
- 做自我复盘时优先提取哪些 pattern

它偏局部、任务型、按需加载、高频调用。

一句话说：

- schema 决定“这个国家怎么运行”
- skill 决定“这次任务怎么干活”

**文章和思考怎么放进这个知识库**

你平时写文章记录思考，这种内容很重要，而且我建议不要只当作 raw/personal/ 的原始材料，也不要直接全塞进 wiki/self/axioms/。更合适的是把它看成一种**介于原始材料和提炼结果之间的中层产物**。

最自然的 fit 有三种：

**1. 作为 raw/personal/writings/ 的原始材料**  
如果这篇文章更像“当时的完整思考记录”，还没有经过系统蒸馏，就先放这里。  
它是你认知的证据之一，后续可以被 agent 提取 observation、pattern、axiom。

适合：

- 日记式文章
- 阶段性想法
- 某次事件后的即时反思
- 还不确定是否成熟的观点

**2. 作为 wiki/bridges/ 的桥接产物**  
如果文章是在“某个外部主题”上，加入了你的判断框架，那它其实是最典型的 bridge。

比如：

- 你怎么看 agent workflow
- 你如何评价某个产品方向
- 你对某篇论文的带立场解读

这类文章既不是纯外部知识，也不是纯个人原则，而是“你用自己的认知框架解释外部世界”的产物。放 bridges/ 最合适。

**3. 反向提炼到 wiki/self/**  
一篇文章写完后，agent 可以进一步问：

- 这篇文章暴露了哪些稳定判断标准？
- 哪些只是这次的临时意见？
- 哪些可以沉淀成 pattern 或 axiom？

也就是说，文章本身可以是成品；同时它又是蒸馏个人原则的输入。

所以文章在这个系统里通常有“双重身份”：

- 它本身是一项知识资产
- 它也是你认知结构的训练样本

**我建议你加一个专门的位置**

如果你平时确实会写很多文章，我建议显式给它一个区块，比如：

`raw/personal/writings/ wiki/bridges/essays/ wiki/knowledge/syntheses/`

可以这样分：

- 写作草稿、随想、未定型文章：raw/personal/writings/
- 已成型的“带你视角的主题文章”：wiki/bridges/essays/
- 偏客观综述、读书笔记、研究整合：wiki/knowledge/syntheses/

这样你的文章既不会被埋在原始材料里，也不会和最高层 axiom 混在一起。
