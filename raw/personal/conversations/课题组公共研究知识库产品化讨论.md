我现在的判断是：现有流程适合“增量维护一个逐渐变好的知识库”，不太适合“用 100-200 篇论文一次性冷启动出一个开箱即用、还能产出 insight 的公共版”。所以我会建议保留它的一些原则，但新增一套 bootstrap-first 的流程，并相应重设计 schema。

1. 现有 ingest 能不能吃下 100-200 篇论文？

能吃下“文件处理和单篇摘要”这件事，但不太能可靠地吃下“建出可用 wiki 并抽出高质量 insight”这件事。

它现在的优点是：

有明确的 source hierarchy：raw 是证据，wiki 是维护层。
有“优先更新已有页面而不是复制”的意识。
有把 tension、caveat、contradiction 写出来的习惯，这对 insight 很重要。
但它有几个结构性缺陷，会在 100-200 篇规模下暴露：

单篇驱动，不是语料驱动。
当前 schemas/ingest.md 和 skills/research-ingest/SKILL.md 默认动作是“读一个 source，找它该进哪个 page，更新那个 page”。这适合增量 ingest，不适合先看整个 corpus 再决定知识骨架。

缺少 bootstrap 的“中间层产物”。
现在只有 raw -> wiki/knowledge -> wiki/bridges。但大规模论文冷启动通常需要中间层，比如 paper cards、主题聚类、方法 taxonomy、时间线、对比矩阵。没有这一层，agent 很容易直接把 100 篇论文压成一堆松散 summary，最后 wiki 可读，但不够可用。

insight 的生成逻辑目前依赖 knowledge + self。
当前 bridge-write 明确是读 wiki/knowledge/ 加 wiki/self/ 再产出桥接分析。公共版去掉 self 后，insight 必须来自另一种东西，比如“课题组任务 lens”或“研究问题模板”。这个替代物现在 schema 里还不存在。

缺少面向领域建图的全局约束。
现有规则没有要求先定义：

核心问题空间
方法分类树
benchmark / task / setting 的命名规范
哪些是 canonical pages，哪些是 source summaries
没有这些，全量 ingest 很容易产出重复页、粒度失衡页、命名漂移页。

query 还不是“开箱即用 insight”导向。
现在的 query schema 更像“从现有 wiki 回答问题并在必要时写回”。公共版要的是，哪怕用户第一天就来问“这个方向有哪些空白点”“两类方法的关键 tradeoff 是什么”，系统也应直接落到已经准备好的 insight 页面或 insight 模板上。
所以结论是：
现有 ingest 可以作为新流程里的“单篇编译器”，但不能直接承担 bootstrap orchestrator。

2. 那应该搭什么新流程？

我建议新增一个专门的 bootstrap 流程，而不是硬把现在的 ingest 扩到 100-200 篇。

比较合理的冷启动流程大概是：

corpus intake
先把 100-200 篇论文整理成统一语料，带基本 metadata。
最少需要：标题、年份、作者、 venue、任务、方法、数据集、关键词、来源链接/文件。

paper card extraction
每篇论文先生成标准化 paper card，而不是直接写进 topic page。
每张 card 提取固定字段：

解决什么问题
核心方法
相比前作改进了什么
依赖什么假设
在什么 setting 下成立
明显局限
可复用到哪些主题页
corpus mapping
对 paper cards 做聚类和命名，形成领域骨架。
产物应该包括：

主题地图
方法 taxonomy
时间演化线
关键争议点
常见 evaluation 维度
knowledge synthesis
把上一步的骨架编译成 wiki/knowledge/ 的 canonical pages。
这一步不是按“论文一篇一页”，而是按“问题域/方法类/任务/benchmark/研究脉络”建页。

insight generation
再基于 knowledge 产出 wiki/insights/。
这里的 insight 不是自由发挥，而是按固定模板生产，比如：

研究机会页
方法比较页
选题判断页
实验设计建议页
文献间张力页
coverage review
最后检查知识图谱和 insight 图谱的覆盖度。
问的不是“论文都处理了吗”，而是：

核心主题是否都有 canonical page
主要方法路线是否都有比较页
关键分歧是否已有 tension page
课题组常见决策是否已有 insight 页
这样 public version 才是真的“第一天就可用”。

3. 整个 schema 要不要重设计？

要，但我建议是“保留底层原则，重写上层任务模型”，不是全部推倒。

我会保留的原则：

raw 作为不可变证据
wiki 作为维护层
local-first
优先更新、避免重复
显式记录 tension / uncertainty / contradiction
我会重写的部分：

仓库分层定义
从：
wiki/knowledge/
wiki/self/
wiki/bridges/
改成：

wiki/knowledge/
wiki/insights/
如果你愿意，还可以加一个很有用的中间层：

wiki/maps/ 或 wiki/corpus/
用来放 taxonomy、paper index、timeline、method map。
这是大规模 bootstrap 非常需要的一层。
ingest schema
当前 ingest 是 source-based，公共版需要 corpus-aware。
建议拆成至少两类：
bootstrap ingest schema：面向 100-200 篇冷启动
incremental ingest schema：面向后续新增论文/会议记录/实验记录
insight schema
这个现在其实缺席。
公共版要新增一个独立 schema，明确：
insight 页有哪些类型
每种 insight 页以什么证据为基础
什么叫足够强的 insight
怎样区分“材料复述”和“真正有判断价值的 synthesis”
query schema
query 不该再围绕 knowledge + self + bridge 设计，而应该改成：
factual question -> wiki/knowledge/
research judgment / planning / comparison -> wiki/insights/
repository gap -> 回退到 raw 或 corpus map
lint schema
lint 要新增针对公共研究库的检查：
taxonomy 命名是否一致
同一方法是否被重复命名
insight 页是否挂靠到足够的知识页
论文覆盖是否只停留在 source summary 而没进入 canonical knowledge
insight 是否过度脱离证据
4. 我觉得你最需要补上的，不是更多 ingest，而是“任务 lens”

当前自用版靠 self 提供非平庸视角。公共版没了 self，那就必须显式定义一套公共 lens，不然 insight 会退化成“总结得更像总结”。

这个 lens 可以写成公共的 research questions framework，例如：

一个方向为什么值得做
哪些约束下现有方法失效
哪些比较是表面优于、哪些是本质推进
哪些结果依赖特定 benchmark 假设
一篇论文最值得继承的是方法、问题设定、还是 evaluation 设计
对课题组选题来说，什么叫低风险高信息增量
本质上，公共版的 insight 来源会变成：

knowledge + explicit research lens -> insights

而不是现在的：

knowledge + self -> bridges

这一步非常关键。

5. 我的建议结论

如果目标是课题组公共版，我建议不要直接“删掉 self 然后把 bridges 改名成 insights”就上线。那样结构上更干净了，但产品能力还没真正切换。

更稳的路线是：

保留现有仓库的本地优先、证据分层、写回机制。
把 self/bridges 体系重构为 insights/ 体系。
新增一套 bootstrap schema，专门服务于 100-200 篇论文冷启动。
新增一套显式的 research lens / insight 模板。
把现有 ingest 降级为 bootstrap 流程里的一个子模块，而不是主流程本身。

context-infrastructure 最有价值的地方，不是“self”本身，而是它背后的多层去噪思想：不要从高噪声原始材料直接跳到高置信度结论，而是先经过若干中间层，把弱信号慢慢压缩成稳定结构。这个逻辑完全可以迁移到文献语料上。

如果套到公共版里，大致可以变成：

raw
原始论文、项目文档、会议记录、实验记录。这里对应生活记录，噪声最高。

paper cards 或 source notes
先把每篇论文压成标准化卡片。这里对应 observation。它还不是 insight，只是把单篇材料里的有效信号提纯出来。

corpus maps
把大量 paper cards 聚成主题、方法族、时间演化、争议点、评价维度。这里确实很像 pattern。它不是最终判断，但已经是跨文献的稳定结构。

wiki/insights
从 corpus maps 再往上提炼，形成研究机会、方法比较、选题判断、实验设计建议。这里很像 axiom，但我会更愿意叫它 research judgment，因为公共版里的结论通常应该保持“条件化”，而不是像个人 axiom 那样追求高度稳定的人格化原则。

所以你的直觉我基本同意：公共版可以借鉴 context-infrastructure 的“多层去噪”，只是把对象从个人痕迹换成文献语料，把产物从 patterns/axioms 换成 maps/insights。

不过我会补两个区别，避免类比过头。

第一，个人材料里的 axiom 是“这个人反复如此判断”，而公共版 insight 更像“在这组文献和这类任务下，目前较强的工作判断”。它通常比 personal axiom 更临时、更依赖语料边界，也更需要写清适用条件。

第二，文献 insight 不能只靠“重复出现”来升级。生活记录里，多次重复可能就足以支持 pattern；但文献里，一个观点反复出现，可能只是共识偏见，不一定是好 insight。所以公共版在从 maps 到 insights 的升级条件里，还要加入：

是否跨方法路线成立
是否经得住反例或 tension
是否对研究决策真的有区分度
是否能导出下一步行动
所以我会建议你把公共版的核心流程明确写成：

raw -> paper cards -> corpus maps -> insights

其中：

paper cards 是单篇去噪
corpus maps 是跨篇聚合
insights 是面向任务的高阶判断
这比直接 raw -> knowledge -> insights 更稳，也更接近你说的多层去噪结构。

四层含义

raw/
这里放原始证据，不追求可读性，只追求可追溯性。论文 PDF、论文 markdown、项目说明、组会记录、实验日志都在这里。

这个概念是什么

去噪流程

raw -> source cards -> maps -> knowledge / insights

raw

source card 设计

每篇论文先变成一张标准卡，不直接写进知识页。

建议字段：

标题
来源文件
年份
任务
研究问题
核心方法
关键假设

主要结果
局限
与哪些主题页相关

是否提供可提炼 insight 的 tension
这一步的作用是统一粒度，避免 agent 直接从原文自由发挥。

maps 设计

wiki/maps/ 建议至少有五类页面。

corpus overview
说明当前语料覆盖了什么，缺了什么。

taxonomy
把方法、任务、问题设定做成稳定分类树。

timeline
看领域是怎么演化的，哪些转折点重要。

comparison matrix
把常见方法按统一维度并排比较。

tension map
专门记录互相冲突、互相限制、互相补充的文献关系。

这层的本质就是你说的 patterns。它是跨文献的稳定结构，但还不等于研究判断。

insight 设计

wiki/insights/ 不应当是一个泛泛的“分析区”，而应当按固定页面类型生产。

建议至少有这五类：

research opportunity
某个空白点为什么值得做，证据是什么，进入门槛是什么。

method comparison
两类或多类方法在什么条件下各自成立，核心 tradeoff 是什么。

topic evaluation
某个选题值不值得做，为什么，现在是不是好时机。

experiment design
如果要验证某个判断，最小实验集应该怎么设计。

tension note
某组论文表面一致但实际上冲突在哪里，这个冲突是否值得进一步研究。

每类 insight 页都应强制包含：

适用问题
证据基础
判断
反例或限制
对课题组的下一步含义
这样能防止“insight”退化成华丽总结。

agent 工作流

我建议 agent workflow 分成四个模式。

bootstrap
适合第一次导入 100-200 篇论文。
流程：

盘点语料
生成 source cards
聚类并建立 maps
从 maps 生成 canonical knowledge pages
从 maps 和 knowledge 生成首批 insight pages
做 coverage review
incremental ingest
适合后续新增几篇论文、一次组会、一次实验记录。
流程：

分类材料
更新相关 source cards
更新受影响的 maps
必要时更新 knowledge
必要时刷新相关 insights
query
适合回答用户问题。
路由：

事实性问题先看 knowledge
结构性问题先看 maps
判断性/建议性问题先看 insights
若三者都不够，再回到 raw
lint
适合维护一致性。
检查：

taxonomy 是否漂移
knowledge 是否重复
maps 是否失链
insights 是否脱离证据
新材料是否只停留在 raw 而未进入结构层
bootstrap 工作流细化

这是最重要的一段。建议明确分阶段，而不是一口气 ingest 全部论文。

第一阶段：语料入库

把论文和其他材料放进 raw/
建 metadata 清单
去重
标记类型和主题
第二阶段：单篇去噪

每篇生成 source card
不要求长摘要，要求字段稳定
先保证覆盖率，再做深挖
第三阶段：群体建图

从 source cards 提炼主题簇、方法簇、时间线、张力点
产出 wiki/maps/
第四阶段：知识编译

把已经稳定的结构写成 wiki/knowledge/
优先写高复用页面，不追求全覆盖
第五阶段：insight 冷启动

用固定模板生成一批首批 insight 页
优先覆盖课题组最常见的判断任务
第六阶段：覆盖复核

检查是否已经能回答典型问题
检查哪些地方只有 summary 没有 insight
检查哪些 insight 证据还太薄
query 工作流

公共版 query 不该像现在这样依赖 self。新的默认顺序应是：

列出 consulted pages
先找 wiki/insights/
若 insight 不足，再看 wiki/maps/
再看 wiki/knowledge/
最后才下钻 raw/
原因是用户来问课题组公共版，往往想要的是判断，而不只是知识。

schema 重设计

建议新增并改写这些 schema。

schemas/bootstrap.md
定义大规模冷启动流程。
重点写清：

何时生成 source cards
何时建立 maps
何时可以产出 insight
coverage 如何判断
schemas/ingest.md
保留，但改成增量 ingest 版本。
它不再负责冷启动全局建图，只负责更新已有结构。

schemas/query.md
改成：

factual -> knowledge
structural -> maps
evaluative/advisory -> insights
schemas/insight.md
这是新公共版最重要的新 schema。
需要定义：

insight 页类型
每类 insight 的证据门槛
输出模板
何时只能写成 tension note，不能上升为 opportunity 或 recommendation
schemas/lint.md
新增：

taxonomy consistency
alias normalization
map orphan detection
insight-to-evidence linkage
stale insights 检查
skill 设计

建议新增两个 skill。

kb-bootstrap
负责大规模冷启动，不要让 kb-ops 兼任。
它的职责是 orchestration，不是逐篇摘要。

map-build
负责从 source cards 生成 maps。
这是公共版的关键 skill，因为 insight 质量很大程度取决于 map 质量。

同时把现有：

research-ingest 保留为单篇或小批量编译器
bridge-write 改造成 insight-write
insight 的升级标准

从 maps 升级到 insights 时，我建议至少满足其中两到三条：

不是单篇论文结论，而是跨至少多篇材料的综合
不是简单共识复述，而是有区分度的判断
能明确指出适用条件
能指出反例、限制或 tension
能转化成课题组下一步行动
如果不满足，就先留在 maps，不要硬升成 insight。

第一天可用版本的最小集合

如果要“部署即能用”，我建议最少先产出这些页面：

1 个 corpus overview
3 到 5 个 taxonomy / timeline / comparison matrix
8 到 15 个高复用 knowledge 页面
5 到 10 个高价值 insight 页面
这些 insight 页优先覆盖：

方向选择
方法比较
常见实验设计
重要张力
研究空白
这样第一天用户就不需要等“积累”，而是直接能提问。

一句话总结

这个公共版最适合被设计成一个“研究语料的多层去噪系统”：

raw 保留原始证据
source cards 提取单篇信号
maps 形成跨篇结构
knowledge 保存稳定事实
insights 产出面向课题组任务的判断
agent 的核心职责也不再是“帮我记住”，而是“把大语料稳定编译成可导航、可判断、可持续更新的研究工作面”。

1. 怎么避免只提炼出共识，而无法支持导师寻找反共识和 gap

你这个判断是对的。只从语料自动提炼，系统天然更容易产出：

主流分类
常见结论
重复出现的比较维度
也就是更接近 consensus surface，而不是 anti-consensus surface。

问题不在于多层去噪本身，而在于公共版目前还缺一条“判断写回链路”。自用版靠 self 解决这个问题；公共版没了 self，就必须换成另一种显式机制。我建议不要恢复 self/，而是新增一种更适合公共研究场景的层或页面类型：

wiki/insights/hypotheses/
或更简单一点，直接在 wiki/insights/ 里容纳两类内容：
corpus-derived insights
judgment-augmented insights
核心区别是，后者明确允许把导师或课题组成员的研究判断写进去，但要标清来源和置信度。

我建议把 insight 拆成三种证据层：

corpus finding
来自多篇文献的稳定综合。偏共识。
tension
来自文献间冲突、空白、假设不一致。是 gap 的前体。
research judgment
由导师或课题组成员提出的非共识判断，但要锚定到前两者，而不是凭空写。
这样做有几个好处。

第一，不会把导师判断伪装成“领域事实”。
第二，它允许真正有价值的反共识进入系统。
第三，它让 query 的高质量问答可以沉淀成研究判断资产，而不是一次性聊天。

所以我同意你说的：query 必须继续承担写回职责，而且对公共版来说，这个职责比现在更重要。
新的 query write-back 规则可以是：

如果问题只是事实查询，回写到 wiki/knowledge/
如果问题暴露了跨文献结构，回写到 wiki/maps/
如果问题产出了有区分度的判断、反共识假设、潜在 gap、或新的比较框架，回写到 wiki/insights/
换句话说，公共版里真正承接“导师 lens”的，不是 self，而是“带证据锚点的研究判断页”。

我会建议 insight 页固定加一段：

判断来源
文献综合
组内问答沉淀
导师研究判断
置信度
低 / 中 / 高
证据锚点
对应 knowledge / maps / raw
这样既能保留非共识，又不破坏层次。

对学生来说，你说得也对。学生主要需要的是共识、脉络和指导，所以他们主要消费：

2. 保持精髓的前提下，什么是最小可用但又足够惊艳的 MVP

我会把复杂架构再压缩一层。
MVP 不要一开始就做完整的 raw / source cards / maps / knowledge / insights 五段式显式系统。
MVP 应该只保留三个用户可见层，加一个隐含中间层。

我建议的 MVP 是：

raw/
wiki/knowledge/
wiki/insights/
但在 workflow 里，仍然保留一个轻量的 maps 角色，只是先不把它做成很大的目录体系。可以先缩成一两个总表页，比如：

wiki/knowledge/领域地图.md
wiki/knowledge/方法比较矩阵.md
也就是说，MVP 的精髓是保留“多层去噪”，但把 maps 折叠进少量高价值知识页，而不是先建完整 wiki/maps/ 目录。

如果目标是“让人一眼惊艳”，我觉得 MVP 不是靠目录复杂，而是靠第一次问答就能看到三种神奇能力同时出现：

能快速给出领域脉络。
用户问“这个方向主要分几条路线”，系统能直接回答，而且有组织。

能指出关键 tension。
用户问“这几类方法真正分歧在哪里”，系统不是只列优缺点，而是指出假设冲突和盲区。

能形成可行动的研究建议。
用户问“接下来最值得补哪块”，系统能给出带理由的判断，而不是泛泛建议。

所以 MVP 我会设计成：

MVP 架构

raw/
wiki/knowledge/
wiki/insights/
MVP 中最少的高价值页面

1 个领域总览页
1 个方法比较矩阵页
1 个关键张力页
3 到 5 个主题知识页
3 个 insight 页：
值得做的 gap
最重要的方法 tradeoff
建议优先验证的实验方向
MVP agent 工作流

导入一批核心论文，不求全，只求代表性。
先生成论文卡片，但卡片可以先放在 raw/ 辅助文件或单独索引里，不必完整产品化。
直接产出三类高价值页面：
领域地图
方法比较
研究机会
后续 query 强制写回高价值问答。
让导师通过问答逐步把“非共识判断”注入 wiki/insights/。
所以如果只做 MVP，我会把产品定义收紧成一句话：

“这是一个能把一批代表性论文快速编译成领域地图、关键张力和研究机会的本地研究助手。”

它不需要先做全量冷启动，也不需要先把所有 schema 做满。
它只要第一次就能把“共识 + tension + 下一步建议”一起给出来，用户就会觉得神奇。

我的建议结论

第一点上，我建议不要试图只靠语料自动产生反共识。更现实的做法是：

让语料负责提供共识和 tension
让导师通过 query 把研究判断持续写回 wiki/insights/
第二点上，我建议 MVP 先压缩成：

raw
wiki/knowledge
wiki/insights
然后把 maps 暂时折叠成少量关键知识页，不单独做完整层。这样既保留精髓，又能最快做出“第一次用就惊艳”的效果。
